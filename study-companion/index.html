Claude API Basics

Overview of Claude Models

  • Opus is the highest-intelligence family for complex, multi-step reasoning (higher cost/latency); Sonnet balances intelligence, speed, and cost with strong coding ability for most practical use cases; Haiku is fastest/cheapest with no reasoning capability, suited to real-time and high-volume work. →
  • Teams commonly mix models within one application rather than picking a single one — e.g. Haiku for real-time chat, Sonnet for core logic, Opus for the hardest reasoning steps. →

Accessing the API

  • Never call the Anthropic API directly from a client app — the client sends text to your server, which holds the API key and calls the API with the SDK (Python, TypeScript, Go, Ruby) or plain HTTP. →
  • Generation runs through four stages: tokenization (text → tokens), embedding (tokens → numeric meaning vectors), contextualization (embeddings adjusted by neighboring tokens), and generation (repeatedly sampling the next token by probability until max_tokens or an end-of-sequence token stops it). →

Making a Request

  • Setup is: pip install anthropic python-dotenv, store the key in a .env file (never in version control), load it with python-dotenv, then create the client and call client.messages.create(model, max_tokens, messages). →
  • max_tokens is a safety ceiling on length, not a target; the generated text is at message.content[0].text, and a user message is {"role": "user", "content": "..."}. →

Multi-Turn Conversations

  • The Anthropic API is stateless and stores nothing — every follow-up call must resend the entire message history yourself, or the response loses all context of what came before. →
  • Standard helpers — add_user_message, add_assistant_message, and a chat(messages) wrapper — build up a running list of {"role", "content"} dicts and resend it whole on each call. →

System Prompts

  • A system prompt (passed via the system keyword) controls how Claude responds rather than what — e.g. a "patient math tutor" role produces guiding hints instead of the direct answer to the same question. →
  • Build the API params as a dict and only add the system key when a prompt is actually supplied — handling the None case this way avoids passing an invalid empty system string. →

Temperature

  • Temperature (0-1) shapes how much lower-probability tokens get a chance during sampling — 0 is fully deterministic (always the top-probability token), and higher values increase the odds of variation without guaranteeing it. →
  • Use low temperature near 0 for factual/extraction tasks needing consistency, and high temperature near 1 for creative writing, brainstorming, or marketing copy. →

Response Streaming

  • Streaming exists because a full response can take 10-30 seconds — Claude sends an initial acknowledgment immediately, then a sequence of events, of which only content_block_delta carries actual text chunks. →
  • client.messages.stream() with its text_stream property gives clean incremental text for the UI, and stream.get_final_message() assembles the complete message afterward for storage. →

Controlling Model Output

  • Pre-filling the assistant message (e.g. ending it with "Coffee is better because") makes Claude continue exactly from that point rather than restart — the final output must be stitched from the pre-fill plus what Claude generates. →
  • A stop sequence halts generation the instant that exact string is generated and excludes it from the output — e.g. stopping on "five" during "count 1 to 10" leaves the response at "four, " while a stop sequence of ", five" produces the cleaner "one, two, three, four". →

Structured Data

  • Pre-filling an opening delimiter (e.g. "```json") plus a stop sequence on the closing delimiter ("```") makes Claude output only the raw structured content, with no headers or explanatory commentary. →
  • The technique works for any structured format (JSON, Python, lists), not just JSON — anywhere clean, directly copy/pasteable or parseable output is needed. →

Prompt Evaluation

Prompt Evaluation

  • Prompt evaluation is objective, automated testing of a prompt — distinct from prompt engineering (the craft of writing it) — and evaluation comes first to establish a measurable baseline before optimizing. →
  • Testing once or twice before shipping, or only tweaking against a handful of custom inputs, are both common traps; running the prompt through a real evaluation pipeline for an objective score is the recommended path. →

A Typical Eval Workflow

  • The six-step loop: draft an initial prompt, build an eval dataset (3 examples to thousands, hand-written or LLM-generated), interpolate each input into the prompt template, get Claude's response for each, grade every response (e.g. 1-10), average the scores, then iterate. →
  • There's no standard required methodology or tool — objective scoring is what enables systematically comparing prompt version A against version B rather than guessing. →

Generating Test Datasets

  • For an AWS code-assistance prompt (output only Python, JSON config, or regex, nothing else), the dataset is generated by asking Claude (often a faster model like Haiku) to produce realistic test task descriptions. →
  • The generation call itself uses the pre-fill ("```json") + stop-sequence ("```") pattern to force clean, parseable JSON, which then gets saved to a file for reuse across eval runs. →

Running the Eval

  • The eval pipeline is three small functions: run_prompt merges a test case into the prompt and calls Claude, run_test_case calls run_prompt and (once real grading exists) scores the output, and run_eval loops the whole dataset through run_test_case. →
  • At this stage scoring is a hardcoded placeholder and the prompt has no output-formatting instructions, so responses are verbose — the next step is wiring in an actual grader. →

Model Based Grading

  • The three grader types: code graders (programmatic checks — length, syntax, keywords), model graders (an extra API call judging quality/instruction-following), and human graders (most flexible, most time-consuming). →
  • A model-grading prompt should explicitly request strengths/weaknesses/reasoning alongside the score — asking for a bare number tends to produce default middling scores, whereas requiring justification surfaces real signal. →

Code Based Grading

  • validate_json(), validate_python() (via AST parsing), and validate_regex() (via compilation) each return 10 on success and 0 on any parse error — the dataset needs a "format" field so grade_syntax() can dispatch to the right validator. →
  • The final score averages the model score with the syntax score: (model_score + syntax_score) / 2, combining semantic evaluation with mechanical validity. →

Prompt Engineering

Prompt Engineering

  • The improvement loop is: write a deliberately weak first draft, evaluate it, apply one technique, re-evaluate, repeat — the meal-plan example climbs from a poor baseline score with each successive technique. →
  • The eval setup supports concurrency (tunable against rate limits) and produces an output.html report showing every test case, its score, and the grading reasoning. →

Being Clear and Direct

  • The first line of a prompt matters most — lead with an action verb (write, generate, identify, analyze) plus a precise description of the task and expected output. →
  • In the worked example, switching to a direct action-verb opening alone raised the eval score from 2.32 to 3.92. →

Being Specific

  • Type A guidelines list desired output attributes (length, structure, format) and are almost always worth adding; Type B guidelines give the model an explicit step-by-step process, reserved for complex problems needing broader consideration. →
  • Adding guidelines to the meal-plan prompt lifted its score from 3.92 to 7.86 — a bigger jump than clarity alone, since specificity narrows the model's output space directly. →

Structure with XML Tags

  • Wrapping distinct content blocks in descriptive tags (, , — never generic ones like ) tells the model exactly where one kind of content ends and another begins. →
  • This matters most once a prompt interpolates multiple large blocks (like code vs. documentation), but even short content benefits from a tag that marks it explicitly as external input. →

Providing Examples

  • One-shot is a single example, multi-shot is several; wrap each in XML with sample input and ideal output, and use them especially for corner cases (like sarcasm detection) and complex output formats. →
  • A strong source of examples is your own eval results — pull the highest-scoring outputs and place them after the main instructions, optionally with a brief note on why the output is ideal to reinforce the desired behavior. →

Tool Use

Introducing Tool Use

  • Tool use exists because Claude only knows its training data — the loop is: Claude requests external data it needs, your server fetches it (e.g. calling a weather API), and Claude composes the final answer using that data. →
  • The code you write runs in the opposite order from the logical flow (function → schema → result handling → included in the request), which is why it helps to keep the flow diagram in view while implementing. →

Project Overview

  • The course project teaches Claude to set time-based reminders, exposing three real gaps: it doesn't know the precise current time, sometimes miscalculates date arithmetic (e.g. "379 days from January 13th, 1973"), and has no mechanism to actually create a reminder. →
  • Three tools close those gaps one at a time — get current datetime, add a duration to a datetime, and set the reminder — built individually before being combined into multi-tool coordination. →

Tool Functions

  • Tool functions are plain Python functions Claude calls automatically when it needs information it can't produce itself — descriptive names for the function and its arguments matter because Claude reads them to decide how to call it. →
  • Raise a clear error (e.g. "date format cannot be empty") rather than failing silently on bad input — Claude reads the error message and can retry with corrected parameters. →

Tool Schemas

  • A tool schema is a JSON Schema (a general-purpose, non-LLM-specific validation format) with a name, a 3-4 sentence description of what it does/when to use it/what it returns, and an input_schema describing each argument. →
  • A fast way to build one: paste your function code into Claude.ai along with Anthropic's tool-use documentation and ask for a compliant schema; wrap the result in ToolParam (from anthropic.types) to prevent type errors. →

Handling Message Blocks

  • Once tools are introduced, a request must include the tools parameter, and responses become multi-block: a text part (for the user) plus a tool_use part (function name + arguments). →
  • The entire response.content (every block, not just text) must be appended to the message history — helper functions that only handled a single text block need updating to accept a list of blocks. →

Sending Tool Results

  • A tool_result block carries tool_use_id (matching the original request), content (the function's output, usually JSON), and is_error (false by default) — it goes back to Claude inside a user message, not an assistant one. →
  • The original tool schemas must be included again in the follow-up call even though you're just sending results — omitting them breaks Claude's understanding of what the tools even are. →

Multi-Turn Conversations with Tools

  • A single user query can require multiple sequential tool calls — e.g. "what day is 103 days from today" needs get_current_datetime, then add_duration_to_datetime, before Claude can answer. →
  • A while loop keeps calling Claude and executing requested tools as long as the response contains tool_use blocks, since you can't predict in advance how many chained tool calls a query will need. →

Implementing Multiple Turns

  • The run_conversation loop calls Claude, appends its response, checks stop_reason, and (if it's "tool_use") calls run_tools and feeds the results back as a user message — repeating until stop_reason is anything else. →
  • run_tools filters content for tool_use blocks and dispatches each to the right function via run_tool, wrapping execution in try/except so failures return is_error: true with the error message rather than crashing the loop. →

Using Multiple Tools

  • Once the first tool is wired up, adding another is a fixed three-step pattern: add its schema to RunConversation's tools list, add a matching case in RunTool, and implement the actual function. →
  • Assistant responses can mix multiple blocks in one message (text plus several tool_use blocks), and Claude can chain tools on its own once all are registered (e.g. calculate a date, then set a reminder with the result). →

The Batch Tool

  • Claude can technically emit several tool_use blocks in one message but rarely does in practice, so a batch_tool schema (a list of "invocations," each a tool name + arguments) is introduced to make it prefer parallel execution. →
  • The batch handler parses each invocation's JSON arguments and dispatches them through run_tool, returning all results together — cutting a chain of sequential round trips down to a single request-response cycle. →

Tools for Structured Data

  • Define a schema whose inputs match your desired JSON shape, then force Claude to call it via tool_choice = {"type": "tool", "name": "your_tool_name"} — the structured data comes back directly at response.content[0].input, with no tool_result step needed. →
  • This is more reliable than the prompt pre-fill/stop-sequence method but requires more setup — reserve it for extractions where reliability matters more than simplicity. →

Fine Grained Tool Calling

  • By default the API buffers a tool's JSON argument chunks and validates them against the schema before sending, which produces a delay followed by a burst of chunks arriving together rather than a smooth stream. →
  • Setting fine_grained: true disables that server-side validation so chunks stream immediately as generated (useful for early UI updates), but shifts the burden of handling potentially invalid JSON (e.g. "undefined" instead of null) onto the client. →

The Text Edit Tool

  • Claude ships only the JSON schema for the text editor tool (view, str_replace, create, insert, undo_edit) — you must write the implementation for every command yourself. →
  • The schema type string is version-specific (Claude 3.5 vs. 3.7 use different date-stamped identifiers) — sending the wrong one breaks the integration even though the small stub auto-expands to the full schema. →

The Web Search Tool

  • Web search needs only a minimal schema (type "web_search_20250305", name "web_search", max_uses) — Claude runs the search itself, with no custom implementation required. →
  • allowed_domains restricts results to specific sources (e.g. NIH.gov for medical content) to improve quality, and the response mixes text, search-result blocks (title/URL), and citation blocks that a UI should surface separately for transparency. →

Retrieval-Augmented Generation

Introducing Retrieval Augmented Generation

  • Feeding a 100-1000+ page document straight into the prompt hits hard token limits and gets slower/costlier as prompts grow — RAG instead chunks the document and injects only the chunks relevant to the current question. →
  • RAG trades added complexity (a chunking strategy, a relevance-search mechanism, no guarantee retrieved chunks hold the complete context) for the ability to scale to large or multiple documents at lower cost. →

Text Chunking Strategies

  • Poor chunking causes wrong-context retrieval — e.g. a medical "bug" chunk surfacing for a software-engineering question purely from word overlap — so how a document is chunked directly shapes RAG quality. →
  • Size-based chunking is easiest and most common in production but cuts words mid-sentence unless overlap is added between neighboring chunks; structure-based chunking (splitting on headers) needs guaranteed formatting, while character-based chunking is the most reliable fallback across arbitrary document types. →

Text Embeddings

  • An embedding model outputs a long vector (values -1 to +1) representing text meaning; the individual numbers are opaque, but it helps to imagine each as a score for some unnamed semantic quality. →
  • Anthropic recommends Voyage AI for embedding generation (a separate account/API key, free to start) — embeddings power semantic search by comparing meaning rather than exact keywords. →

The Full RAG Flow

  • The seven-step pipeline: chunk the document, embed each chunk, normalize the vectors to unit magnitude, store them in a vector database, embed the incoming query the same way, run a similarity search, then assemble a prompt from the question plus the retrieved chunks. →
  • Cosine similarity ranges -1 to 1 (closer to 1 = more similar); cosine distance is 1 minus that, so values near 0 indicate high similarity between the query and a stored chunk. →

Implementing the Rag Flow

  • A minimal implementation: chunk by section, embed each chunk, store embedding + metadata (the original text) pairs via zip() into a vector index, embed the incoming query, then call store.search(query_embedding, k) for the top-k matches by cosine distance. →
  • Storing the original text alongside each embedding is deliberate — a bare embedding vector alone is meaningless to a developer, so metadata is what makes a retrieved result actually usable. →

BM25 Lexical Search

  • BM25 is a keyword-based algorithm that tokenizes the query, counts term frequency across chunks, and weights rare terms (like "incident 2023") higher than common ones ("a", "the") — catching exact-match cases pure semantic search can miss. →
  • The fix for semantic search alone missing exact-term matches is hybrid search: run BM25 and vector search in parallel and merge the results, since each catches cases the other misses. →

A Multi-Index Rag Pipeline

  • A retriever class wraps a vector index and a BM25 index behind one add_document/search API, then merges their rankings with Reciprocal Rank Fusion: score = sum of 1/(1+rank) across the methods that returned each document. →
  • In the worked example, vector search returns [doc2, doc7, doc6] and BM25 returns [doc6, doc2, doc7] — RRF produces [doc2, doc6, doc7] because doc2 ranks well in both, showing how cross-method agreement wins. →

Reranking Results

  • After hybrid retrieval, an LLM call re-orders the merged candidates by relevance — documents get short IDs (so Claude returns compact ordered IDs, not full text) with pre-fill/stop-sequence used for clean, structured JSON output. →
  • This adds latency but catches cases hybrid retrieval alone gets wrong — e.g. correctly moving a "software engineering + incident 2023" section above an unrelated cybersecurity section for an ambiguous "engineering team" query. →

Contextual Retrieval

  • Because chunking strips a chunk of its surrounding context, an LLM pre-processing step generates a short description of how each chunk fits into the larger document, which gets joined to the chunk before it's indexed. →
  • For documents too large for one prompt, only a subset is used for context generation — the opening chunks (for a summary/abstract) plus the chunks immediately preceding the target — skipping less-relevant middle sections. →

Claude Features

Extended Thinking

  • Extended thinking lets Claude reason before answering, returned as a thinking block (with a cryptographic signature preventing tampering) plus the final text block — thinking tokens are billed and add latency, with a minimum thinking_budget of 1024 tokens. →
  • max_tokens must exceed thinking_budget (e.g. a 1024 budget needs max_tokens ≥ 1025); enabling extended thinking should be eval-driven — turn it on only after prompt optimization alone fails to reach the needed accuracy. →

Image Support

  • A request can carry up to 100 images, each priced by pixel dimensions; naive prompts against images ("how many marbles?") tend to undercount or otherwise produce inaccurate results. →
  • Accuracy comes from prompting technique, not image quality — step-by-step analysis instructions with a verification/recount step, or one-shot/multi-shot examples alternating image and text parts, meaningfully improve results (demonstrated in a satellite-imagery fire-risk assessment). →

PDF Support

  • PDF handling reuses nearly identical code to image support — swap the file type to "document", the media type to "application/pdf", and rename the variable to file_bytes. →
  • Claude can extract text, images, charts, and tables from a PDF in one pass, making it a single tool for comprehensive document analysis rather than needing separate extraction pipelines. →

Citations

  • Enabling citations ({"enabled": true} plus a source document) makes Claude reference exactly where in the source a statement came from — citation_page_location for PDFs (document index/title/start-end pages) and citation_char_location for plain text (character position). →
  • The response becomes a list of text blocks, some carrying a citations array, letting a UI build hover popups that show users the exact supporting source text — verifying Claude's interpretation rather than trusting it blindly. →

Prompt Caching

  • Normally Claude discards all the internal computation on a request's input the moment it responds — prompt caching stores that work instead so an identical follow-up request can reuse it rather than recomputing from scratch. →
  • The benefit is speed and lower cost, but it depends on the input text being exactly identical to what was previously cached — any difference means normal (uncached) processing happens instead. →

Rules of Prompt Caching

  • A cache point requires the longhand text-block format ({"type": "text", "text": ..., "cache_control": {...}}) — the shorthand plain-string content can't carry a cache_control at all. →
  • Everything up to and including the breakpoint is cached (nothing after); the cache lasts 1 hour on the direct Anthropic API, requires a minimum 1024 tokens, allows up to 4 breakpoints, and any change to pre-breakpoint content invalidates the entire cache — the best candidates are stable content like system prompts and tool schemas. →

Prompt Caching in Action

  • Implementation adds a cache_control field with type "ephemeral" to the last tool in the list (cloning it rather than mutating the original schemas) and wraps the system prompt as a text block with the same cache_control — processing order is tools → system prompt → messages. →
  • usage.cache_creation_input_tokens reports tokens newly written to cache; usage.cache_read_input_tokens reports tokens reused from it, with partial cache reads possible when only some of the cached content still matches. →

Code Execution and the Files API

  • The Files API lets you upload a file once and reference it by ID in later requests instead of re-sending raw file data every time. →
  • The code execution tool runs Claude-written Python inside an isolated Docker container with no network access — combined with the Files API, Claude can read an uploaded file by ID, execute analysis code against it, and produce downloadable output files (like plots or reports) by their returned file IDs. →

Model Context Protocol

Introducing MCP

  • MCP shifts tool definition and execution to a dedicated MCP server rather than requiring your own server to author and maintain schemas and functions for every integration (e.g. a full GitHub chatbot needing tools for repos, PRs, issues, projects). →
  • MCP and tool use are complementary, not identical: MCP addresses who builds and runs the tool (a specialized server rather than you), while tool use is the underlying mechanism through which Claude calls it either way. →

MCP Clients

  • The MCP client sits between your server and the MCP server, relaying list-tools and call-tool requests/results over a transport-agnostic connection (stdio, HTTP, WebSockets) — it never executes a tool itself. →
  • A full round trip: your server → client (list tools) → MCP server responds → tools handed to Claude → Claude requests execution → client (call tool) → MCP server executes (e.g. a GitHub API call) → the result flows back through the same chain to Claude and the user. →

Project Setup

  • The course project builds a CLI chatbot implementing both an MCP client and server side by side purely for learning — a real project would normally build only one side. →
  • It works against fake in-memory documents with two tools (read and update contents); setup is the standard download-configure-install-run sequence via uv or python. →

Defining Tools with MCP

  • The MCP Python SDK auto-generates a tool's JSON schema from a decorated function (@mcp.tool(name=..., description=...) + typed parameters with pydantic Field descriptions) — no manual schema writing. →
  • The example tools are read_doc_contents (returns content by doc_id, raising ValueError if missing) and edit_document (doc_id, old_string, new_string performing a find/replace), both validating existence before acting. →

The Server Inspector

  • The MCP Inspector is an in-browser debugger launched with "mcp dev [server_file.py]" — its left sidebar Connect button starts the server, and the Tools panel lets you select a tool, fill parameters, and Run Tool to verify the result. →
  • It's built for live testing during development (e.g. chaining a read after an edit to confirm the change took effect) before wiring the server into a real application, and its UI is expected to keep evolving. →

Implementing a Client

  • A wrapper class around ClientSession exposes list_tools() (await self.session.list_tools(), return result.tools) and call_tool() (await self.session.call_tool(name, input)) to the rest of the codebase, with resource cleanup handled through async enter/exit. →
  • The common pattern is wrapping the client session in a larger class rather than using the raw session directly, so connection lifecycle management stays in one place. →

Defining Resources

  • Resources expose data for reads, not actions — a direct/static resource has a fixed URI (docs://documents), a templated one has wildcard parameters (documents/{doc_id}) that become function keyword arguments. →
  • Defined with @mcp.resource and a MIME type (application/json, text/plain); the SDK auto-serializes return values to strings, and the common pattern is one resource per distinct read operation. →

Accessing Resources

  • The client reads a resource via session.read_resource(AnyUrl(uri)), takes result.contents[0], and branches on mime_type — application/json parses with json.loads(), otherwise it returns plain resource.text. →
  • This lets a CLI show a resource list the user selects with arrow keys/space, with the content going straight into the prompt rather than requiring a tool call to fetch it. →

Defining Prompts

  • MCP prompts are pre-defined, tested instructions a server exposes for its domain (e.g. document formatting) so users or clients don't need to write ad-hoc prompts themselves. →
  • Defined with @mcpserver.prompt(name, description); the function takes parameters (like a document ID) and returns a list of base.UserMessage objects ready for the LLM, surfaced to clients as slash-command autocomplete. →

Prompts in the Client

  • The client calls list_prompts() (returning result.prompts) and get_prompt(name, arguments) (returning result.messages) to retrieve a server-defined template with runtime values already interpolated. →
  • Arguments flow from the client call → the prompt function's keyword arguments → interpolated into the prompt text → the final messages array fed directly to the LLM. →

Anthropic Apps: Claude Code & Computer Use

Anthropic Apps

  • Claude Code and Computer Use are Anthropic's own deployed applications, both used in this course as concrete, learnable examples of agent architecture rather than one-off features. →
  • Studying how these two are built is the practical bridge from tool use into the agents-and-workflows material that follows. →

Claude Code Setup

  • Claude Code is a terminal-based coding assistant that can search/read/edit files, use advanced tools like web fetching and terminal access, and act as an MCP client to pull in tools from external MCP servers. →
  • Setup is Node.js → npm install → run "claude" in the terminal to log into your Anthropic account, with the full guide at docs.anthropic.com. →

Claude Code in Action

  • Running the init command has Claude scan the codebase and produce a claude.md capturing architecture and coding-style notes, which then loads automatically as context on every future request — project, local, and user memory files all layer together. →
  • Two effective workflows for a complex feature: (1) read relevant files → plan without writing code yet → implement the plan, or (2) read context → suggest tests (no implementation) → implement the chosen tests → write code until they pass — treating Claude Code as a collaborative engineer, not just a generator, is the core mindset. →

Enhancements with MCP Servers

  • Claude Code has an embedded MCP client, so "claude mcp add [server-name] [startup-command]" connects an external MCP server (e.g. documents, Sentry, Jira, Slack) and a restart picks up its new tools. →
  • This lets Claude Code gain capabilities dynamically (e.g. converting PDF/Word documents to Markdown) without any change to Claude Code's own core. →

Parallelizing Claude Code

  • Git worktrees solve the file-conflict problem of running multiple Claude instances at once — each worktree is a complete, isolated project copy tied to its own branch. →
  • The full workflow (create worktree → assign a task → work in isolation → commit → merge back → clean up) can itself be delegated to Claude, including automatic conflict resolution during the merge and removing finished worktrees; .claude/commands markdown files with an $ARGUMENTS placeholder automate this via /project:command-name. →

Automated Debugging

  • A daily GitHub Action pulls CloudWatch logs, Claude deduplicates and analyzes the errors, generates fixes, and opens a PR — a real example caught an "invalid model identifier" typo that only broke in production, not locally. →
  • Human review of the proposed fix before merge is still required — this automates detection, log-hunting, and diagnosis, not unattended deployment. →

Computer Use

  • Computer use lets Claude take screenshots and perform clicks/typing/scrolling to drive an actual interface, running inside an isolated Docker container for safety. →
  • The primary use cases are QA and web-application testing — Claude navigates, fills forms, identifies bugs, and reports pass/fail results the way a human tester would. →

How Computer Use Works

  • Computer use is a special case of the ordinary tool-use loop: a minimal schema expands into a large action-function structure (mouse move, left click, screenshot, etc.), and Claude sends tool_use requests exactly as it would for any tool. →
  • Claude never touches the machine directly — a developer-provided execution environment (Anthropic's reference implementation runs it in Docker) performs the actual key presses and mouse movements and returns the result. →

Agents and Workflows

Agents and Workflows

  • Use a workflow when the exact steps are known ahead of time; use an agent when the task details are uncertain and Claude needs to figure out the approach itself using its tools. →
  • The image-to-3D-model example follows an evaluator-optimizer pattern: Claude + CADQuery produces a model (the producer), Claude compares the rendering to the original image (the evaluator), and the loop repeats until the evaluator accepts the result — a workflow is a proven pattern, but you still write the actual implementation code. →

Parallelization Workflows

  • Instead of one large prompt juggling many criteria at once (e.g. "choose the best material: metal, polymer, ceramic, composite..."), split it into separate simultaneous requests, each judging one option, then aggregate the results in a final step. →
  • This buys focus (each request handles one concern), independent optimization (each sub-prompt can be improved on its own), and easy scalability (new sub-tasks don't disturb existing ones). →

Chaining Workflows

  • Rather than one prompt trying to satisfy many constraints at once, chaining splits a task into sequential steps where each step's output feeds the next (topic → trending search → topic selection → research → script → video → post). →
  • It's the fix specifically for a prompt that keeps violating some constraints despite repetition in a single call — accept an imperfect first pass, then send a focused follow-up asking Claude to fix just the specific violations it produced. →

Routing Workflows

  • A routing step first classifies user input into a predefined category, then forwards it to a category-specific pipeline with its own tailored prompt — e.g. a programming topic routes to an "educational" script prompt, a surfing topic routes to an "entertainment" one. →
  • This single routing decision determines the entire downstream processing path, ensuring the output style matches the nature of the input rather than one generic prompt trying to serve every case. →

Agents and Tools

  • Agents dynamically combine tools to solve tasks whose steps aren't known in advance, unlike workflows, which need the steps predetermined — the same small toolset (get_current_datetime, add_duration, set_reminder) can serve both a simple and a compound request. →
  • The best agent tools are abstract and general (bash, web_fetch, file_write) rather than hyper-specialized (a dedicated "refactor" tool) — abstraction is what lets Claude recombine tools creatively for cases you didn't anticipate. →

Environment Inspection

  • Agents need feedback beyond a tool's raw return value to understand what actually happened — Claude takes a screenshot after every computer-use action because it can't predict how a click changed the screen. →
  • The same principle applies to code editing (read a file before modifying it) and to a video-generation agent (extract frames with FFmpeg, generate captions with Whisper to verify placement) — inspection is what lets an agent detect errors and adapt instead of operating blind. →

Workflows vs Agents

  • Workflows break a big task into small, specific, predetermined subtasks and are easier to test and more reliable; agents adapt to varied inputs and can request more information, but have lower success rates because their execution path is unpredictable. →
  • The exam-relevant takeaway: prioritize workflows whenever the steps are knowable, and reach for agents only when real flexibility is required — reliability beats a flashier but less dependable approach. →

Claude API on Bedrock Basics

Accessing the API

  • Bedrock is accessed through a distinct SDK and documentation from the direct Anthropic API — same Claude models (Sonnet, Haiku), but a genuinely different service with its own client and request shape. →
  • The flow is: user text → your server → the Bedrock runtime client → a request carrying the user message + a model ID → Bedrock returns the assistant message → your server relays it to the client. →

Making a Request

  • A Bedrock request needs a boto3 client scoped to a region, a model ID, and a message object shaped {"role": "user", "content": [{"text": "..."}]} — content is a list because a message can carry multiple parts (text + images). →
  • Not every model is hosted in every region, and using the wrong one produces cryptic errors — inference profiles (found under "cross region inference," not "model catalog") route the request to wherever the model actually lives, so use the inference profile ID rather than a bare model ID for guaranteed routing. →
  • The call is client.converse(modelId=profile_id, messages=[...]), and the generated text comes back at response["output"]["message"]["content"][0]["text"]. →

Multi-Turn Conversations

  • Bedrock is stateless — it stores no messages, so every follow-up call must resend the entire conversation history yourself, strictly alternating user → assistant → user with no two consecutive turns from the same role. →
  • Without resending history, a follow-up like "and three more" gets no context and produces a nonsensical answer — helper functions that append to a running messages list are the standard fix. →

System Prompts

  • A system prompt (passed via the converse function's system keyword) assigns Claude a role so it "pretends" to have a job, rather than you spelling out every do/don't rule — e.g. "You are an AWS cloud support specialist" naturally makes it refuse off-topic questions. →
  • The system prompt must be at least 1 character and is passed as a list containing a dict with a text field; make it an optional function parameter defaulting to none so you don't hit empty-string errors when it's unused. →

Temperature

  • Temperature (0-1) controls randomness in token selection after tokenization and probability assignment — 0 is deterministic (always the highest-probability token), and the default is 1.0 for maximum creativity. →
  • Use low temperature near 0 for data extraction and factual, consistent tasks, and high temperature near 1 for creative writing, brainstorming, or marketing copy — it's passed via inference_config on the converse call. →

Streaming

  • Converse Stream exists because users expect immediate feedback but full generation can take 3-30 seconds — the response carries a "stream" key you iterate over, and only content_block_delta events carry actual text chunks. →
  • The text is at event['content_block_delta']['delta']['text']; collect the chunks as they arrive to reconstruct the full message if you need to store it. →

Controlling Model Output

  • Pre-filling the assistant message steers the response by making Claude continue from wherever the pre-filled text ends (not restart) — you must concatenate the pre-fill with what Claude returns to get the complete output. →
  • Stop sequences (passed via inference_config) force generation to halt the instant a matching string appears, and the stopping string itself is excluded from the final response — both techniques control output beyond what prompt wording alone can do. →

Structured Data

  • Combining a pre-filled opening delimiter (e.g. "```json") with a stop sequence on the closing delimiter ("```") makes Claude emit only the raw structured content, since it assumes the delimiter was already written and stops right before the matching close. →
  • This same pre-fill + stop-sequence pattern works for any structured format, not just JSON — it's the standard way to get clean, parseable output without manual text extraction from Claude's natural commentary. →

Prompt Evaluation

Prompt Evaluation

  • Prompt evaluation is automated, objective testing of a prompt — distinct from prompt engineering, which is the craft of writing the prompt itself; evaluation comes first to establish a measurement baseline before optimizing. →
  • The two traps are testing once or twice and shipping (no real signal) or tweaking against a handful of custom inputs — the recommended path runs the prompt through a real evaluation pipeline and iterates on the resulting score. →

A Typical Eval Workflow

  • The loop is: draft a prompt, build an eval dataset (hand-crafted or AI-generated, tens to thousands of records), run every dataset item through the prompt, grade each response (commonly 1-10), then average the scores into one comparable number. →
  • There's no standard methodology or required tooling — a lightweight custom implementation is enough to start; the point is running multiple prompt versions through the identical pipeline so their average scores are directly comparable. →

Generating Test Datasets

  • For an AWS code-generation prompt (output only Python, JSON, or regex, no explanation), the eval dataset is generated by asking a cheaper/faster model like Haiku to produce realistic task descriptions — dataset generation doesn't need top-tier reasoning. →
  • The generation call itself uses the pre-fill + stop-sequence JSON-extraction trick (assistant message opens with "```json", stop sequence "```") so the dataset comes back as clean, parseable JSON ready to save to a file. →

Running the Eval

  • The eval pipeline is just three small functions: run_prompt merges a test case into the prompt template and calls Claude, run_test_case calls run_prompt and (once real grading exists) scores the result, and run_eval loops run_test_case over the whole dataset. →
  • At this stage scoring is a hardcoded placeholder (always 10) and the prompt has no output-formatting instructions, so responses come back verbose — the next step is wiring in a real grader. →

Model Based Grading

  • There are three grader types: code graders run programmatic checks (length, syntax, keywords), model graders make an extra API call to judge quality/instruction-following, and human graders are the most flexible but slowest. →
  • A model-grader prompt should explicitly request reasoning and strengths/weaknesses alongside the score — asking for a bare number tends to produce default middling scores, whereas requiring justification surfaces real signal. →

Code Based Grading

  • Code graders validate by attempting to parse: validate_json() via json.loads(), validate_python() via the ast module, and validate_regex() via pattern compilation — each returns 10 on success and 0 on any parse error. →
  • The dataset needs a "format" field so grade_syntax() can route to the right validator, and the final score is the average of the model score and the syntax score: (model_score + syntax_score) / 2. →

Prompt Engineering

Prompt Engineering

  • The improvement loop is: set a goal, write a deliberately weak first draft, evaluate it, apply one prompt-engineering technique, re-evaluate, repeat — the meal-plan example starts from a poor baseline score and climbs with each technique. →
  • The eval setup supports concurrency (tunable against your rate limits) and an extra_criteria field for validation requirements beyond the base grading rubric, producing an output.html report for inspecting each test case. →

Being Clear and Direct

  • The first line of a prompt matters most — lead with an action verb (write, generate, identify, analyze) plus a precise task description rather than a vague opening. →
  • In the worked example, switching to a direct action-verb opening alone raised the eval score from 2.32 to 3.92 — clarity in the first line has an outsized, measurable effect. →

Being Specific

  • Type A guidelines list desired output attributes (length, structure, format) and are almost always worth adding; Type B guidelines give the model an explicit step-by-step process, reserved for complex problems needing broader consideration. →
  • Adding Type A guidelines to the meal-plan prompt lifted the score from 3.92 to 7.86 — a bigger jump than clarity alone, showing how much specificity narrows the model's output space. →

Structure with XML Tags

  • Wrapping distinct content blocks in descriptive XML tags (, , ) tells the model exactly where one kind of content ends and another begins, which matters most once a prompt interpolates multiple large blocks. →
  • Tag names should be specific rather than generic — "sales_records" communicates more than "data" — and even short content benefits from tags that mark it explicitly as external input. →

Providing Examples

  • One-shot means a single example, multi-shot means several; wrapping each in XML with sample input and ideal output is the standard structure, and examples are especially effective for corner cases (like sarcasm) and complex output formats (like JSON). →
  • A strong source of examples is your own eval results — pull the highest-scoring outputs and reuse them as examples, optionally with a short explanation of why the output is ideal to reinforce the desired behavior. →

Tool Use

Introducing Tool Use

  • Tool use exists because Claude only knows what was in its training data — the loop is: Claude requests external data it needs, your server fetches it (e.g. a weather API call), and Claude uses that data to compose the final response. →
  • The code you write runs in the opposite order from the logical flow (function → schema → result handling → included in the request), which is why it helps to keep the flow diagram in view while implementing. →

Tool Functions

  • Tool functions are plain Python functions Claude calls automatically when it needs something it can't know or do itself — descriptive argument names and input validation matter because Claude reads them to decide how to call the function. →
  • Raise an error rather than silently failing on bad input — Claude can read the error message and retry with corrected arguments, so a clear message ("date format cannot be empty") is itself part of the interface. →

JSON Schema for Tools

  • A tool schema has two parts: a name/description at the top and an input_schema (plain JSON Schema, not an LLM-specific format) describing the function's arguments. →
  • A fast way to build one: hand Claude your function's code and ask it to write the schema — the overall tool description should run 3-4 sentences on what it does, when to use it, and what it returns, with a description on every individual property too. →

Handling Tool Use Responses

  • A response with stop_reason "tool_use" means Claude wants to call a tool — its content list mixes a text part (for the user) with a tool_use part carrying a tool_use_id, a name, and an input dict of arguments. →
  • The full assistant message (every part, not just the text) must be preserved in the conversation history, and tool_choice can be set to "auto" (Claude decides), "any" (force some tool), or a specific {tool: {name: ...}} (force one tool, handy for testing). →

Running Tool Functions

  • Extracting tool_use parts means filtering the message content for entries with a "tool_use" key — Claude can send several in parallel, each needing its own matched result keyed by tool_use_id. →
  • Wrap execution in try/except and return an error status (is_error: true) with the error message as content rather than letting the call fail outright — Claude can read that and retry with corrected arguments. →

Sending Tool Results

  • Tool results go back to Claude as a user message (not assistant), and the original tool schemas must be included again in that follow-up call or Claude loses track of what the tools even are. →
  • The full conversation shape is: user message → assistant message (tool_use) → user message (tool_result) → assistant's final response — proof it worked is Claude answering with data it couldn't otherwise have (like the actual current time). →

Multi-Turn Conversations with Tools

  • The controlling logic is a while loop: keep calling Claude and processing tool requests as long as stop_reason == "tool_use"; once it's anything else, the conversation is complete for this turn. →
  • This same loop handles both tool-requiring and plain conversations automatically — it only builds a tool-result message when stop_reason actually indicates a tool was requested, avoiding empty result messages otherwise. →

Adding Multiple Tools

  • Once the first tool is wired up, adding another is just two steps: add its JSON schema to the request and add a matching case to the tool-dispatch function — no architectural change needed. →
  • Claude can plan and chain several tools on its own for a compound request (e.g. get the current date, then add a duration, then set a reminder) once all three are registered. →

Batch Tool Use

  • Claude can technically emit several tool_use blocks in one message but rarely does in practice, so a "batch_tool" schema is introduced whose input is a list of invocations (tool name + arguments) that Claude calls as one unit instead of going sequential. →
  • The batch handler parses each invocation's JSON arguments, dispatches each to the normal run_tool function, and returns all results together as a single tool response — cutting a chain of round trips down to one. →

Structured Data with Tools

  • Instead of pre-fill + stop sequence, you define a "fake" tool whose input schema matches your desired JSON shape and force Claude to call it via tool_choice — Claude then returns the extracted data as the tool's arguments, no execution needed. →
  • This is more reliable than the prompt-based method but costs more setup (a schema definition) — end the conversation as soon as the data is extracted rather than continuing the loop. →

Flexible Tool Extraction

  • A single flexible "toJSON" tool with an open-ended object parameter avoids writing a rigid schema per extraction task — the desired properties and types are specified in the prompt text instead of the schema. →
  • The trade-off is slightly lower reliability than a dedicated schema, so reserve the flexible approach for general extraction and keep dedicated schemas for tasks where accuracy is critical. →

The Text Editor Tool

  • Claude ships the JSON schema for the text editor tool but not the implementation — you must write the handler for all five commands: view, str_replace, create, insert, and undo_edit. →
  • The exact tool name is version-specific on Bedrock (str_replace_editor for Claude 3-7, str_replace_based_edit_tool for Claude 3-5) — using the wrong string ID breaks the integration. →

Retrieval-Augmented Generation

Introducing Retrieval Augmented Generation

  • Feeding an entire large document (100-1000 pages) directly into the prompt hits token limits, gets slower and more expensive, and degrades quality — RAG instead chunks the document and injects only the chunks relevant to the current question. →
  • RAG scales to large or multiple documents at lower cost, but adds real complexity: you need a chunking strategy, a relevance-search mechanism, and no guarantee that the retrieved chunks contain the complete context. →

Text Chunking Strategies

  • Poor chunking causes wrong-context retrieval (e.g. a medical "bug" chunk surfacing for a software engineering question just from word overlap) — size-based chunking is easiest to implement and most common in production, but cuts words mid-sentence unless you add character overlap between neighboring chunks. →
  • Structure-based chunking (splitting on headers/sections) produces cleaner, contextual chunks but only works on documents with guaranteed formatting; character-based chunking is the most reliable fallback across arbitrary document types despite being the least elegant. →

Text Embeddings

  • An embedding model turns text into a long list of numbers (commonly ~1024 values between -1 and +1); the individual numbers are opaque, but it helps to imagine each as a score for some semantic quality. →
  • Embeddings enable semantic search — comparing numerical representations to find related chunks — rather than relying on exact keyword matches. →

The Full RAG Flow

  • The full pipeline is: chunk the document, embed each chunk, normalize the vectors, store them in a vector database, embed the incoming user query the same way, then run a similarity search against the stored vectors. →
  • Cosine similarity ranges -1 to 1 (closer to 1 = more similar); cosine distance is 1 minus that, so values near 0 mean high similarity — the retrieved chunks get combined with the user's question into the final prompt sent to the LLM. →

Implementing the Rag Flow

  • A minimal implementation: chunk a document by section, embed each chunk, store embedding+text pairs in a vector index via zip(), embed the incoming query, then call store.search(query_embedding, k) to get the top-k chunks by cosine distance. →
  • Storing the original text alongside each embedding is a deliberate design choice — raw embedding vectors alone are meaningless to a developer, so metadata (the chunk's text) is what makes retrieved results actually usable. →

BM25 Lexical Search

  • BM25 is a keyword-based (lexical) search algorithm that catches exact-term matches pure semantic search can miss — it tokenizes the query, counts term frequency across chunks, and weights rare terms (like "incident 2023") higher than common ones ("the", "a"). →
  • The fix for semantic search's blind spot is hybrid search: run BM25 and vector search in parallel and merge their results, since each catches cases the other one misses. →

A Multi-Search RAG Pipeline

  • A retriever class wraps a vector index and a BM25 index behind one add_document/search API, then merges their rankings with Reciprocal Rank Fusion: score = sum of 1/(1+rank) across the methods that returned each document. →
  • A document ranked 1st in vector search and 2nd in BM25 gets RRF score 1/(1+1) + 1/(1+2) = 0.83 — documents that rank well across multiple methods bubble to the top of the merged list. →

Reranking Results

  • After hybrid retrieval, an LLM call reorders the merged results by relevance — documents are given temporary IDs (so Claude returns compact ordered IDs, not full text) and the prompt uses XML formatting plus pre-fill/stop-sequence for structured JSON output. →
  • This adds latency but improves quality: in the worked example, hybrid retrieval alone ranked the correct "software engineering + incident 2023" section second, and reranking correctly moved it to first. →

Contextual Retrieval

  • Because chunking strips a chunk of its surrounding context, an LLM is used as a pre-processing step to generate a short description of how each chunk fits into the larger document, and that description is prepended before the chunk is indexed. →
  • For documents too large to fit in one prompt, only a subset is used for context generation — the opening chunks (for a summary/abstract) plus the chunks immediately preceding the target, skipping less-relevant middle sections. →

Claude Features

Extended Thinking

  • Extended thinking lets Claude reason before answering, shown as a separate thinking block with a cryptographic signature (to prevent tampering) — it costs more (thinking tokens are billed) and adds latency, with a minimum thinking_budget of 1024 tokens. →
  • The decision to enable it must be eval-driven: run prompt evals first, and only turn on extended thinking if accuracy is still insufficient after prompt optimization — there's no rule-of-thumb budget, only what the evals show. →

Image Support

  • A request can carry up to 20 images, each consuming tokens based on its pixel dimensions; simple prompts against images tend to produce weak results (a naive "how many marbles?" undercounted 13 as 12). →
  • Accuracy comes from prompting technique, not image quality — step-by-step analysis instructions with a verification/recount step, or one-shot/multi-shot examples alternating image and text parts, meaningfully improve results. →

Prompt Caching

  • Normally Claude discards all the internal computation it did on a request's input the moment it responds — prompt caching instead stores that work temporarily so an identical follow-up request can reuse it instead of recomputing from scratch. →
  • The benefit is speed and cost: reusing cached computation avoids redundant processing whenever the same input text reappears in a later request. →

Rules of Prompt Caching

  • A cache point is a special marker in a message part — everything before it is eligible for caching, everything after it never is, and the content before the cache point must be byte-for-byte identical across requests or the cache is invalidated. →
  • Caching requires a minimum of 1024 tokens before the cache point and expires after 5 minutes of inactivity; the best candidates are things that rarely change between requests — system prompts and tool-definition schemas. →

Prompt Caching in Action

  • Implementation adds a cache_point with type "default" to the system prompt and to the tools list; the response's usage field then reports cache_write_input_tokens (first request) or cache_read_input_tokens (subsequent identical ones). →
  • Any change to the cached content — a different system prompt or tool schema — triggers a fresh cache_write instead of a cache_read, so caching only pays off when that content is genuinely stable across calls. →

Model Context Protocol

Introducing MCP

  • MCP shifts tool definition and execution to a dedicated MCP server rather than requiring your own server to author and maintain tool schemas — the MCP server is the interface to the outside service (e.g. GitHub, AWS). →
  • MCP and tool use are complementary, not the same thing: MCP is about who builds and runs the tool (a specialized server rather than you), while tool use is the underlying mechanism either way. →

MCP Clients

  • The MCP client sits between your server and the MCP server, most commonly communicating over stdio on the same machine — it relays list-tools and call-tool requests and results, without executing anything itself. →
  • A full round trip runs: your server → client → MCP server (list tools) → tools handed to Claude → Claude requests execution → client → MCP server (call tool) → result flows back up the chain to Claude. →

Project Setup

  • The Bedrock course project builds a CLI chatbot with both an MCP client and server side by side (real-world projects normally build only one) working against fake in-memory documents. →
  • Setup mirrors the Anthropic-API version: download the starter zip, configure the Bedrock region and model ID as environment variables, install dependencies, then run with uv or python. →

Defining Tools with MCP

  • The MCP Python SDK auto-generates JSON schemas from a decorated function (@mcp.tool + typed parameters with pydantic Field) — no manual schema writing. →
  • The example tools are read_doc_contents (returns content by doc_id, raising ValueError if missing) and edit_document (doc_id, old_string, new_string performing a find/replace) — both validate the doc_id exists before acting. →

The Server Inspector

  • The MCP Inspector is an in-browser debugger launched with "mcp dev [server-filename.py]" — Connect starts the server, then Tools → List Tools lets you pick a tool, fill parameters, and click Run Tool to see the result. →
  • It's meant for live development testing before wiring the server into a real application, and its UI is expected to keep changing even though the core workflow stays the same. →

Implementing a Client

  • A wrapper class around ClientSession exposes list_tools() (await self.session.list_tools(), return result.tools) and call_tool() (await self.session.call_tool(name, input)) to the rest of the codebase. →
  • On Bedrock specifically, MCP tool definitions differ from what the Bedrock API expects, so a to_bedrock_tools() conversion step is needed before the tool list reaches Claude. →

Defining Resources

  • Resources expose data for reads rather than actions — a direct/static resource has a fixed URI (docs://documents), a templated one has wildcard parameters (docs://documents/{doc_id}) that become function keyword arguments. →
  • Defined with @mcp.resource and a MIME type; a common pattern is a "list documents" resource for autocomplete plus a "fetch one document" resource, enabling @ mentions in chat without a tool call. →

Accessing Resources

  • The client reads a resource with session.read_resource(AnyURL(uri)), takes result.contents[0], and branches on mime_type — application/json parses with json.loads(), otherwise it's returned as plain text. →
  • Because the resource content is already fetched and inserted into the prompt directly, no separate tool call is needed just to read that data. →

Defining Prompts

  • MCP prompts are pre-built, tested instructions the server exposes for its domain (e.g. document formatting) so clients and users don't have to write their own prompts from scratch. →
  • Defined with @prompt(name, description); the function takes parameters like a document ID and returns base.UserMessage objects with the prompt text already interpolated. →

Prompts in the Client

  • The client calls list_prompts() (await self.session.list_prompts(), returning result.props) and get_prompt(name, arguments) (returning result.messages) to retrieve a server-defined prompt with runtime values filled in. →
  • A concrete example: a format_document prompt expects a document_id argument, and the client supplies it, letting the server return a fully formatted prompt ready for the LLM. →

MCP Review

  • The three server primitives map to three different controllers: tools are model-controlled (Claude decides, e.g. running JavaScript for a calculation), resources are app-controlled (the application decides, e.g. auto-complete or document injection), and prompts are user-controlled (triggered via UI, e.g. chat starter buttons). →
  • The shorthand: tools serve the model, resources serve the app, prompts serve the user — that's the deciding question when picking which primitive a new capability should be. →

Claude Code in Action

  • Running the init command has Claude scan the codebase and produce a claude.md capturing architecture and coding-style notes, which then loads automatically as context on every future request. →
  • Two effective workflows for a complex feature: (1) read relevant files → plan without writing code → implement the plan, or (2) read context → suggest tests (no implementation) → implement the chosen tests → write code until they pass. →

  • Claude Code has an embedded MCP client, so "claude mcp add [server-name] [startup-command]" connects an external MCP server (e.g. a documents server, Sentry, Jira, Slack) and a restart picks up its tools. →
  • This lets Claude Code gain capabilities dynamically (e.g. converting PDFs/Word docs to Markdown) without any change to Claude Code's own core. →

  • Git worktrees solve the file-conflict problem of running multiple Claude instances at once — each worktree is a complete, isolated project copy tied to its own branch. →
  • The workflow (create worktree → assign a task → work in isolation → commit → merge back → clean up) can itself be delegated to Claude, including conflict resolution during the merge and removing finished worktrees. →

Automated Debugging

  • A daily GitHub Action pulls CloudWatch logs, Claude analyzes and deduplicates the errors, generates fixes, and opens a PR — a real example caught an "invalid model identifier" typo that only broke in production, not locally. →
  • Human review of the proposed fix before merge is still required — this automates detection and diagnosis, not unattended deployment. →

  • Computer use lets Claude take screenshots and perform clicks/typing/scrolling to drive an actual interface, running inside an isolated Docker container for safety. →
  • The primary use cases are QA and web-application testing — Claude navigates, fills forms, and reports pass/fail results the way a human tester would. →

How Computer Use Works

  • Computer use is a special case of the ordinary tool-use loop: a minimal schema expands into a large action-function structure (mouse move, left click, screenshot, etc.), and Claude sends tool_use requests exactly as it would for any tool. →
  • Claude never touches the machine directly — a developer-provided execution environment (Anthropic's reference implementation runs it in Docker) performs the actual key presses and mouse movements and returns the result. →

Agents

Qualities of Agents

  • An agent is a language model with tool access run repeatedly in a loop until the goal is achieved or it errors out — most of its tool calls gather information about the environment rather than change it, since the model has no inherent world knowledge of its own. →
  • Agents suit high-value, low-risk tasks where mistakes are recoverable, work best with a small focused toolset, and depend entirely on evals to confirm they're actually effective rather than just plausible-looking. →

Overview of Claude Models

  • Generation runs through four stages: tokenization (text → tokens), embedding (tokens → numeric meaning vectors), contextualization (embeddings adjusted by neighboring tokens), and generation (repeatedly picking the next token by probability + randomness until max_tokens or an end-of-sequence token). →

Making a Request

  • Setup is: pip install "anthropic[vertex]", then instantiate the vertex client with region="global" and a project_id from the Google Cloud console. →

  • A system prompt controls how Claude responds, not just what — e.g. a "patient math tutor" role produces guiding hints instead of direct answers to the same question. →
  • The system parameter can't be None, so make it an optional function argument and only include it in the API call when a prompt is actually supplied. →

  • Temperature (0-1, default 1.0) controls how much lower-probability tokens get a chance during sampling — 0 is fully deterministic, picking the top-probability token every time. →
  • Use temperature near 0 for factual/extraction tasks and near 1 for creative work; a higher value only increases the *chance* of variation, so multiple attempts may be needed to actually see different output. →

  • Streaming exists to avoid a 10-30 second blank wait — Claude sends an initial acknowledgment immediately, then a sequence of events; only content_block_delta carries the actual text. →
  • client.messages.stream() with stream.text_stream gives clean incremental text, and stream.get_final_message() assembles the complete message afterward (e.g. for saving to a database). →

Prompt Evaluation

Prompt Evaluation

  • Prompt evaluation is objective, automated testing of a prompt — distinct from prompt engineering (the craft of writing it) — and comes first in the learning sequence to establish a measurable baseline. →
  • Shipping after one or two manual checks, or only tweaking against a few custom inputs, are both traps; a real evaluation pipeline with objective scoring is the recommended path before deployment. →

A Typical Eval Workflow

  • The five-step loop: draft a prompt, build an eval dataset (3 examples to start, hundreds/thousands in production, hand-crafted or AI-generated), run each input through the prompt, grade each response (typically 1-10), then average and iterate. →
  • There is no industry-standard methodology — a simple custom implementation in a notebook is a legitimate starting point, with the win being an objective, comparable score across prompt versions. →

Generating Test Datasets

  • For an AWS code-generation prompt (Python, JSON config, or regex, nothing else), the dataset is an array of {task: "..."} objects generated by asking Claude (often the faster Haiku model) to produce realistic test cases. →
  • The generation call uses the pre-fill ("```json") + stop-sequence ("```") pattern to force clean JSON, which is then parsed and saved to a file for reuse across eval runs. →

Running the Eval

  • run_prompt merges a test case into the prompt and calls Claude; run_test_case wraps that and (for now) returns a hardcoded score of 10; run_eval loops the dataset through run_test_case and collects everything. →
  • At this stage the prompt has no formatting instructions (so output is verbose) and there's no real grading — the next step is replacing the hardcoded score with a genuine grader. →

Model Based Grading

  • The three grader types are code graders (programmatic checks like length/syntax/word presence), model graders (an extra API call judging quality/instruction-following/completeness), and human graders (most flexible, most time-consuming). →
  • A model-grading prompt should require reasoning alongside the score — without that requirement, models default to middling scores around 6, so asking for strengths/weaknesses forces a more discriminating result. →

Code Based Grading

  • validate_json(), validate_python() (via AST), and validate_regex() (via compilation) each try to parse the output and return 10 on success, 0 on failure — grade_syntax() dispatches to the right one using a "format" field on the test case. →
  • The prompt template is updated to explicitly request only code (no commentary), pre-filled with "```code" since the exact format isn't known ahead of time, and the final score averages the model score with the syntax score. →

Prompt Engineering

Prompt Engineering

  • The improvement loop is: write a deliberately weak first prompt, evaluate it, apply one technique, re-evaluate, repeat — for the meal-plan example, scores start poor and climb systematically as techniques are layered in. →
  • The eval setup allows tunable concurrency (start around 3, drop to 1 if rate-limited) and extra_criteria for validation requirements beyond the base rubric, producing an HTML report of every test case and its reasoning. →

Being Clear and Direct

  • The first line carries the most weight — open with an action verb (write, generate, identify, analyze) plus a precise description of the task and expected output. →
  • In the worked example, switching to a direct, action-verb opening alone raised the eval score from 2.32 to 3.92. →

Being Specific

  • Type A guidelines list desired output attributes (length, structure, format) and are almost always worth including; Type B guidelines give the model an explicit process to follow, reserved for complex problems needing a broader perspective. →
  • Adding guidelines to the meal-plan prompt lifted its score from 3.92 to 7.86 — specificity had a larger effect than clarity alone. →

Structure with XML Tags

  • Wrapping distinct content blocks in descriptive tags (, , not generic ones like ) tells the model exactly where one kind of content ends and another begins. →
  • This matters most once a prompt interpolates multiple large blocks, but even short content benefits from a tag that marks it explicitly as external input. →

Providing Examples

  • One-shot is a single example, multi-shot is several; wrap each in XML with sample input and ideal output, and use them especially for corner cases (like sarcasm detection) and for demonstrating complex output formats. →
  • A strong source of examples is your own eval results — reuse the highest-scoring outputs, optionally with reasoning for why they're ideal, to reinforce the desired behavior. →

Tool Use

Introducing Tool Use

  • Tool use exists because Claude only knows its training data — the loop is: Claude requests external data it needs, your server fetches it (e.g. calling a weather API), and Claude composes the final answer using that data. →
  • Without tools, a question like "what's the weather in San Francisco right now" gets an honest "I don't have access to that" — tools close that gap. →

Project Overview

  • The course project teaches Claude to set time-based reminders, exposing three real gaps: it doesn't know the exact current time, sometimes miscalculates date math, and has no mechanism to actually create a reminder. →
  • Three tools close those gaps one at a time: get current datetime, add a duration to a datetime, and set the reminder — built individually before being combined. →

Tool Functions

  • Tool functions are plain Python functions Claude calls automatically when it needs information it can't produce itself — descriptive names and input validation matter because Claude reads them to decide how to invoke the function. →
  • Raising a clear error (e.g. "date format cannot be empty") rather than failing silently lets Claude read the message and retry with corrected arguments. →

Tool Schemas

  • A tool schema is a JSON Schema (a general-purpose, non-LLM-specific data-validation format) with a name, a 3-4 sentence description, and an input_schema describing each argument with its own description. →
  • A fast way to build one: hand Claude your function code plus Anthropic's tool-use documentation and ask it to write the schema; wrap the result in ToolParam (from anthropic.types) for type safety. →

Handling Message Blocks

  • Once tools are introduced, a request must include the tools parameter, and the response becomes multi-block: text (for the user) plus tool_use blocks (function name + input arguments). →
  • The entire content list (every block, not just the text) must be appended to the message history — helper functions that only handle single text blocks need to be updated to handle multiple. →

Sending Tool Results

  • After executing the requested function, extract its arguments from the tool_use block, call it with **kwargs, and send the result back as a tool_result block whose tool_use_id matches the original request. →
  • The tool schema must be included again in every follow-up call, even once you're just sending results — omitting it breaks Claude's understanding of what the tools are. →

Multi-Turn Conversations with Tools

  • A single user query can require multiple sequential tool calls — e.g. "what day is 103 days from today" needs get_current_datetime, then add_duration_to_datetime — handled by looping while stop_reason keeps coming back as tool_use. →
  • Helpers need updating to handle multi-block messages, and a text_from_message helper extracts just the text portion when a message mixes text and tool_use blocks. →

Implementing Multiple Turns

  • The run_conversation loop calls Claude, appends its response, checks stop_reason, and (if it's "tool_use") calls run_tools and feeds results back as a user message — repeating until stop_reason is anything else. →
  • run_tools filters content for tool_use blocks, dispatches each to the right function via run_tool, and returns tool_result blocks (type, tool_use_id, JSON-encoded content, is_error) — wrapped in try/except so failures come back as is_error: true with the error message rather than crashing the loop. →

Using Multiple Tools

  • Once the first tool exists, adding another is a fixed two-step pattern: add its schema to the tools list, then add a matching branch in the RunTool dispatcher. →
  • Claude can chain tools in sequence on its own (e.g. AddDurationToDateTime → SetReminder), each producing its own tool_use/tool_result pair in the growing conversation history. →

The Batch Tool

  • Claude rarely emits multiple tool_use blocks in one message even when it technically could, so a batch_tool schema (taking a list of "invocations," each a tool name + arguments) is introduced to make it prefer parallel execution. →
  • The handler parses each invocation and dispatches it through run_tool, returning all results together — cutting a chain of sequential round trips down to a single request-response cycle. →

Tools for Structured Data

  • Define a schema whose inputs match your desired output shape, then force Claude to call it via tool_choice = {"type": "tool", "name": "..."} — the structured data comes back directly as response.content[0].input, with no tool_result step needed. →
  • This is more reliable than the prompt pre-fill/stop-sequence method but requires more setup — pick whichever technique matches how much reliability the use case actually needs. →

The Text Edit Tool

  • Claude ships only the schema for the text editor tool (view, string_replace, create_file, etc.) — the actual file-system implementation is entirely your responsibility to write. →
  • The schema stub differs by model version (Claude 3.7 vs 3.5 use different date-stamped type strings), and once sent it auto-expands into the full schema behind the scenes. →

The Web Search Tool

  • Web search needs only a minimal schema (type "web_search_20250305", name "web_search", max_uses) — Claude runs the search itself, with no custom implementation required. →
  • allowed_domains restricts results to specific sources (e.g. NIH.gov for medical content) to improve quality, and the response mixes text, search-result blocks (title/URL), and citation blocks that should be surfaced separately in the UI for transparency. →

Retrieval-Augmented Generation

Introducing Retrieval Augmented Generation

  • Feeding a 100-1000 page document straight into the prompt hits token limits and gets slower/costlier — RAG instead chunks the document and injects only the chunks relevant to the current question. →
  • RAG trades added complexity (a chunking strategy, a relevance-search mechanism, no guarantee retrieved chunks hold the complete context) for the ability to scale to large or multiple documents cheaply. →

Text Chunking Strategies

  • Poor chunking causes wrong-context retrieval (a medical "bug" chunk surfacing for a software-engineering question via word overlap) — size-based chunking is the easiest and most common approach but cuts words mid-sentence unless overlap is added between neighboring chunks. →
  • Structure-based chunking (splitting on headers/sections) needs guaranteed document formatting; character-based chunking is the most reliable default across arbitrary document types, even though it's the least elegant. →

Text Embeddings

  • An embedding model outputs a long vector (-1 to +1 per value) representing text meaning; the individual numbers are opaque but useful to think of as scores on unnamed semantic qualities. →
  • Google's text-embedding-005 (via the Google GenAI SDK on Vertex) generates these vectors, enabling semantic search that compares meaning rather than exact keywords. →

The Full RAG Flow

  • The full pipeline: chunk the document, embed each chunk, normalize the vectors to unit length, store them in a vector database, embed the user's query the same way, then run similarity search — steps 1-4 happen ahead of time, only 5-7 run at query time. →
  • Cosine similarity ranges -1 to 1 (closer to 1 = more similar); cosine distance is 1 minus that, so values near 0 indicate high similarity between the query and a stored chunk. →

Implementing the Rag Flow

  • A minimal implementation: chunk by section, embed each chunk, store embedding + metadata (the original text) pairs in a vector index, embed the incoming query, then call store.search(query_embedding, k) for the top-k matches by cosine distance. →
  • Storing the original text with each embedding is deliberate — a bare embedding vector is meaningless to a developer, so metadata is what makes a retrieved result actually usable. →

BM25 Lexical Search

  • BM25 is a keyword-based algorithm that tokenizes the query, counts term frequency across chunks, and weights rare terms (like "incident 2023 Q4 011") higher than common ones — catching exact-match cases pure semantic search misses. →
  • The fix for semantic search alone returning irrelevant matches (e.g. an unrelated financial-analysis chunk) is hybrid search: run BM25 and vector search in parallel and merge the results. →

A Multi-Index Rag Pipeline

  • A retriever class wraps a vector index and a BM25 index behind an identical add_document/search API, then combines their rankings via Reciprocal Rank Fusion: score = sum of 1/(1+rank) across every method that returned the document. →
  • A document ranked well by both methods scores higher than one that ranks well in only one — the merged approach outperforms either method alone, especially for queries needing both concept matching and exact terms. →

Reranking Results

  • After hybrid retrieval, an LLM call re-orders the merged candidates by relevance — documents get short random IDs (so Claude returns compact ordered IDs, not full text), with pre-fill/stop-sequence used for clean JSON output. →
  • This adds latency but catches cases hybrid retrieval alone gets wrong, e.g. correctly prioritizing a "software engineering" section over an unrelated "cybersecurity" section for an ambiguous "engineering team" query. →

Contextual Retrieval

  • Because chunking strips a chunk of its surrounding context, an LLM pre-processing step generates a short "situating" description of each chunk's place in the larger document, which gets prepended before the chunk is indexed. →
  • For documents too large for one prompt, only the opening chunks (for a summary) plus the chunks immediately preceding the target are used for context generation, skipping less-relevant middle sections. →

Claude Features

Extended Thinking

  • Extended thinking lets Claude reason before answering, returned as a thinking block (with a cryptographic signature Claude checks before reusing it in later turns) plus the final text block — thinking tokens are billed and add latency. →
  • A minimum thinking_budget of 1024 tokens applies, and max_tokens must comfortably exceed it; enable extended thinking only after prompt-optimization evals show accuracy is still insufficient, never as a default. →

Image Support

  • A request can carry up to 100 images, each priced by pixel dimensions; naive prompts against images ("how many marbles?") tend to produce inaccurate results. →
  • Accuracy depends on prompting technique, not image quality — step-by-step analysis with a verification/recount pass, or one-shot/multi-shot examples alternating image and text, substantially improve results (demonstrated in a wildfire-risk satellite-imagery example). →

PDF Support

  • PDF handling reuses almost identical code to image support — swap type "document" for "image", media_type "application/pdf" for the image mime type, and rename the variable to file_bytes. →
  • Claude can extract text, images, charts, and tables from a PDF in one pass, making it a single tool for comprehensive document analysis. →

Citations

  • Enabling citations ({"enabled": true} plus a source document) makes Claude reference exactly where in the source a given statement came from — citation_page_location for PDFs (document index/title/start-end pages) and citation_char_location for plain text. →
  • The response becomes a list of text blocks, some carrying a citations array, which a UI can use to build hover popups showing users the exact supporting source text. →

Prompt Caching

  • Normally Claude discards all the internal computation on a request's input as soon as it responds — prompt caching stores that work instead so an identical follow-up request can reuse it rather than recomputing from scratch. →
  • The requirement is exact identity: input text must match previously cached content exactly, or the cache doesn't apply and normal (slower, costlier) processing happens instead. →

Rules of Prompt Caching

  • A manual cache breakpoint must be added to a message block using the longhand text-block format ({"type": "text", "text": ..., "cache_control": {...}}) — the shorthand plain-string content form can't carry a cache_control. →
  • Everything before the breakpoint is cached (nothing after), the cache lasts 5 minutes, requires a minimum 1024 tokens, allows up to 4 breakpoints per request, and can sit on text, image, tool-use, tool-result, tool-schema, or system-prompt content. →

Prompt Caching in Action

  • Implementation adds a cache_control field with type "ephemeral" to the last tool schema and wraps the system prompt as a text block with the same cache_control — processing order is tools → system prompt → messages. →
  • usage.cache_creation_input_tokens shows tokens newly written to cache; usage.cache_read_input_tokens shows tokens reused from it — any change to the cached tools or system prompt invalidates the cache and forces a fresh cache_creation. →

Model Context Protocol

Introducing MCP

  • MCP shifts tool definition and execution to a dedicated MCP server rather than requiring your own server to author and maintain schemas and functions — the MCP server wraps an outside service (like GitHub or AWS) into ready-made tools. →
  • MCP and tool use are complementary, not identical: MCP addresses who builds and runs the tool (a specialized server instead of you), while tool use is the mechanism through which Claude calls it either way. →

MCP Clients

  • The MCP client sits between your server and the MCP server, relaying list-tools and call-tool requests/results over a transport-agnostic connection (stdin/stdout, HTTP, WebSockets) — it never executes a tool itself. →
  • A full round trip: your server → client (list tools) → MCP server → tools handed to Claude → Claude requests execution → client (call tool) → MCP server executes → result flows back through the same chain. →

Project Setup

  • The course project builds a CLI chatbot implementing both an MCP client and server side by side purely for learning — a real project would normally build only one side. →
  • Setup is standard: download the starter zip, add the API key to .env, install dependencies, and run with "uv run main.py" or "python main.py". →

Defining Tools with MCP

  • The MCP Python SDK auto-generates a tool's JSON schema from a decorated function (@mcp.tool + typed parameters using pydantic Field) — no manual schema authoring. →
  • The example tools are read_doc_contents (returns content by doc_id, raising ValueError if missing) and edit_document (doc_id, old_string, new_string, performing a find/replace), both validating existence before acting. →

The Server Inspector

  • The MCP Inspector is an in-browser debugger launched with "mcp dev [server-file.py]" — Connect starts the server, then Tools → List Tools lets you select a tool, fill parameters, and Run Tool to verify the result. →
  • It's meant for live testing during development, e.g. verifying edit_document's changes by re-running read_doc_contents afterward — and its UI is expected to keep evolving. →

Implementing a Client

  • A wrapper class around ClientSession exposes list_tools() (await self.session.list_tools()) and call_tool() (await self.session.call_tool(name, input)), handling connection lifecycle via async context managers. →
  • The usage flow is: the application calls client.list_tools() to hand tools to Claude, then client.call_tool() whenever Claude requests execution. →

Defining Resources

  • Resources expose data for reads, not actions — a direct/static resource has a fixed URI (docs://documents), a templated one has wildcard parameters (documents/{doc_id}) that become function keyword arguments. →
  • A common pattern pairs a "list documents" resource (for autocomplete) with a "fetch one document" resource, enabling @ mention functionality that inserts content directly into a prompt without a tool call. →

Accessing Resources

  • The client reads a resource via session.read_resource(AnyURL(uri)), takes result.contents[0], and branches on mime_type — application/json parses with json.loads(), otherwise it returns plain resource.text. →
  • This lets a CLI show a resource list the user selects with arrow keys/space, with the content going straight into the prompt rather than requiring a tool call to fetch it. →

Defining Prompts

  • MCP prompts are pre-defined, tested instructions a server exposes for its domain (e.g. document formatting) so users or clients don't need to write ad-hoc prompts themselves. →
  • Defined with @prompt(name, description) and imported via BaseMessage from mcp.server.fastmcp.prompts; the function takes parameters (like a document ID) and returns a list of messages ready for the LLM. →

Prompts in the Client

  • The client calls list_prompts() (returning result.props) and get_prompt(name, arguments) (returning result.messages) to retrieve a server-defined template with runtime values already interpolated. →
  • A concrete flow: a /format command selects a document, the client passes its ID as an argument, and the server returns a ready-to-send prompt that Claude uses with its tools to fetch and reformat the document. →

MCP Review

  • The three server primitives map to three different controllers: tools are model-controlled (Claude decides, e.g. running code for a calculation), resources are app-controlled (the application decides, e.g. autocomplete or Google Drive listings), and prompts are user-controlled (triggered by a button or slash command). →
  • The shorthand: tools serve the model, resources serve the app, prompts serve the user — that framing is the fastest way to pick the right primitive for a new capability. →

Agents and Workflows

Agents and Workflows

  • Use a workflow when the exact steps are known ahead of time; use an agent when the task details are uncertain and Claude needs to figure out the approach itself using its tools. →
  • The image-to-3D-model example follows an evaluator-optimizer pattern: Claude + CADQuery produces a model (the producer), Claude compares the rendering to the original image (the evaluator), and the loop repeats until the evaluator accepts the result — a workflow is a proven pattern, but you still write the actual implementation code. →

Parallelization Workflows

  • Instead of one large prompt juggling many criteria at once (e.g. "recommend the best material: metal, polymer, ceramic..."), split it into separate simultaneous requests, each judging one option, then have a final aggregator step combine the results. →
  • This buys focus (each request handles one concern), independent optimization (each sub-prompt can be tuned separately), and easy scalability (new sub-tasks don't disturb existing ones). →

Chaining Workflows

  • Rather than one prompt trying to satisfy many constraints at once, chaining splits a task into sequential steps where each step's output feeds the next (topic → trending search → topic selection → research → script → video → post). →
  • It's the fix specifically for a prompt that keeps violating some constraints despite being repeated in a single call — accept an imperfect first pass, then send a focused follow-up asking Claude to fix just the specific violations. →

Routing Workflows

  • A routing step first classifies user input into a predefined category, then forwards it to a category-specific pipeline with its own tailored prompt — e.g. a programming topic routes to an "educational" script prompt, a surfing topic routes to an "entertainment" one. →
  • This single routing decision determines the entire downstream processing path, ensuring the output style actually matches the nature of the input rather than using one generic prompt for everything. →

Agents and Tools

  • Agents dynamically combine tools to solve tasks whose steps aren't known in advance, unlike workflows, which need the steps predetermined — the same small toolset (get_current_datetime, add_duration, set_reminder) can serve both a simple and a compound request. →
  • The best agent tools are abstract and general (bash, web_fetch, file_write) rather than hyper-specialized (a dedicated "refactor" tool) — abstraction is what lets Claude recombine tools creatively for cases you didn't anticipate. →

Environment Inspection

  • Agents need feedback beyond a tool's raw return value to understand what actually happened — Claude takes a screenshot after every computer-use action because it can't predict how a click changed the screen. →
  • The same principle applies to code editing (read a file before modifying it) and to a video-generation agent (extract frames with FFmpeg, generate captions with Whisper to verify placement) — inspection is what lets an agent detect errors and adapt instead of operating blind. →

Workflows vs Agents

  • Workflows break a big task into small, specific, predetermined subtasks and are easier to test and more reliable; agents adapt to varied inputs and can request more information, but have lower success rates because their execution path is unpredictable. →
  • The exam-relevant takeaway: prioritize workflows whenever the steps are knowable, and reach for agents only when real flexibility is required — users want a 100%-working product over a flashy but unreliable one. →

Steering Long Sessions

A CLAUDE.md That Follows

  • CLAUDE.md is guidance Claude follows, not enforced configuration — every line competes for attention, so a longer file means less reliable adherence to any one rule. →
  • A hard rule like "never push to main" belongs in a PreToolUse hook (code that runs), not CLAUDE.md (instructions Claude reads) — hooks stop the action even if Claude tries it. →
  • Four memory locations load together every session: managed policy (org-wide), user (global), project (team-shared), and local (yours only, in this project). →
  • Imports let you split a large CLAUDE.md into smaller files, but they do NOT reduce context — every imported file still expands inline and loads up front. →
  • Phrasing that gets followed is specific and checkable ("put new API routes in src/api/handlers") and names the replacement ("use named exports, not default exports") rather than vague best-practice language. →
  • Emphasis (IMPORTANT, "you must") is a budget relative to the quieter rules around it — spend it on the 2-3 rules that actually hurt when broken, not everything. →

Verification Skills

  • A skill is a folder with a skill.md holding a name, a trigger description, and a procedure — only descriptions load into context until a skill is actually needed. →
  • The verification skill is the one to build first: it fires after Claude edits code, runs the test suite, checks no test was weakened just to pass, and reports pass/fail with evidence. →
  • skill.md should stay lean; put detailed material in a linked reference.md that Claude only reads when it needs the depth, and scripts in the folder are executed rather than loaded into context. →
  • The three instruction surfaces are distinct: CLAUDE.md for always-on conventions, skills for procedures tied to a specific kind of task, hooks for rules Claude must not be able to skip. →

Automation & Safety

Permission Modes

  • Shift-tab cycles the everyday permission modes; the six are Manual (reads only), Accept edits (reads + edits + safe bash), Plan (read-only research), Auto (classifier-reviewed), Don't ask (pre-approved tools only, else auto-denied), and Bypass permissions (no checks at all). →
  • Auto mode's classifier guards intent — it blocks moves that escalate beyond the request (production deploys, force pushes, piping downloaded code into a shell) but allows everyday work like local edits and installing from the lockfile. →
  • The classifier never judges correctness — broken code isn't "dangerous," so it waves it through; pair auto mode with a Stop hook that runs tests to catch that gap. →
  • Don't ask mode is right for CI and unattended pipelines because an unapproved action is auto-denied rather than hanging on a prompt no one will answer; Bypass permissions should only run inside an isolated container or VM. →

Hooks

  • A hook is deterministic code at a fixed point in the loop — it turns "Claude usually listens" into "Claude can't skip it," guaranteeing behavior even on unwatched runs. →
  • PreToolUse is the enforcement primitive (fires before a tool call); PostToolUse is where auto-format/lint go (fires after); Stop can refuse to end the turn if conditions aren't met. →
  • PreToolUse can return JSON with a permissionDecision of allow, deny, or ask (plus defer for non-interactive -p runs); updatedInput replaces the whole tool input object to rewrite a call (e.g. redact a secret) without blocking it. →
  • Exit code 2 is the blocking error that feeds stderr back to Claude as context almost everywhere; exit 1 is easy to mistake for blocking but is actually non-blocking — Claude runs the command anyway. →
  • To re-inject context after compaction, use a SessionStart hook with the compact matcher — not PostCompact, since PreCompact/PostCompact fire around the event but SessionStart(compact) is the pattern for restoring state. →

Routines and Headless

  • Routines are saved prompts + repos + connectors that run on Anthropic's managed infrastructure on a trigger (cron, HTTP POST, or a GitHub event) — no machine of yours stays on and there's no workflow file to maintain. →
  • Routines are a research preview limited to hourly-or-less recurring schedules, and each run starts from a fresh clone of the default branch and can only push to claude/-prefixed branches unless that's loosened per repo. →
  • Headless mode (-p / --print) runs Claude Code as a one-shot pipeable command with no TUI; --bare skips auto-discovery of hooks/skills/plugins/MCP/CLAUDE.md for a faster, deterministic run with only explicitly allowed tools. →
  • Pairing a JSON schema with --output-format json constrains headless output into a structured_output field you can pull with jq; capturing the session ID lets you resume later with full context. →
  • The Agent SDK (TypeScript and Python) embeds Claude Code in your own application via a query function with the same primitives as the CLI — use it when the work belongs inside your own product rather than as a managed routine. →

GitHub Actions and Code Review

  • Managed Code Review is an Anthropic-hosted service wired through the Claude GitHub app (nothing to build or host) — an org admin enables it, picks repos, and chooses when it runs (PR open, every push, or "@claude review" comments). →
  • Managed Code Review posts findings as inline comments tagged by severity and never approves or blocks the PR itself — judgment stays with a human, and there's no managed autofix; apply fixes locally with /code-review --fix. →
  • The Claude Code GitHub action (anthropics/claude-code-action@v1) is for more than review — implementing changes from a comment, scheduled reports — installed via /install-github-app, triggered by a phrase like @claude on PR/issue comments or by a cron schedule. →
  • Tune the action via claude_args: max turns caps the agent loop, permission mode "don't ask" suits unattended runs, and allowed tools should be scoped to the job (e.g. read-only for a report). →

Trust It: Verifying Unsupervised Runs

  • Verify in proportion to how unsupervised the run was — a watched session needs a glance, but an unattended or CI run needs a real check since nobody saw it happen. →
  • Keep unattended runs in auto mode, not bypass — the classifier still reviews each action for danger, but it never judges correctness, so the verification bar doesn't move. →
  • Start from the diff, not the summary — a tidy summary can read fine while the diff touched files you didn't expect, so read what actually changed, especially files that were in the plan first. →
  • Make tests the real gate by wiring a Stop hook that runs them and refuses to end the turn on failure — a hook exiting with code 2 feeds the failure back to Claude, which fixes it unprompted, on every run whether or not you remember to ask. →
  • A cold second opinion — a fresh session or subagent reviewing the changed code with no memory of how it was built — has no stake in the approach and catches what the original run talked itself past. →

Plugins

  • A plugin is one installable unit bundling skills, subagents, hooks, and MCP server configs (plus LSP servers, monitors, themes, and a slice of settings.json) — installed directly or through a team's private marketplace for centralized discovery and version tracking. →
  • A plugin runs code on your machine with your privileges — installing it for the skills also installs its PreToolUse and Stop hooks, whether you read them or not, and "reviewed" (automated marketplace review) is not the same as "trusted." →
  • A plugin's hooks stack alongside your own (neither replaces the other) and its skills/agents/commands are namespaced under the plugin name so they never clash; only the agent and subagent status line keys in its settings.json are honored. →
  • Packaging your own plugin reuses the same .claude shape you already use (skills folders, agents/ markdown, hooks/hooks.json, .mcp.json) with an optional plugin.json manifest — name is the only required field, and it namespaces skills as plugin-name:skill-name. →
