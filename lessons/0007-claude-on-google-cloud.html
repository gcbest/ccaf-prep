7:35 a.m. · The whiteboard

The five-step lifecycle—and the one line you never cross

Before anyone touches code, you draw the request lifecycle in the Vertex framing:

  1. Request to Server — the client sends the user’s text to your server.
  2. Request to Vertex — your server calls Vertex AI with an identifying credential, the model name, messages, and max_tokens.
  3. Model Processing — Vertex routes the request to the selected Claude model.
  4. Response to Server — the response comes back with content, usage, and a stop reason.
  5. Response to Client — your server forwards the result for display.

Your server can reach Vertex through either Anthropic's SDKs (Python, TypeScript, Go, or Ruby) or Google's own official Vertex SDKs—the course builds with Anthropic's.

It also helps to know what happens once the request lands on the model, because it explains why max_tokens and stop reasons behave the way they do. Four stages: Tokenization breaks the input into tokens; Embedding turns each token into a numeric vector; Contextualization adjusts those embeddings based on neighboring tokens to resolve meaning—it's how "quantum" gets disambiguated between physics and computing; Generation takes the contextualized embeddings, produces a probability distribution over the next token, mixes that probability with some randomness rather than always taking the top pick, and repeats. That last stage, repeated one token at a time, is the whole model.

Lena asks the question every on-call engineer asks: can the browser just call Vertex itself and save a hop?

Your call

Yes. Never call Vertex directly from client-side code. Credentials must stay server-side and secret; anything shipped to a client is visible to anyone who looks. Your server is the secure intermediary, and that is exactly why step 1 of the lifecycle exists.
Still the wrong side of the line. The rule in these notes is unconditional: route through your own server. A credential in client code is exposed regardless of how you dress it up, and you also lose the server-side place to enforce validation, allowlists, and logging.
Obfuscation is not secrecy. Anything the browser can use, a reader of the bundle can extract. Keep credentials and privileged actions on the server.

Memory hook: never tape the vault key to the storefront window. The server is the locked back office—on Vertex, on Bedrock, and on the direct API alike.

9:50 a.m. · The string that breaks builds

The model identifier

Lena is writing the config schema and wants to know what a valid model value looks like, so she can validate it before a deploy rather than after.

Which identifier is a Vertex model name?

That’s the one. Vertex model IDs use the model-name@version-date form—claude-sonnet-4@20250514. The @ version suffix is the visual tell that you are looking at a Vertex identifier.
That’s the direct Anthropic API. The direct API takes a plain model name string with no version suffix and no vendor prefix. On Vertex you must add the @version-date suffix.

12:40 p.m. · The manifest parser

Getting machine-readable output out of a Vertex call

Meridian wants shipment manifests turned into structured records that flow into their warehouse system. Aster has two techniques available, and they are the same two she would use on the direct API.

  • Assistant prefill plus a stop sequence — prefill the opening delimiter, stop at the closing one, and Claude emits only the delimited payload with no commentary. Good for small, delimited outputs like JSON or CSV. The matched stop-sequence text is excluded from the returned output.
  • A dedicated tool schema — define a tool whose inputs match the structure you want, then force it with tool_choice. More setup, more reliable, and the right choice when a production workflow needs a strict output contract.

The tool_choice options are worth memorizing as a trio: automatic when Claude may answer normally, any when one of the available tools must be used, and a specific tool when a particular schema is mandatory.

Manifests feed a downstream system that rejects malformed records. Your call

Right for production. When the output contract is strict, prefer a dedicated tool schema and force it with tool_choice naming that specific tool. Then still parse and validate in application code.
Workable, but the weaker guarantee here. Prefill plus stop sequence is the right reach for small, delimited outputs and quick extraction. For a production workflow that needs reliable structured data, the tool schema is the recommended path.
Not a contract. Claude naturally adds headers, footers, and explanation around structured data. That is exactly the problem prefill/stop sequences and tool schemas exist to solve.
Half right, and the dangerous half is missing. The schema shapes the output; it does not make the values correct. Valid JSON can still contain invalid dates, unauthorized identifiers, or values that violate domain rules. Parse and validate in application code regardless of technique.

Also carried over unchanged: keep system instructions separate from user data, and place stable instructions before volatile context. When a prompt is reused across calls, consider caching or reusing the stable prefix—but measure the token savings and the invalidation behavior rather than assuming a win. The rules that govern that decision are fixed and worth knowing cold: a cache breakpoint must be set manually (it is not on by default), content up to and including the breakpoint needs at least 1024 tokens to be eligible, the cached content must be byte-identical on every follow-up or the cache invalidates, a cache lasts 5 minutes, and you get up to 4 breakpoints per request across system prompt, tool schemas, and messages—processed in that order (tools → system → messages) behind the scenes.

1:30 p.m. · The tracking agent

The tool loop, and the temptation to batch

Meridian’s support agent needs to look things up: shipment status, terminal hours, customs codes. The Vertex tool loop has the same non-negotiables as everywhere else, and Aster’s first implementation drops two of them.

On the follow-up call your application must: preserve the complete assistant content, execute each requested tool, send matching tool results with their IDs, and retain the original tool definitions. Alongside that: validate tool inputs, enforce permissions, and make side effects idempotent where possible.

Lena: “Three separate round-trips just to answer one question. Can we make it do them all at once?”

That is the batch-tool pattern: give Claude one higher-level batch_tool whose schema takes an invocations list—each entry naming a tool and its arguments—rather than trusting it to emit several native tool-use blocks in one turn, which it rarely does in practice. Your code unpacks the list and runs each invocation, then returns one combined result. Done this way, six independent lookups collapse from six round-trips (or seven, counting the initial request) down to two: the request that returns the batch call, and the single response carrying all six results. It is appropriate for independent lookups or transformations—and inappropriate for a sequence where the second call depends on the first, or where concurrent execution could duplicate an unsafe action.

Which of Lena’s requests is a good batch candidate?

Ideal. Six independent read-only lookups with no ordering dependency is precisely what the batch tool is for—group the invocations, run them in parallel, return one combined result, and collapse the round-trips.
Not batchable. The second call consumes the first call’s output, so this is a dependent sequence. Batching is for independent sub-invocations only; let the loop run these in order.
Dangerous. These are side-effecting actions where concurrent execution could duplicate something unsafe. Keep them sequential, make them idempotent, and route consequential actions through a human approval path.

Memory hook: keep the full order ticket, cook the requested dish, return it with the matching table number, and leave the menu on the table—assistant content, tool execution, tool_use_id, tool definitions.

2:20 p.m. · The tariff handbook

RAG on Vertex

Meridian has a nine-hundred-page customs and tariff handbook. Nobody is pasting that into a prompt. You sketch the production retrieval path, and it is the same architecture you would build anywhere—with one Google-flavored ingredient.

  1. Chunk documents while retaining source and chunk metadata.
  2. Generate semantic embeddings and search a vector index. On Vertex AI, the course names Google’s text-embedding-005 as the embedding model available for this, used through the Google GenAI SDK. Embedding vectors are normalized to unit length (magnitude 1.0)—typically handled automatically by the embedding API—which is what makes the similarity math below meaningful: cosine similarity is the cosine of the angle between two vectors, from −1 to 1 (higher is more similar), and cosine distance is 1 minus that, so values near 0 are the best matches. Vector databases report distance, and lower wins.
  3. Search a lexical index such as BM25 for exact terms, identifiers, and names. BM25 tokenizes the query, counts how often each term appears across the chunks, and weights rare terms higher than common ones—so a specific identifier like "incident 2023 Q4 011" outranks chunks that merely share common words, which is exactly the failure mode pure semantic search falls into.
  4. Fuse the ranked results with reciprocal rank fusion.
  5. Rerank the short list against the query when better relevance is worth the added latency.
  6. Give Claude only the best labeled chunks and require source-aware answers.

Two implementation details that reliably show up as questions: reranking should return document or chunk IDs so the application can fetch the original text, rather than paying to repeat full chunks in the reranker’s response. And contextual retrieval enriches a chunk with enough document-level context to stand on its own before it is embedded and indexed.

Kwame: “It quoted a tariff rule that contradicts page 412. Is Claude wrong, or is the pipeline wrong?”

How do you find out?

The only diagnostic that works. An answer can be wrong because the needed chunk was never retrieved, because the supplied context was misread, or because the model synthesized it incorrectly. Test retrieval separately from generation and you learn which of the three doors is broken.
Guessing. If the correct chunk never made it into the prompt, no model can recover it. Establish whether retrieval succeeded before you touch the generation side.
A plausible fix applied blindly. Re-chunking may help—if retrieval is the failing stage. You do not know that yet. Measure retrieval first; contextual retrieval and hybrid search are the tuned responses once you have confirmed the problem lives there.
Exhortation is not evaluation. Requiring source-aware answers over labeled chunks is good design, but it does not tell you which stage failed. Split retrieval from generation and measure.

Memory hook: three doors—did the librarian fetch the right page, did Claude read it right, did it tell the story right?

3:10 p.m. · The scoping meeting

Workflow or agent—and what you owe either one

Meridian wants two things. First, a nightly exception report: fixed steps, known order. Second, a support assistant that answers whatever a dispatcher throws at it.

Use a known workflow for fixed steps—chaining, routing, parallelization, or evaluator–optimizer review. Use an agent only when Claude needs to choose an unknown sequence of tools. The nightly report is a workflow. The dispatcher assistant is the case for an agent.

In both cases the operational contract is the same, and it is what Lena actually cares about: define budgets, timeouts, stop conditions, retries, state, observability, and a human approval path for actions that change external systems.

Shared capabilities are not controls. Tools, web search, computer-use-style features, MCP integrations, prompt caching, and file or image inputs are architectural capabilities—not replacements for application controls. Keep credentials and privileged actions on the server, allowlist tools and destinations, validate files and arguments, limit time and tokens, log decisions and failures, and require human review for consequential side effects.

None of this is Vertex-specific, which is exactly why it is worth saying out loud in a Vertex lesson: an exam scenario set on Google Cloud will still ask domain-general orchestration questions, and the Google Cloud framing is not a hint that the answer changes.
