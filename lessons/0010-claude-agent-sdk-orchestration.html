The second engine

You are the architect. Northstar is about to put an agent inside its own product — a support agent that answers customers directly, at three in the morning, with nobody watching. Claude Code gave your engineers hands. This gives your customers one, and every decision you make now is a decision you cannot take back on Monday.

8:05 a.m. · The brief

A coworker with hands, then a product with hands

Yesterday Northstar adopted Claude Code: an agent that works inside your repository, for your engineers. Today the ask is different. Dana Osei, who runs support ops, has a queue of 4,000 tickets a week and a resolution playbook her team follows by hand. She wants that playbook to be an agent that talks to customers.

“Same model. Same tools, more or less. Can’t we just point Claude Code at it?”

No — because Claude Code is a terminal application and this needs to live inside Northstar’s product. What you want is the Claude Agent SDK: the same agent harness, exposed as a library you call from your own code.

The mental model that explains everything else

Here is the fact that makes the rest of the API stop looking arbitrary: the SDK spawns the Claude Code CLI as a subprocess and talks to it over a control protocol.

Once you know that, you stop being surprised that a library has permission modes, hooks, settings files, CLAUDE.md loading, plan mode, and subagents. Those are Claude Code’s features. The SDK is a steering wheel bolted onto a car that already exists — which is also why options like pathToClaudeCodeExecutable and spawnClaudeCodeProcess are there at all.

8:40 a.m. · What you stop writing

The loop is no longer yours

In the Claude API course you wrote the agentic loop by hand: call the model, check stop_reason, and while it is "tool_use", run the tool yourself, append a tool_result block, and call again — stopping at "end_turn".

That knowledge is still tested and still true underneath. But the SDK runs that loop for you and hands you a stream of messages instead. What you own shifts from mechanism to policy: which tools exist, who may call them, when to stop, and what runs around each call.

from claude_agent_sdk import query, ClaudeAgentOptions

async for message in query(
    prompt="Resolve ticket NS-4417.",
    options=ClaudeAgentOptions(
        allowed_tools=["Read", "Grep"],
        max_turns=12,
    ),
):
    if hasattr(message, "result"):
        print(message.result)
import { query } from "@anthropic-ai/claude-agent-sdk";

for await (const message of query({
  prompt: "Resolve ticket NS-4417.",
  options: {
    allowedTools: ["Read", "Grep"],
    maxTurns: 12
  }
})) {
  if ("result" in message) console.log(message.result);
}

No stop_reason check anywhere. That is the trade.

9:20 a.m. · The empty stage

“It’s ignoring our CLAUDE.md.”

Kenji has spent a week getting Northstar’s CLAUDE.md right — tone rules, escalation language, the list of things support may never promise. The SDK agent ignores all of it. He assumes a bug.

It is not a bug. It is two defaults, and both surprise people.

Default one: the system prompt is minimal

Omit systemPrompt and you do not get Claude Code’s system prompt — you get a minimal one. To opt in:

Default two: settingSources decides what the SDK reads off disk

ValueLocation
user~/.claude/settings.json

Omit the option entirely and all three load, exactly like the CLI. Pass [] and none of them do. And project CLAUDE.md loads only when "project" is among the sources — which is Kenji’s bug, because Toby had written settingSources: [] to make the prototype deterministic.

Northstar is shipping this in a product. What goes in the config?

Non-reproducible. Loading user and local means the shipped agent’s behavior depends on files on whichever machine it runs on — including a developer’s personal settings. Fine for a CLI, wrong for a product.
Right for a shipped product. [] disables user, project, and local settings, so behavior is identical everywhere it runs. The tone rules still need a home — they move into systemPrompt (or its append), where they are version-controlled with the code that depends on them. Endpoint-managed policy still loads regardless.
Defensible, and a real trade. It keeps CLAUDE.md authoring in Kenji’s hands, but it also means editing a markdown file changes production behavior with no deploy and no review. For an internal tool, reasonable. For a customer-facing agent, prefer [] and put the rules in the prompt.
Worst of both. You’ve kept the reproducibility problem — user settings still vary per machine — without gaining anything ["project"] alone wouldn’t give you.

Version trap, Python only: in Python SDK 0.1.59 and earlier, setting_sources=[] was treated the same as omitting the option, so it did not disable filesystem settings. If a Python agent is mysteriously reading settings you told it to ignore, check the SDK version first. TypeScript is unaffected.

10:00 a.m. · Rosa’s question

“What stops it?”

Rosa has one question about anything that runs unattended, and it is always the same question. An agentic loop that can call tools can also call tools forever.

OptionWhat it caps
maxTurns / max_turnsAgentic turns — tool-use round trips
maxBudgetUsdStops when the client-side cost estimate reaches a USD figure
taskBudget: { total } (alpha)An API-side token budget the model is told about, so it paces itself and wraps up before the limit
fallbackModelNot a cap — the model to use if the primary fails
abortController (TS)Cancellation from your side

The distinction worth holding: maxTurns and maxBudgetUsd are guillotines — the run stops, mid-thought, when the number is hit. taskBudget is different in kind, because the model knows the budget and can choose to summarize and finish rather than be cut off.

“I don’t mind it stopping. I mind it stopping in a way that leaves the customer holding half an answer.”

Cap the loop twice: once with a hard stop you control, and once with a budget the model can see and plan against. The first protects your bill; the second protects the answer.

The SDK gives you the loop for free. It does not give you judgment for free.Everything from here is about buying judgment back.

10:45 a.m. · The context problem

One agent, reading everything

Toby’s prototype works, and then it doesn’t. A hard ticket makes it read the order history, then the refund policy, then eleven similar past tickets — and by the time it has an answer, the window is full of material the customer never asked about, and the answer is worse for it.

Subagents are the fix. A subagent is a separate agent instance your main agent spawns for a focused subtask, and it buys you four things:

  • Context isolation. Each subagent runs its own fresh conversation. Intermediate tool calls and results stay inside it; only its final message comes back. A researcher can read fifty files without fifty files landing in the main window.
  • Parallelization. Independent subtasks finish in the time of the slowest, not the sum of all of them.
  • Specialized instructions. Deep refund-policy knowledge that would be noise in the main prompt.
  • Tool restrictions. A subagent given only Read and Grep cannot modify anything, ever.

Defining one

from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Grep", "Glob", "Agent"],
    agents={
        "policy-checker": AgentDefinition(
            description="Checks refund eligibility against policy. "
                        "Use before any refund is offered.",
            prompt="You are a refund policy specialist...",
            tools=["Read", "Grep"],     # read-only
            model="sonnet",
            maxTurns=6,                 # camelCase — see the trap below
        )
    },
)
import { query } from "@anthropic-ai/claude-agent-sdk";

const options = {
  allowedTools: ["Read", "Grep", "Glob", "Agent"],
  agents: {
    "policy-checker": {
      description:
        "Checks refund eligibility against policy. Use before any refund is offered.",
      prompt: "You are a refund policy specialist...",
      tools: ["Read", "Grep"],   // read-only
      model: "sonnet",
      maxTurns: 6
    }
  }
};
FieldRequiredWhat it does
descriptionYesWhen to use this agent. This is what Claude matches against — vague descriptions mean the subagent never gets picked.
promptYesThe subagent’s system prompt.
toolsNoAllowed tool names. Omit and it inherits every tool available to subagents.
disallowedToolsNoRemoves tools. Accepts MCP patterns: mcp__server__*, mcp__*.
modelNo'opus', 'sonnet', 'haiku', 'inherit', or a full ID.
skills, memory, mcpServersNoPreloaded skills, memory source, per-agent MCP servers.
maxTurns, effort, permissionModeNoPer-agent turn cap, reasoning effort, permission mode.
backgroundNoForce non-blocking background execution.
initialPromptNoAuto-submitted first turn when this agent runs as the main thread agent — ignored when it’s invoked as a subagent.

A tool you leave out of tools isn’t merely denied — it isn’t in the subagent’s session at all. No permission prompt, no error. Claude just works without it.

The Python camelCase trap. AgentDefinition keeps camelCase field names even in Python — disallowedTools, permissionMode, maxTurns, mcpServers, initialPrompt — because they map straight to the wire format shared with the TypeScript SDK. Meanwhile ClaudeAgentOptions uses ordinary snake_case (disallowed_tools, permission_mode, max_turns). Since AgentDefinition is a dataclass, passing max_turns= raises TypeError at construction. Two objects, two conventions, one file.

11:30 a.m. · Nothing is being delegated

The tool with two names

And what comes back

Only the subagent’s final message, delivered as the tool result. Everything it did to get there stays inside it — that is the isolation working. Note that the parent may summarize that final message in its own response; if you need it preserved verbatim, say so in the main query’s prompt or system prompt.

Delegation is a briefing, not a handoff. You cannot give a subagent your memory — only a note. Write the note as if the reader has never seen the conversation, because they haven’t.

Dana wants more than refunds. She wants the agent to handle a whole class of “investigate this account and tell me what happened” tickets. That is a different shape of problem, and the exam names three shapes.

Hub-and-spokeA coordinator owns all inter-subagent communication, error handling, and routing. Spokes never talk to each other.Any multi-agent system. This is the default topology.

3:10 p.m. · Everything passed, nothing worked

When every worker succeeds and the answer is still wrong

Northstar’s research agent — the one that summarizes “what happened with this account” — decomposes each ticket into three parallel subagents. Every subagent returns cleanly. Every log is green. And the summary Dana gets covers billing, only billing, and nothing but billing, while the actual complaint was about delivery.

Toby wants to add retries to the subagents. Rosa wants to know why three green checks produced a wrong answer.

Where is the defect?

The logs say otherwise. Each subagent did exactly what it was told. Blaming a downstream component that provably worked is the trap this question is built around.
Correct. The coordinator generated three subtasks that all pointed at the same sub-topic, so the workers succeeded within a scope that was wrong before they ever started. When every worker succeeds and the aggregate is wrong, look up the chain, not down.
Nothing to drop. Synthesis can only combine what it received, and delivery findings were never produced — because nobody was asked for them.
Not the constraint here. Restricted tools would show up as subagent failures or empty results. These returned cleanly and in scope; the scope was just the wrong one.

The other half: what a failing subagent should say

A subagent that times out mid-investigation has three ways to report it, and only one lets the coordinator recover well:

  • Return an empty result marked successful. Now the coordinator believes there was nothing to find. Worst option — it converts a failure into a confident wrong answer.
  • Retry silently, then return “search unavailable.” Better, but the coordinator learns nothing about how far it got or what it did find.
  • Return a structured error naming what failed and how far it got. Now the coordinator can re-scope, re-dispatch a narrower query, or escalate — an actual decision.

A coordinator can only be as smart as its inputs. Error propagation is an architecture decision, not an implementation detail: what a failing component says determines what its supervisor is capable of doing about it.

Where part 1 leaves you

Dana’s agent runs. It answers tickets, delegates policy checks, and stays inside a turn budget. Rosa still won’t ship it, and she’s right not to.

The SDK is Claude Code as a library. Subprocess underneath, which is why permissions, hooks, settings, and subagents all came along for the ride. query() for one-off work; ClaudeSDKClient when the next move depends on the answer or a human might interrupt.

The defaults are quieter than you expect. Minimal system prompt unless you ask for the preset. No CLAUDE.md unless "project" is in settingSources. In a shipped product, prefer [] and put the rules where they get reviewed.

Subagents buy isolation, parallelism, specialization, and restriction — and cost you the assumption that anyone downstream knows anything. Task/Agent in allowedTools or nothing gets delegated. The prompt string is the entire channel. Only the final message comes back.

And when the aggregate is wrong but every part is green, the coordinator wrote the wrong assignment. That is the multi-agent failure mode worth memorizing, because it looks like nothing is broken.

Part 2 is Rosa’s objection, stated properly: the agent currently usually does the right thing. Next we make “usually” into “always.”
