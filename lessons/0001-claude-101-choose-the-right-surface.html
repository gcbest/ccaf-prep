The Northstar launch

You are the architect. One busy day, five messages, and one question underneath all of them: what kind of work is this?

8:42 a.m. · The first message

“Can you think this through with me?”

Maya, the support lead, is preparing a new refund policy. She does not want a report yet. She wants to bounce ideas around, ask follow-up questions, and revise the wording as she goes.

“I need a thinking partner, not a robot that disappears for ten minutes and comes back with a finished memo.”

Your call

Exactly. Chat is turn-by-turn work: brainstorming, explaining, drafting, reviewing. The next move depends on the last reply.
Not quite. Cowork can do this, but it adds delegation and tool access that Maya does not need. This is a conversational job, so Chat is the natural fit.
Wrong workshop. Code is designed for work inside a software repository. Maya needs a conversation, so Chat is the natural fit.

Chat is the café. You stay present, exchange turns, and steer the work as understanding develops.

9:16 a.m. · The handoff

“Make the launch kit while I’m in the meeting.”

Owen from operations drops a folder of product notes on your desk. He needs a customer FAQ, a checklist, and a polished HTML handout saved back into the launch folder. He also wants this repeated every Friday.

“I can give it the folder, the deadline, and the rules. I don’t need to supervise every paragraph.”

Your call

Possible, but awkward. Chat can draft from uploads, but it is not the best fit for a delegated workflow that must save work into a local folder and run on a schedule.
That’s the workshop. Cowork is built for multi-step handoffs involving local folders, connectors, browser/computer use, subagents, or schedules.
Too code-shaped. Unless the deliverable is primarily repository work, Code is not the best surface for this operations handoff. Cowork fits the shape.

Cowork is the workshop. It can take a goal, use permitted tools, produce a deliverable, and put it where it belongs. More agency means you need clear permissions, checkpoints, and a way to verify the result.

10:03 a.m. · The red build

“Find the bug. Prove the fix.”

Priya from engineering sends a failing test and a link to the Northstar repository. The job is to inspect the code, edit the function, run the test suite, and show the diff for review.

“The answer is not enough. I need the change, the evidence, and a reviewable trail.”

Your call

Good for discussion, not the full workflow. Chat could help reason about the bug, but the repository, edits, tests, and diff belong in Code.
Broader than necessary. Cowork can coordinate multi-step work, but Code is the purpose-built surface for repository inspection, editing, testing, and review.
Open the garage. Code is designed for the full software loop: inspect → plan → edit → test → review.

Code is the garage. The surface matches the artifact and the verification loop—not just the topic.

Surface selection is a shape-of-work decision.Conversation → Chat · Delegation → Cowork · Repository → Code

11:21 a.m. · The briefing

Maya asks for a better instruction

Her first prompt was: “Explain our refund policy.” The answer was accurate but generic. You help her rewrite it as a brief she could hand to a capable coworker.

Stage: “You are a customer-support coach helping new Northstar agents.”
Task: “Explain the refund policy and identify the three decisions an agent must make.”
Rules: “Use plain language, a numbered decision tree, and one example conversation under 120 words.”

The three ingredients are setting the stage, defining the task, and specifying rules. If format matters, show an example or describe the structure explicitly—“make it clear” is not a structure.

A good prompt is not a spell. It is a clear brief.

1:40 p.m. · The growing library

“Where should this knowledge live?”

Northstar has a permanent support playbook: policies, product history, and team decisions. It belongs in a Project—a persistent workspace for knowledge, instructions, and conversation history.

But the team also has a repeatable procedure called “Friday launch kit”: inspect the folder, summarize changes, create three files, run a checklist, and save the results. That belongs in a Skill—a packaged process with instructions, scripts, and resources.

Project = the what. Skill = the how. The bookshelf stores the knowledge; the recipe card describes the procedure. A Skill can draw on knowledge in a Project.

When the Project’s knowledge grows too large for the context window, Claude can use RAG: search the knowledge base and retrieve only the relevant pieces instead of loading everything at once.

3:05 p.m. · The locked doors

“Can Claude search the company?”

Northstar connects Slack and SharePoint. Claude’s connectors use MCP, a shared standard Anthropic compares to “USB-C for AI”: one consistent way to connect many tools.

But the connector is not a master key. Claude sees only what the user is already permitted to see. Access can be scoped, toggled, and revoked. Enterprise Search adds a permission-aware organizational search experience; admins configure document and chat sources, while each user authenticates their own access.

The rule at Northstar: a connector is an office badge, not a skeleton key.

4:18 p.m. · The research question

“Should we change vendors?”

The COO asks for a sourced comparison across current pricing, support policies, and three years of analyst reports. A quick fact would call for web search. This is different: the answer needs a plan, many searches that build on each other, synthesis, and citations.

Research is agentic and multi-step. It uses Thinking to plan, searches across many sources, synthesizes, and cites. It may take minutes. Web search is the lighter tool for a quick current fact. Research needs web search enabled to function.

5:02 p.m. · The last check

“Did we make Claude reliable—or just impressive?”

Before automating the Friday launch kit, you gather 5–10 real examples of the task. You write test prompts using natural context, compare Claude’s output with the team’s originals, look for missing facts, wrong tone, and format drift, then refine the prompt or add examples.

That is the lightweight eval loop. And when Claude sounds confident about a niche fact, you verify it independently, ask for sources or confidence, and use web search when current evidence matters.

Finally, you separate two kinds of personalization: Memory carries context such as preferences and past decisions across conversations; Styles control how Claude communicates.

The architect’s pocket card

At the launch meeting, someone asks how you made all those calls so quickly. You answer:

First identify the shape of work. Then choose the surface. Give Claude a clear brief. Put durable knowledge in Projects and repeatable procedures in Skills. Scope connectors like badges. Match Research to questions that need multi-step evidence. Test recurring work with real examples.

That is Claude 101: not “what button do I press?” but “what kind of collaboration does this job require?”
