CCA-F · Section 2Northstar Dispatch · Monday

The Northstar launch

You are the architect. One busy day, a growing team, and a series of decisions that reveal what Claude is—and how to work with it well.

7:55 a.m. · Before the doors open

Meet the new coworker

Northstar is about to launch a new product. Your manager introduces Claude as a remarkably capable coworker: it can summarize a long brief, search, write collaboratively, answer questions, code, and help reason through a complicated multi-step problem.

It is also steerable. Give it a different role, tone, or behavior and it can adapt. But capability is not the same as judgment, so the team keeps responsibility for the goal, the permissions, and the final verification.

Under the hood, in this course’s framing: Constitutional AI guides Claude toward being helpful, harmless, and honest. That includes avoiding toxic or discriminatory output and refusing illegal or unethical assistance while operating transparently.

Northstar can meet Claude in several places: Claude.ai on web, desktop, or mobile; Claude Code for agentic coding; @Claude in Slack; Claude Design for UI prototyping; and Claude for Microsoft 365 in the Word, Excel, PowerPoint, and Outlook sidebars.

The standard context window is described as 200K+ tokens—roughly 500 pages—with up to 1M tokens on Pro, Max, Team, and Enterprise for supported models. When a problem is difficult, Thinking lets Claude spend more effort reasoning before answering. When the goal is to learn, Learning mode guides your reasoning instead of simply handing you the answer.

First principle: Claude is more than a chatbot, but it is not an autonomous replacement for human responsibility. The architect chooses the setting, the scope, the tools, and the checks.

8:42 a.m. · The first message

“Can you think this through with me?”

Maya, the support lead, is preparing a new refund policy. She does not want a report yet. She wants to bounce ideas around, ask follow-up questions, and revise the wording as she goes.

“I need a thinking partner, not a robot that disappears for ten minutes and comes back with a finished memo.”

Your call

Exactly. Chat is turn-by-turn work: brainstorming, explaining, drafting, reviewing, and quick iteration. The next move depends on the last reply.
Not quite. Cowork can do this, but it adds delegation and tool access that Maya does not need. This is a conversational job, so Chat is the natural fit.
Wrong workshop. Code is designed for work inside a software repository. Maya needs a conversation, so Chat is the natural fit.

Chat is the café. You stay present, exchange turns, and steer the work as understanding develops.

9:16 a.m. · The handoff

“Make the launch kit while I’m in the meeting.”

Owen from operations drops a folder of product notes on your desk. He needs a customer FAQ, a checklist, and a polished HTML handout saved back into the launch folder. He also wants this repeated every Friday.

“I can give it the folder, the deadline, and the rules. I don’t need to supervise every paragraph.”

Your call

Possible, but awkward. Chat can draft from uploads, but it is not the best fit for a delegated workflow that must save work into a local folder and run on a schedule.
That’s the workshop. Cowork is built for a multi-step handoff involving local folders, connectors, browser use, computer use, subagents, plugins, or schedules.
Too code-shaped. Unless the deliverable is primarily repository work, Code is not the best surface for this operations handoff. Cowork fits the shape.

Cowork is the workshop. It can read a local folder and save the finished work back there—not merely return a download. It can coordinate tools and people-like subagents, but more agency means more need for a clear goal, permissions, constraints, checkpoints, and a way to verify the finished artifact.

10:03 a.m. · The red build

“Find the bug. Prove the fix.”

Priya from engineering sends a failing test and a link to the Northstar repository. The job is to inspect the code, plan the change, edit the function, run the test suite, and show the diff for review.

“The answer is not enough. I need the change, the evidence, and a reviewable trail.”

Your call

Good for discussion, not the full workflow. Chat could help reason about the bug, but the repository, edits, tests, and diff belong in Code.
Broader than necessary. Cowork can coordinate multi-step work, but Code is the purpose-built surface for repository inspection, editing, testing, and review.
Open the garage. Code is designed for the full software loop: inspect → plan → edit → test → review.

Code is the garage. Local and cloud sessions have different filesystem and GitHub access, so confirm the environment before acting. Permission settings can include Manually approve, Accept edits, and Plan. The more powerful the session, the more important checkpoints and verification become.

Surface selection is a shape-of-work decision.Conversation → Chat · Delegation → Cowork · Repository → Code

11:21 a.m. · The briefing

Maya asks for a better instruction

Her first prompt was: “Explain our refund policy.” The answer was accurate but generic, too long, and not shaped like something a new agent could use. You help her rewrite it as a brief she could hand to a capable coworker.

Setting the stage: “You are a customer-support coach helping new Northstar agents.”
Defining the task: “Explain the refund policy and identify the three decisions an agent must make.”
Specifying rules: “Use plain language, a numbered decision tree, and one example conversation under 120 words.”

The three ingredients are setting the stage (role, objective, and context), defining the task (the specific action), and specifying rules (style, tone, format, constraints, and examples). Talk to Claude like a capable coworker: naturally, concisely, and with the context it needs.

The repair bench

What went wrongWhat the architect adds
Too genericAudience, role, situation, and constraints
Too long or shortAn explicit length target
Wrong formatA structure or example, not just “make it clear”
Wrong toneA plain-language description plus a tone example
Confidently wrong niche factIndependent verification, sources/confidence, and web search when appropriate

A good prompt is not a spell. It is a clear brief.

11:48 a.m. · The second draft

“Don’t start over. Coach it.”

Claude’s second answer has the right structure, but the conclusion is too soft. You say, “Cut the first two paragraphs and make the conclusion more action-oriented.” That specific feedback is much more useful than “make it better.”

The first prompt is the start of a conversation, not a one-shot test. Redirect within the same chat when the context is still useful; restart in a new chat when the conversation has accumulated the wrong assumptions or needs a clean frame. If you made the original instruction unclear, edit it with the pencil icon and resubmit rather than building a chain of corrections downstream.

Iteration is part of the method. Give concrete feedback, observe the next output, and decide whether to redirect or restart. And once a prompt is actually earning its keep on recurring work, don't leave it to memory — save it as Project instructions or turn it into a Skill, so the next person doesn't have to reconstruct it from scratch.

12:35 p.m. · The growing library

“Where should this knowledge live?”

Northstar has a permanent support playbook: policies, product history, team decisions, and the preferred way answers should be written. It belongs in a Project—a self-contained workspace with its own memory, chat history, knowledge base, custom instructions, and ongoing context.

A Project is useful for a domain, client, course, or recurring workflow. It answers: what should Claude know, and what should stay consistent? Team and Enterprise sharing can distinguish Can view, Can edit, and Owner.

When the knowledge base approaches the context limit, Claude need not carry every page into every conversation. It can use RAG—Retrieval Augmented Generation—to search the knowledge base and retrieve the relevant pieces. The course describes this as expanding effective capacity by up to 10×. That headroom is not a license to dump the playbook in unsorted, though—the source material still has to be organized and reviewed, or retrieval just finds the relevant mess faster.

Project = the knowledge home. It is persistent context for an ongoing area, not merely a folder of files.

1:40 p.m. · The repeatable procedure

“Where should the launch kit instructions live?”

The team’s Friday launch kit is a repeatable procedure: inspect the folder, summarize changes, create three files, run a checklist, and save the results. That belongs in a Skill—a package of instructions, scripts, and resources that Claude loads dynamically for a specialized workflow.

Anthropic’s built-in Skills power specialized document, spreadsheet, presentation, and PDF creation. A custom Skill can be created for a team’s own procedure—and not by hand-writing a file yourself: you build one through conversation, where Claude interviews you about the workflow and generates the skill file from what you describe. It needs code execution and file creation enabled, and it runs in a sandboxed environment.

Keep the boundary clear: Projects store the what; Skills define the how. A Skill can reference knowledge stored in a Project. Project instructions say how Claude should work in that workspace; a Skill is a reusable procedure that can be invoked when relevant. The project description is a different thing again—it's metadata for the humans browsing your Projects list, not instructions Claude reads and acts on.

One more habit before installing someone else's Skill: review externally sourced Skills before enabling them. A Skill can bundle executable code and file-changing steps, so accepting one sight-unseen is accepting code you haven't read running with Claude's permissions.

The bookshelf stores the knowledge. The recipe card describes the process.

2:25 p.m. · Something worth keeping

“This should live beyond the chat.”

Claude turns the launch kit into a standalone interactive HTML guide. It is substantial, self-contained, reusable, and easy to inspect on its own. That makes it an Artifact—an output in a dedicated window that can be previewed, edited, copied, downloaded, and versioned. There's a rough rule of thumb for when Claude spins content out this way rather than leaving it in the chat: typically once it passes about 15 lines.

Artifacts can be documents, code snippets, HTML pages, SVG images, Mermaid diagrams, or React components. Short prose can stay in the conversation; a reusable object deserves its own surface.

Word documents, Excel spreadsheets, PowerPoint presentations, and PDFs are handled by a separate file-creation capability rather than being treated as ordinary Artifacts. In Northstar’s workflow, the relevant Skills create those files and return them as downloadable documents.

Publishing is a separate decision

When the guide is ready, only the selected Artifact version is published. The surrounding chat remains private, and other people may remix the published Artifact. Internal sharing and public publishing are not the same risk level, so remove confidential information before making anything public.

3:05 p.m. · The locked doors

“Can Claude search the company?”

Northstar connects Slack, SharePoint, and Notion. Claude’s connectors use MCP, the Model Context Protocol—a shared standard Anthropic compares to “USB-C for AI.” One consistent interface lets developers build connectors that work across Claude’s surfaces.

There are two connector shapes:

  • Web connectors: cloud services such as Google Drive, Notion, Slack, and Asana, typically connected through the Claude directory.
  • Desktop extensions: local tools and files reached through the Claude Desktop app.

But the connector is not a master key. Claude sees only what the user is already allowed to access. Individual permissions can be toggled, and the connection can be revoked. And for anything consequential the connector can actually do—not just read—Claude may still stop and ask for confirmation before a sensitive action goes through.

Security memory hook: a connector is an office badge, not a skeleton key. It grants scoped access; it does not erase the source system’s permissions.

3:28 p.m. · The company-wide question

“Ask Northstar.”

The company has Team and Enterprise plans. Admins configure an organization-wide Enterprise Search experience that appears as “Ask Northstar” in the sidebar. It is a pre-built Project spanning connected organizational knowledge, with custom instructions from Anthropic.

Setup has two stages: an administrator configures the organization’s connectors, with a Documents connector and a Chat connector required; Email can be added but is optional. Then each employee authenticates personally. Search results stay permission-scoped: the employee sees only what they could already see in the source systems.

Enterprise Search is not “the whole company.” It is “the connected company knowledge this person is allowed to access.”

4:18 p.m. · The research question

“Should we change vendors?”

The COO asks for a sourced comparison across current pricing, support policies, and three years of analyst reports. You pause before choosing a tool.

Which route matches the evidence needed?

Exactly. Research is agentic and multi-step: it plans using Thinking, runs multiple searches that build on one another, synthesizes findings, and cites sources. It may take minutes and search across hundreds of sources. Web search must be enabled.
Too light for this job. Web search is right for a quick current fact or a small number of sources. A comprehensive, cited comparison calls for Research.
Missing the evidence. Thinking helps with difficult reasoning, but pure reasoning is not a substitute for gathering current external sources and citations. Use Research.
Wrong knowledge boundary. Enterprise Search is for permission-scoped organizational knowledge. This question needs external, multi-source investigation, so use Research.

Route by evidence: Research for comprehensive multi-source work; web search for a quick fact; Thinking for hard reasoning when external information is not the main requirement; Enterprise Search for internal connected knowledge.

5:02 p.m. · The last check

“Did we make Claude reliable—or just impressive?”

Before automating the Friday launch kit, you gather 5–10 real examples of the task the team already performs. You write test prompts using the context people naturally provide, run them, and compare Claude’s outputs with the originals.

You inspect several dimensions: Did it capture the important information? Use the right tone? Follow the requested format? Make assumptions? Leave anything out? You refine the prompt or add examples based on consistent misses. That is the lightweight eval loop from Claude 101.

When Claude gives a plausible answer about a niche fact, you do not confuse confidence with truth. Verify independently, ask for sources or a confidence level, and enable web search when current evidence matters.

Two final personalization knobs

Memory automatically carries context such as your role, preferences, past decisions, and working style across conversations. It is reviewable and editable in Settings and syncs across devices.

Styles control how Claude communicates. Choose a preset such as concise, formal, or explanatory, or describe a custom style that applies across conversations.

Reliability is a workflow, not a vibe. Test with representative examples, compare against a desired result, and keep responsibility for consequential facts and decisions.

The architect’s pocket card

At the launch meeting, someone asks how you made all those calls so quickly. You answer:

First identify the shape of work. Choose Chat for conversation, Cowork for delegated multi-step work, and Code for repository work. Give Claude a clear brief: stage, task, and rules. Put durable knowledge in Projects and repeatable procedures in Skills. Use Artifacts for substantial reusable outputs. Scope connectors like badges. Match Research to questions that need multi-step evidence. Test recurring work with real examples. Verify what matters.

That is Claude 101: not “what button do I press?” but “what kind of collaboration, evidence, and responsibility does this job require?”
