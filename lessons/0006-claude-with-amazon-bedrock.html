8:50 a.m. · The first request

Three things in the envelope

Rosa deletes the Anthropic client and writes the Bedrock one. Every Bedrock request needs exactly three ingredients: a Bedrock Runtime client (the connection, bound to a region), a model ID (which model to run), and a user message (the input).

import boto3
client = boto3.client("bedrock-runtime", region_name="us-west-2")

Then the call itself. Bedrock’s unified entry point is converse—the standard method across Bedrock-hosted model providers, not an Anthropic-specific messages.create.

user_message = {
  "role": "user",
  "content": [{"text": "What's 1+1?"}]
}
response = client.converse(modelId=model_id, messages=[user_message])
response["output"]["message"]["content"][0]["text"]

Two details Ana flags in review. First, content is a list, not a bare string—because one message can carry several parts: text, images, other media. That list is what makes multimodal requests possible at all. Second, there are only two roles and they share the same structure: role: "user" for input, role: "assistant" for the model’s reply. That symmetry is what makes multi-turn chaining trivial.

The request path itself is unremarkable, and that is the point: user submits a message → your server receives it → your server’s Bedrock client calls AWS Bedrock with the message plus a model ID → the model generates text → Bedrock returns an assistant message → your server forwards it to the user.

Memory hook for the response shape: follow the nesting dolls—response → output → message → content → first block → text.

9:45 a.m. · The durable fix

Inference profiles

You could solve this by memorising which region hosts which model and hard-coding accordingly. That is a maintenance debt that comes due every time AWS changes something. The intended solution is a cross-region inference profile: instead of naming one region’s copy of the model, you name a profile that automatically routes your request to a region where the model actually is—transparently spanning, for example, us-west-2 and us-east-2.

Rosa needs the profile ID. Kenji leans in, because “routes across regions” is exactly the sentence a compliance officer notices.

Where does she find it?

Right shelf. Inference profile IDs live in the AWS Bedrock console’s “Cross-region inference” section. That is a specific, testable fact—the exam likes it precisely because the obvious guess is wrong.
The obvious guess, and the wrong one. The main model catalog page gives you plain model IDs. Profile IDs are in the console’s “Cross-region inference” section instead.
Don’t guess identifiers. Inventing an ID by pattern-matching is how you end up back at “model doesn’t exist.” Take the profile ID from the console’s cross-region inference area.

The exam-relevant distinction, stated as plainly as it can be stated: a plain model ID is region-locked; an inference profile ID is not. Rosa swaps the identifier and the call succeeds. Nothing else in the code changes—modelId happily accepts the profile ID.

For Kenji: the trade is explicit. A profile buys you availability by allowing the request to be served from another supported region. If a workload must be pinned to one region for a data-residency reason, that is a deliberate decision to accept a region-locked model ID and manage availability yourself. The architecture question is which constraint wins—not which identifier is “better.”

11:10 a.m. · The amnesiac

There is a hard structural rule that goes with statelessness: the message list must strictly alternate roles—user → assistant → user → assistant. You can never have two consecutive messages with the same role. In practice you write small helpers that append user and assistant messages to a single growing list.

Two parameters that trip people on the way in

The system prompt is passed to converse through the system keyword parameter—as a list containing a dictionary with a text field, not a bare string. It must contain at least one character; an empty string throws an error, which is why well-designed chat helpers make the parameter optional and default it to None rather than "".

system=[{"text": "You are an AWS cloud support specialist"}]

A role-based system prompt enforces constraints more naturally than a list of do’s and don’ts: told it is a cloud support specialist, the model automatically avoids competitor mentions and declines off-topic questions, without you enumerating either rule.

Temperature is a decimal from 0 to 1 controlling randomness during token sampling, and it is set inside inferenceConfig. It helps to know what it is actually turning the dial on: text generation runs in three steps—tokenization breaks the input into chunks, prediction assigns a probability to every possible next token, and sampling picks one token according to those probabilities. Temperature 0 always takes the highest-probability token—deterministic output. A higher temperature raises the odds that a lower-probability token gets picked instead. The default is 1.0—maximum creativity. Rosa’s extraction jobs were inheriting that default. Near 0 for data extraction and factual consistency; near 1 for brainstorming and marketing copy.

Memory hook: it’s a conversation, not a monologue—you can’t speak twice in a row, and Bedrock forgets the whole chat the second it hangs up. And the creativity dial ships turned all the way up.

11:40 a.m. · The waiting bar

Streaming, so the portal doesn’t look broken

Responses take three to thirty seconds. In a customer-facing claims portal that reads as a hang. The fix is converse_stream, which emits generated text as it is produced instead of holding it until the end.

The response carries a 'stream' key holding an iterable of events. There are five event types—message start, content block delta, content block stop, message stop, and metadata—and only one of them carries text.

for event in response['stream']:
    if 'content_block_delta' in event:
        chunk = event['content_block_delta']['delta']['text']
        # send chunk to the browser
        total_text += chunk

Memory hook: the stream is a parade of five float types, but only the content block delta float throws candy. Grab delta.text and ignore the rest of the procession.

12:30 p.m. · The half-eaten JSON

“The output is missing its first line.”

The triage service must emit clean JSON for the downstream claims system. Claude keeps wrapping it in friendly headers and footers. You show Rosa the two output-control levers Bedrock gives you without touching the prompt text.

Pre-filling means appending a partial assistant-role message to the end of the message list. Claude treats it as already authored and continues from that exact point. Stop sequences are strings passed through inferenceConfig that halt generation the instant they are produced. Together they extract clean structured data: prefill the opening delimiter, stop at the closing one.

# last message in the list
{"role": "assistant", "content": [{"text": "```json"}]}

# and in inferenceConfig
{"stopSequences": ["```"]}

Rosa ships it. The parser then complains that the payload starts mid-object.

Why?

Half a truth, wrong half. The matched stop sequence is excluded from the returned text—but that is the closing delimiter, at the end. The missing opening is the prefill, which you have to glue back on yourself.

The asymmetry is the exam point: pre-filling hands Claude a sentence to finish, and you glue your half back on. A stop sequence is a tripwire that ends the sentence and then gets swept off the floor before you see the room.

1:15 p.m. · The tool loop

“It called the tool, then forgot it had.”

Claims triage needs live data: policy lookups, current date arithmetic, reminder creation. On Bedrock a tool specification carries a name, a description, and an inputSchema—and the description is doing most of the work. Write three or four sentences explaining what the tool does, when to use it, and what it returns; describe every argument.

tool_spec = {
    "name": "get_current_datetime",
    "description": "3-4 sentences: what it does, when to use it, what it returns.",
    "inputSchema": { }   # JSON Schema describing the arguments
}

The sequence is the same five steps you already know from the direct API:

  1. Send the user message and the tool specifications.
  2. Inspect the assistant content for toolUse blocks.
  3. Execute and validate each requested tool in the application.
  4. Send the complete assistant message plus matching toolResult content.
  5. Request the final response with the original tool definitions still available.

Rosa’s loop returns garbage on the second turn. She had grabbed the visible text from the first response and appended it as a plain assistant message.

What must the follow-up request contain?

All three, every time. Preserve the complete assistant content blocks including each toolUse; send toolResult blocks whose IDs match the requests they answer; and keep the original tool definitions on the follow-up call. Drop any one and the model loses the thread.
This is the bug. Sending only the visible sentence is like returning a package with no tracking label. The toolUse blocks and their IDs are what tie a result to the request that asked for it—especially when several tools run in parallel.
A false economy. The tool schemas must be included in follow-up calls or Claude gets confused about the tool definitions and cannot process the results. If schema tokens are the concern, cache them—see the caching scene.

Three more mechanics worth knowing

Stop reason. The response carries a stop reason; tool_use signals the model wants a tool run. That is the loop condition: keep going while the stop reason is tool use, break when it is not. It also stops you appending empty tool-result messages when no tool was requested.

Errors are data. Wrap execution in try/except and return a tool result with an error status and the message in its content rather than crashing. Claude can read the error and retry with corrected arguments.

The batch tool. Claude can request several tools at once but often runs them sequentially. Exposing a batch_tool whose input is a list of invocations—each naming a tool and its JSON-encoded arguments—lets Claude group independent operations into one request, and your wrapper can run them concurrently. Use it for genuinely independent calls; do not use it when calls depend on one another or could duplicate unsafe side effects.

Memory hook: three independent pizza orders can go to three ovens at once—but never bake the frosting before the cake exists.

A built-in tool worth knowing by name

Not every tool needs a hand-written schema. Claude ships a built-in Text Editor Tool for file and directory manipulation—Claude supplies the JSON schema automatically; you still write the implementation that carries out the five commands it can request: view (read a file or directory), str_replace (replace text), create (make a new file), insert (add text at a line), and undo_edit (reverse the last edit). The required tool-name string is model-specific and must match exactly: str_replace_editor on Claude 3-7, str_replace_based_edit_tool on Claude 3-5. It is the same tool-use loop underneath—Claude requests a command, your code executes it and returns the result—which is how a chat agent becomes something that can refactor a file or scaffold a test.

1:50 p.m. · The extraction contract

Flexible bucket or custom mould?

Two extraction jobs land on the same afternoon. One pulls a fixed, validated record out of every claim document and feeds the system of record. The other is an exploratory dashboard whose fields Ana changes twice a week while the team figures out what matters.

Both can be done by defining a tool whose input schema is the desired output structure, then forcing Claude to call it. toolChoice has three settings: auto (Claude decides whether to use a tool at all—the default), any (it must call some tool, its pick), and a specific named tool (it must call that one). Naming the tool is how you guarantee structured data and no natural-language answer.

The flexible variant defines a single generic tool—commonly named toJSON—whose input is an open-ended object accepting whatever properties Claude adds, with the desired fields and types described in the prompt text instead of the schema. Change the structure by editing prose; no schema rewrite.

Which job gets which technique?

Exactly the intended split. A dedicated, tightly-typed schema is the right call for complex fields, high accuracy, and production validation. The flexible toJSON approach is for general or rapidly-iterating extraction where changing the shape cheaply matters more than the last few points of reliability.

Rigorous but slow. For a structure Ana rewrites twice a week you would be rewriting schemas twice a week. Reserve dedicated schemas for the output contract that actually has to hold.
The older technique. Prefill-plus-stop-sequence works and is genuinely useful, but for reliable structured extraction a tool schema is more reliable than prompt-based extraction. Use the tool mechanism when the output contract matters.

Either way, parse and validate. A tool call that returns something JSON-shaped is not proof the data is correct. The application still checks it before anything downstream trusts it.

2:55 p.m. · Fadumo’s spreadsheet

“Every request pays for the same 8,000 tokens.”

Fadumo has been reading the usage numbers. The system prompt and tool schemas are identical on every single call, and Northstar is paying to process them every time.

Prompt caching is the lever. Normally Claude does its internal work on the input, generates, responds, and discards everything. Caching stores that work instead, so a follow-up request with identical leading content reuses it—faster responses and lower generation cost.

The mechanism is a cache point: a special message part that marks where caching occurs. Everything before the cache point is cached; everything after it never is.

system = [
    {"text": LONG_STABLE_INSTRUCTIONS},
    {"cache_point": {"type": "default"}}
]
tools = tool_specs + [{"cache_point": {"type": "default"}}]

The rules are strict and testable. A minimum of 1024 tokens of content before the cache point is required. The content before the cache point must be exactly identical between requests—any difference invalidates the cache. The cache expires after five minutes of inactivity. And you can verify it is working: the response’s usage field reports cache_write_input_tokens on the first request and cache_read_input_tokens on the hits.

Where does the cache point go?

3:30 p.m. · The policy that vanished

“It can’t find incident 2023.”

The claims knowledge base is a few thousand pages of policy documents. Stuffing all of it into a prompt hits token limits, degrades quality on long prompts, costs more, and runs slower—so the team builds a retrieval pipeline instead.

The Bedrock-flavoured version of the pipeline you already know:

  1. Chunk the source documents, preserving document and chunk IDs. The choice isn’t arbitrary: structured documents with real format guarantees get structure-based chunking (split on headers); unstructured prose gets sentence/semantic-based chunking; code or other complex formats fall back to character/size-based chunking with overlap, which is the least elegant option but the most reliable default because it works across every document type.
  2. Embed the chunks. This course uses Amazon Titan Embed Text V2, which returns roughly 1024 floating-point numbers, each typically between −1 and +1. No single dimension means anything readable; the vector as a whole is a fingerprint of meaning. One easy-to-miss step happens right here: embedding APIs automatically normalize each vector to a magnitude of 1.0 before it's stored, which is what makes the cosine math below behave.
  3. Index them in a vector store and search by similarity. Cosine similarity ranges from −1 to 1 and closer to 1 means more similar; cosine distance is 1 minus that, so closer to 0 means more similar. Vector databases typically report distance—the lowest-distance chunks are the best matches.

Rosa builds exactly that, and the query “what did the engineering team do about incident 2023?” returns semantically adjacent but useless chunks.

What do you add?

Right diagnosis. Pure semantic search can miss exact keyword matches—specific identifiers, codes, rare technical terms. BM25 tokenises the query, weights rare terms higher than common ones, and surfaces chunks containing those terms. Run both searches and fuse the ranked lists.
More is not better. Widening the net dilutes the context without fixing the reason the right chunk ranked low. Evaluate recall and answer quality on representative queries rather than assuming the largest number of retrieved chunks wins.
Treating the symptom. This is a lexical-matching failure on a rare identifier, which is a structural weakness of semantic search in general. Add a lexical ranker instead of shopping for embeddings.
Wrong stage. The generation model cannot cite a chunk that retrieval never returned. Fix retrieval first.

Fusing, reranking, contextualising

Reciprocal Rank Fusion merges the ranked lists. Each method votes with 1/(1 + rank) and the scores are summed per document; a document ranked 1st by vector search and 2nd by BM25 scores 1/(1+1) + 1/(1+2) = 0.5 + 0.33 = 0.83. Documents are re-sorted by the combined score, so appearing near the top of either list earns real points. More generally: RRF rewards documents that appear near the top across methods.

Reranking is an optional pass where Claude reorders the top candidates for relevance to the query. Give the candidates temporary IDs and ask for ordered IDs back rather than repeated full chunks—it is cheaper and faster. It improves relevance and it adds latency and token cost; that is a deliberate trade.

Contextual retrieval attacks the root problem: a chunk torn out of a document loses the context that made it meaningful. Before indexing, send each chunk plus its source document to Claude and ask it to situate the chunk within the larger document; prepend that description to the chunk. If the source document is too large for one prompt, use a subset—chunks from the start (summary or abstract) plus the chunks immediately preceding the target.

One design note that keeps the system portable: a single retriever interface can hide whether the underlying index is semantic, lexical, or hybrid. Give every component add_document and search and you can add methods later without touching callers.

None of this is Bedrock-specific. The embedding model is an AWS one and the calls go through your Bedrock client, but the chunking strategy, the fusion maths, and the evaluation discipline are identical to the direct-API design. This is the “what stays the same” column doing its work.

4:10 p.m. · The engineering room

MCP, Claude Code, and the bug that found itself

Ana’s team wants the same developer tooling they had before the migration. Almost all of it ports, with one seam worth knowing.

MCP. The Model Context Protocol gives Claude tools and context without you authoring every schema by hand. An MCP server wraps an outside service into pre-built tools; an MCP client is the communication layer between your server and it, and it is transport-agnostic—stdio, HTTP, WebSockets. The message vocabulary is small: list tools request/result, call tool request/result. The three server primitives divide by who controls them: tools are model-controlled (Claude decides when to run them), resources are app-controlled (your code decides when to fetch data, exposed by URI, static or templated), and prompts are user-controlled (a person triggers a predefined workflow). Tools serve the model, resources serve the app, prompts serve users.

On the server side, the MCP Python SDK removes the manual schema-writing entirely: decorate a function with @mcp.tool, type its parameters, and describe each one with a pydantic Field—the SDK auto-generates the JSON schema from that. Resources work the same way through @mcp.resource, tagged with a MIME type (application/json for structured data, text/plain for raw text) so the client knows how to deserialize whatever comes back. And before wiring a server into any application, there's a dev-time debugger for it: run mcp dev [server-filename.py] in an activated Python environment, open the local URL it prints, click Connect, then List Tools → select a tool → fill in parameters → Run Tool. It's the fastest way to confirm a server actually works before a client ever touches it—and worth knowing its UI is still evolving even though the underlying workflow is stable.

The Bedrock seam: MCP tool definitions do not match what Bedrock expects. The client needs a conversion step—the course writes a to_bedrock_tools() function—to translate MCP’s tool list into Bedrock tool specifications before they go into a Converse request. That is the one genuinely Bedrock-specific detail in an otherwise portable MCP integration.

Claude Code. It behaves the same on a Bedrock-backed project; the MCP starter project simply reads the Bedrock region and model ID from environment variables, exactly like the notebooks. Run claude, run init to have it scan the codebase and write a claude.md that is included as context in later requests, append notes to it with #, reset with /clear, and attach servers with claude mcp add [server-name] [startup-command]. Context can live at three scopes—project, local, and user—so a note can be scoped to the repo, to your machine, or to you personally. For parallel work, give each Claude instance its own git worktree so instances cannot collide on the same files, then merge the branches back; automate the repetitive parts by dropping markdown prompt files in .claude/commands, using an $ARGUMENTS placeholder for whatever changes per run, and invoking them with /project:command-name.

For any feature bigger than a one-line fix, two workflows hold up well: either (1) have Claude read and analyze the relevant files, then describe the feature and have it plan the solution before writing any code, then implement the plan; or (2) go test-first—read context, propose tests without implementing them, pick the ones that matter, then implement until they pass. Small effort spent directing Claude up front—pointing it at the right files, making it plan or test before coding—buys a disproportionate improvement in what comes back.

Computer use is a special case of tool use: a minimal schema expands into a large structure describing actions—mouse move, left click, screenshot. Claude never touches the machine directly; a Docker container simulates the environment and executes the key presses and mouse movements it requests. Setup is Docker plus a local AWS profile plus a single Docker command, using Anthropic’s reference implementation.

The bug that found itself

Ana demonstrates the automated-debugging pipeline she built: a GitHub Action runs daily, pulls CloudWatch logs, filters and deduplicates the errors, has Claude analyse each one, generate a fix, commit it, and open a pull request for human review.

The only defensible answer. Tools, web search, computer-use interactions, and MCP integrations extend what Claude can do, but Bedrock does not make side effects safe by itself. Comforting and wrong. Bedrock is an engine, not a force field. Running inside a managed AWS service does not validate a tool argument or approve a payout. Your application still needs brakes, locks, logs, and a human at the emergency stop.

The last two architecture calls

Workflow or agent? Prefer a deterministic workflow when the steps are known. Use an agent when Claude genuinely needs to choose the next tool or route through an unknown path. For either, set a bounded context, a stop condition, a budget, and a recovery strategy.

Verify the outcome, not the call. A successful tool call is not proof that the desired business outcome occurred. Check the resulting state. And know what agents are actually good at: a focused toolset, mostly information-gathering calls, running in a loop until goal or error, on high-value tasks where a mistake does not cause major economic or safety damage. Context is king—the model has no inherent knowledge of Cascade Mutual’s environment beyond what tools tell it.

The architect’s pocket card

When you translate a direct-API design to Bedrock, change the access layer and preserve the reasoning:

Credentials come from AWS IAM/boto3 configuration, not an Anthropic API key. Create a bedrock-runtime client in a region where the model is available. Use Converse with modelId, messages, inferenceConfig, and toolConfig as appropriate. Use a cross-region inference profile when the model is routed across supported regions, and take the profile ID from the console’s cross-region inference area rather than guessing from the main model catalog. Read the returned output message and content blocks, then handle stop reasons and usage.

Remember the small facts the exam likes: a plain model ID is region-locked and a profile ID is not; content is a list; system is a list of dicts with at least one character; temperature is 0–1 and defaults to 1.0; only content_block_delta events carry streamed text; the prefill is yours to concatenate and the stop sequence is excluded; caching needs 1024 tokens before the cache point and lasts five minutes; the thinking budget minimum is 1024; twenty images maximum per request; MCP tools need converting to Bedrock tool specs.

And keep the rest identical. Prompts, schemas, RAG, evals, orchestration, and verification carry over unchanged. The deployment choice changes credentials, client shape, model identifier, regional availability, and some parameter names. It does not change the human–AI responsibilities or the architecture of a reliable tool loop.
