7:50 a.m. · Before anyone opens a terminal

A coworker with hands

Claude.ai is a consultant across the table. Claude Code is the engineer inside the workshop: it has direct access to your files, your terminal, and your entire codebase, and it edits and executes directly rather than making you copy-paste between a chat window and an editor.

The course’s definition of an AI agent: software that interacts with its environment and performs actions to complete a defined goal — an LLM operating in a real-time loop, potentially with access to tools, external services, or other agents.

The agentic loop

Prompt in → Claude gathers context and gets back text or a tool call from the model → it takes an action (edit a file, run a command) → it verifies the result against the original intent → if the goal is met it stops and waits for your next prompt; if not, it loops back and retries.

Three things to hold in your head

  • The context window is finite working memory. That is why Claude Code is agentic: it strategically hunts for the information it needs instead of loading the whole repository.
  • Permissions exist. By default Claude asks before edits and commands.
  • It can make mistakes. Stay in the loop early enough to catch them cheaply.

Setup, in four moves

Install Node.js (check with npm help), install Claude Code with npm install, run claude in the terminal to log in to your Anthropic account, then point it at the project: ask it to read the README and follow the setup directions. Running /init makes Claude scan the codebase for architecture and coding style and write a CLAUDE.md that is automatically included as context in future requests.

8:15 a.m. · The one thing to take away

Explore → Plan → Code → Commit

Lila wants to know the “right” way to use it. There is one core recommended workflow, and it has four steps.

  • Explore. Let Claude investigate the codebase before it acts.
  • Plan. This is the best place to course-correct, because it happens before any code is written. Reviewing and revising a plan is far cheaper than reviewing and undoing code that already exists. Actually read the plan — do not skim it.
  • Code. Define explicit success criteria up front. Give Claude tools that let it verify its own work. Provide a reliable test suite to validate against continuously.
  • Commit. Run a subagent code review before committing — a fresh, unbiased context, with none of the same-session bias that comes from having just written the code yourself.

Two conveniences at the commit end: the /commit-push-pr skill handles commit, push, and PR in one step (and can post the PR link to Slack if an MCP server is configured in CLAUDE.md), and claude --from-pr <PR_NUMBER> resumes a session linked to a specific PR with full context, which is how you come back later to address review comments or a failing build.

“Map the trail, draw the blueprint, build the bridge, stamp the permit.”

9:30 a.m. · What the classifier actually guards

Intent, not correctness

Toby is unconvinced, so you spell out the boundary. Auto mode’s classifier is designed to block moves that escalate beyond what you asked for: production deploys and migrations, force pushes, piping downloaded code into a shell, sending sensitive data to external endpoints, destroying files outside the session.

It allows the everyday: local edits inside your project, installing dependencies from the lockfile, read-only requests, pushing to your own branch.

And it never judges correctness. Broken code is not dangerous, so broken code sails straight through.

Airport security asks whether the package is dangerous. It does not check whether the book inside is spelled correctly.

The course also warns that auto mode’s guardrails are still evolving, so the current block and allow lists live in the docs, not in your memory.

Two different questions, two different mechanisms. “Is this action safe?” is the classifier’s job, before the fact. “Is this code right?” is a hook, a test suite, and a diff — after the fact.

Instructions steer behavior. Verification produces evidence. Permissions constrain capability.Three different jobs. Do not ask one to do another’s work.

9:55 a.m. · The file everyone wants to edit

CLAUDE.md is guidance, not configuration

Kenji opens the project CLAUDE.md. It is 400 lines long and growing, because every time Claude did something someone disliked, they appended a paragraph.

Every line competes with every other line for attention. The longer the file, the less reliably Claude follows any single rule. It is a stack of sticky notes, not a steel door.

Without one, Claude re-explores your codebase from scratch every session and makes assumptions. With one, its contents are read every session and appended to your prompt — so commit it to version control and let the whole team benefit.

Four locations, all loaded together, stacking

  1. Managed policy — org-level, controlled by the platform team, cannot be excluded.
  2. User — your personal preferences, following you across all projects.
  3. Project — shared with the team, checked into the repo.
  4. Local — git-ignored, personal notes for this one repo (in-progress architectural decisions on your branch).

A teammate missing instructions everyone else has is almost always a scope bug: the rule lives in somebody’s user-level file instead of the project file.

Phrasing that actually gets followed

# Northstar payments service

## Commands
- Test: npm run test -- --run
- Type check: npm run typecheck

## Conventions
- Use named exports, not default exports.
- Put new API routes in src/api/handlers, one per file.

## Definition of done
IMPORTANT: a change is not done until the test suite has been
run and its result stated explicitly in the reply.

@.claude/conventions/code-style.md

Three rules are doing the work there. Be specific and checkable — “put new API routes in src/api/handlers, one per file,” not “follow best practices.” Name the replacement — “use named exports, not default exports,” not “don’t use default exports.” And emphasis is a budget: IMPORTANT and YOU MUST only raise priority relative to the quieter rules around them, so spend them on the two or three rules that hurt when broken. If everything shouts, nothing does.

That last line is an import. Imports split a big file into organized pieces — but Claude Code expands them inline at launch, so imports help organization, not context size. The moving truck still carries every page.

Keep the file under revision. When Claude does the wrong thing, treat it as a bug report against the file: tell Claude “add that to CLAUDE.md” and it writes the rule. Treat it like production code — if you cannot justify a line, delete it. And the course’s counterintuitive tip: start a project without one, so you discover where you actually have to course-correct instead of guessing.

From the exam guide, not the course notes: the official study reference adds three Claude Code memory objects the course does not name — .claude/rules/, a directory of topic-specific rule files whose YAML frontmatter carries glob paths (e.g. ["**/*.test.tsx"]) so conventions apply by file path rather than by directory; @import syntax as the modularity mechanism; and /memory, which shows which memory files are actually loaded in the current session. 10:45 a.m. · Kenji’s afternoon project

Hooks, past auto-formatting

Claude Code fires around 30 hook events across a session. These are the ones you will actually reach for:

  • PreToolUse — fires before a tool call. The enforcement primitive; it can block.
  • PostToolUse — fires after a successful tool call. Where auto-format and auto-lint go.
  • Stop — fires when Claude wants to end its turn. You can refuse. SubagentStop is the same signal for a subagent finishing.
  • PreCompact / PostCompact — fire around compaction.
  • InstructionsLoaded — fires when a CLAUDE.md or rule file loads, so you can audit exactly what made it into context.
  • SessionStart — primes the environment; check source=startup to run only on fresh starts.

Project-level hooks live in .claude/settings.json and get checked into the repo, so the team inherits them. Use $CLAUDE_PROJECT_DIR in script paths so they stay portable across clones and worktrees.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/guard.sh" }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          { "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/run-tests.sh" }
        ]
      }
    ]
  }
}

Read this for the ideas, not the exact braces. The course notes name the event names, the matcher, the settings file, and $CLAUDE_PROJECT_DIR; the surrounding JSON layout is the ordinary settings-file shape. What the exam cares about is which event, what it can do, and which exit code.

Kenji: “The first time one of these catches something on a run nobody watched, it has paid for itself.”

11:55 a.m. · A live key in a command

Redact instead of block

Toby’s debugging session keeps producing bash commands with a live sk_live_ key pasted straight into a curl. Blocking the command outright stops the work; letting it through leaks the key into logs and transcripts.

A PreToolUse hook returns JSON with exit 0. The field that matters is permissionDecision, with three values — allow, deny, and ask. There is a rare fourth, defer, which applies only to non-interactive -p runs, where a calling process pauses and resumes the tool.

But there is a third option beyond yes and no: updatedInput rewrites the tool call instead of blocking it.

{
  "permissionDecision": "allow",
  "updatedInput": {
    "command": "curl -H 'Authorization: Bearer sk_live_REDACTED' https://api.northstar.test/charges",
    "description": "Probe the charges endpoint"
  }
}

Your call

Safe but blunt. Deny does stop the leak, and it is the right call when the command should not run at all. Here the command is legitimate — only the secret is the problem — so updatedInput lets it run without the secret making it through.
That’s the pattern. A matcher picks the tool, an optional condition narrows to the specific command, and updatedInput rewrites it so the work continues and the secret never lands. The catch: updatedInput replaces the whole input object, so you must echo back every field you are not changing or you lose it.

12:30 p.m. · Procedures worth packaging

Skills, and the one to build first

A skill is a folder with a skill.md holding a name, a description that triggers it, and a procedure. Only descriptions load until a skill is actually needed.

The one to build first is the verification skill, because manual checking depends on you remembering to ask for it every single time. Its shape: it fires when its description matches the situation (say, after Claude edits code), it runs the test suite, it reads the diff, it checks that no test was quietly weakened just to make it pass, and it reports pass or fail with evidence. “Done” means the gates ran and the results were stated explicitly — not “the code looks right” from a diff read.

A skill folder holds more than skill.md. A reference.md alongside it carries detailed material Claude reads only when it needs depth, and scripts in the folder are executed rather than loaded, so a skill can carry its own tooling without bloating context. Check skills into .claude/skills so the whole team inherits them. If you have typed the same multi-step instruction twice, that was a skill.

1:40 p.m. · Four engineers, one repo

Subagents and parallel work

A subagent runs a delegated task in its own isolated context window, in parallel with the main agent, and returns only a summary — so the exploration trail never clutters the main conversation. You create one via /agents → “Create new agent”; Claude auto-generates the name, description, and prompt, and the description is also what determines when Claude invokes it on future prompts.

One sharp edge: preloading a skill into a subagent via the skill key loads the entire skill content immediately — unlike the main conversation, where skills load progressively, name and description first.

Worktrees

Multiple sessions editing one checkout conflict and produce invalid code. Git worktrees give each session its own independent file tree — complete project copies in separate directories, each on its own branch. Clean worktrees are auto-removed when the session exits, and a .worktreeinclude file at the repo root lists git-ignored files (env files, local config) to copy into every new worktree.

2:10 p.m. · The session that stopped being useful

Steering long sessions

Two habits keep a multi-hour session on track: scope the work before Claude starts, and steer it while it runs.

  • /context shows a breakdown of what is consuming your context window — the first thing to run when a session feels degraded.
  • /compact summarises the conversation, uses the summary as new context, and deletes the old messages. Add instructions after the command to shape what survives: /compact Focus on the --version flag implementation. Without steering, something important can get dropped and Claude drifts.
  • /clear wipes everything and starts fresh with no memory of the prior session — the right move when the task has changed and you do not want old-conversation bias bleeding in.
  • The rewind menu opens by double-tapping Escape on an empty prompt. Every user prompt creates a checkpoint. Options: restore code and conversation, restore conversation only, restore code only, “summarize from here” (compresses everything after a checkpoint — good for side conversations), and “summarize up to here” (compresses everything before it, keeping recent implementation intact).
  • /goal sets a completion condition and Claude keeps working across turns until a fast evaluator confirms it is met. The constraint that matters: the evaluator only reads the transcript, so your condition must be checkable from Claude’s own output — test results, not external state. /goal clear cancels it.
  • /loop runs a prompt on an interval between turns, which is how you poll external state like a CI run or a deploy and act when it changes. Escape stops it.

And the counterintuitive one: being specific in prompts saves context. A vague prompt forces more exploration and more of Claude’s own reasoning to fill the gaps, which costs far more context than the detailed prompt would have.

Components run alongside yours, not instead of them. Hooks stack — a plugin’s PreToolUse and yours both fire. Skills, agents, and commands are namespaced under the plugin name so they never clash. And a plugin’s own settings.json is honoured narrowly: only the agent key and the subagent status line key. The agent key promotes one of the plugin’s subagents to the main thread — its system prompt, tool restrictions, and model — so simply enabling a plugin can change how Claude Code behaves by default.

3:50 p.m. · Rosa’s turn

The automation spectrum

Once you trust Claude with a task, stop doing it by hand. There are three rungs.

Routines — build nothing

A saved prompt plus repositories and connectors, running on Anthropic’s managed infrastructure. No machine of yours stays on and no workflow file to maintain. Three triggers: a cron schedule, an HTTP POST to its API endpoint, or a GitHub event such as a new PR. Create one from the web at claude.ai/code/routines or inside Claude Code with /schedule. Three limits to know before relying on it: it is a research preview; recurring schedules run at most hourly; and each run starts from a fresh clone of your default branch and can only push to claude/-prefixed branches unless you loosen that per repo — the guardrail that keeps autonomous runs from rewriting main. In practice, this is the rung for things nobody should have to remember to run by hand: a morning dependency audit that opens a PR if something's outdated, a PR triager that labels and routes new issues, a nightly report — the kind of task you'd otherwise set a recurring calendar reminder for.

Headless — your pipeline

The -p flag (alias --print) runs Claude Code as a one-shot command with no interactive TUI: it reads stdin, writes stdout, and pipes like any shell tool. It is the fix for the classic CI symptom of claude "review this PR" hanging forever waiting for input. --bare skips auto-discovery of hooks, skills, plugins, MCP servers, and CLAUDE.md — you get Claude plus only the tools you explicitly allow, with faster startup, and deterministic, repeatable output run to run.

claude -p "Review the staged diff for security issues" \
  --bare \
  --output-format json \
  --json-schema '{"type":"object","properties":{"findings":{"type":"array"}}}' \
  > result.json

jq -r '.structured_output.findings[]' result.json

claude --resume "$(jq -r .session_id result.json)" \
  -p "Open a PR with the fixes"

That is the whole headless idiom: schema-constrained output lands in structured_output, jq lifts it out into a database or another script, and capturing the session ID lets you resume later with full context, turning one-shot runs into multi-step automation. Resume it only when that context is still trustworthy, though — a session id from a run against a branch that's since force-pushed or a repo state that's moved on is exactly the kind of stale, unverified context this whole course keeps warning about.

Agent SDK — your product

TypeScript and Python libraries that embed Claude Code inside your own application. Both expose a query function with the same primitives as the CLI — prompt plus options such as allowed tools, system prompt, and permission mode — and you iterate the streamed messages it returns.

One wrinkle worth knowing before test day: this workspace’s derived notes.md attaches the “skips auto-discovery of hooks, skills, plugins, MCP servers, and CLAUDE.md” behaviour to headless mode generally, while the course transcript in anthropic-notes.md attaches it specifically to --bare. Decision guide: routines are the default for repeat work. Headless -p when the job needs your own pipeline. --bare when CI needs identical results every run. Agent SDK when the work belongs inside your own product.

4:20 p.m. · The pull request as a handoff point

Managed Code Review vs. the GitHub Action

Managed Code Review is Anthropic-hosted, running through the Claude GitHub app with nothing to build. An org admin enables it from Claude Code admin settings, installs the app, and picks the repos and the trigger: on PR open, on every push, or only on an @claude review comment. Review agents analyse the diff against the full codebase and post findings as inline comments on specific lines, tagged by severity, with a summary table in the check run. It deduplicates and ranks findings, so you get a handful of real issues rather than a wall of nits.

Two hard limits: it never approves or blocks a PR — judgment stays with a human — and there is no managed autofix. It posts findings only; you apply them locally with /code-review and its --fix flag. It is a research preview, currently for Team and Enterprise plans.

The GitHub Action is the do-it-yourself path for anything beyond review. /install-github-app (which needs repo admin) walks through installing the app and setting the API key secret, and the action itself is anthropics/claude-code-action@v1. Its inputs: anthropic_api_key, github_token (defaulting to secrets.GITHUB_TOKEN), trigger_phrase (defaulting to @claude), provider switches for Bedrock or Vertex, prompt, and claude_args for raw CLI arguments passed through — capping the agent loop with a max-turns argument, setting the “don’t ask” permission mode for unattended runs, or scoping allowed tools to read-only for a report. Beyond an @claude mention, it can fire on a cron schedule or via workflow_dispatch for manual runs from the Actions tab.

Automated debugging, end to end

The course’s worked example stitches these together. A GitHub Action runs daily against production: the AWS CLI fetches the last 24 hours of CloudWatch logs, Claude identifies and deduplicates the errors, analyses each one, generates fixes, and opens a pull request with the proposed solutions. It catches production-only failures — invalid model IDs, wrong API keys, configuration that works locally and breaks in production — and it ends in something reviewable rather than something already merged.

5:10 p.m. · The morning after, in advance

Trust it — but verify in proportion

The governing rule: verify in proportion to how little you watched. A session you watched scroll by needs a glance. An unattended or CI run needs a real, reconstructed check, because nobody saw it happen.

Toby’s overnight run finished. There is a clean, well-written summary at the top of the transcript and a green check.

First move

The exact trap the course names. A tidy summary that reads fine can sit on top of a diff that touched files you never expected. Start from the diff, not the summary.
Right order. /code-review walks the changes and flags issues; then your own eyes go on git diff, reading the files that were in the plan first. Evidence beats narrative.
Expensive and non-conclusive. A second run produces a second thing to review, not proof about the first. Read the diff, and get a cold second opinion from a fresh session if the change is risky.
Asking is not evidence. The real question is whether the tests passed and whether Claude actually ran them or only claimed to — which is precisely why that check belongs in a Stop hook that fires on every run, not in a question you might forget to ask.

The four disciplines

  • Keep unattended runs in auto mode, not bypass — the classifier is still a safety net, though it only checks intent.
  • Start from the diff, not the summary.
  • Make tests a gate, not a promise. A Stop hook that runs the tests and refuses to end the turn on failure, or a PostToolUse hook that lints and type-checks after every edit. A hook exiting with code 2 feeds the failure straight back to Claude, which reads it and fixes it unprompted.
  • Get a cold second opinion. A fresh session or subagent with no memory of how the code was built has no stake in the approach and catches what the original run talked itself past. Headless runs get verified by their JSON result and exit code.

A reliable workflow leaves evidence: state the goal and success criteria → inspect and plan the smallest change → make the change with the least privilege needed → run the build, tests, lint, or type checks → review the diff and confirm no test was weakened or deleted → report what was verified and what remains uncertain → ask for a cold second opinion when the change is risky or the session has accumulated too much context.

The architect’s pocket card

At the end of the day Rosa asks how you kept making the same call so fast. You answer:

Match the control surface to the risk. Plan mode for anything architectural. Manual and Accept edits while you are watching. Auto plus a Stop hook when you are not. Don’t ask for unattended pipelines. Bypass only inside an isolated container or VM.

Put each rule in the right mechanism. Always-true conventions → CLAUDE.md, kept lean, specific, and checkable, with emphasis spent on two or three rules. Repeated procedures → skills, starting with verification. Rules that must never be skipped → hooks: PreToolUse to block or rewrite, PostToolUse to format after the fact, Stop to gate the turn, SessionStart with the compact matcher to survive compaction. Exit 0 succeeds, exit 2 blocks, exit 1 does nothing.

Protect the context window. Delegate exploration to subagents. Prune unused MCP servers before the 10% threshold forces tool search mode. Compact with direction, clear when the task changes, rewind when the path was wrong, and be specific — vagueness is the most expensive thing you can type.

Automate in the right order. Routines when there is nothing to host. Headless -p when the pipeline is yours, --bare when CI must be deterministic, the Agent SDK when the work lives inside your product. Managed Code Review to comment; the GitHub Action to act.

Then verify in proportion to how little you watched. That is Claude Code in action: not “how much can it do?” but “how much autonomy has been earned, and what evidence will prove it was used well?”
