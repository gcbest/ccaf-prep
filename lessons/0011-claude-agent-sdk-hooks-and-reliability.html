The gates

The support agent works. It also, in twelve percent of cases, issues a refund to a customer it never actually identified. Nobody wrote a bug. The prompt says to verify identity first, and most of the time it does. This afternoon is about the difference between most of the time and every time.

Code examples in Your choice sticks across every lesson.

2:00 p.m. · The number nobody likes

Twelve percent

Northstar’s support agent has four tools: get_customer, lookup_order, process_refund, and escalate_to_human. The system prompt is explicit — always identify the customer before touching an order.

Production says it skips get_customer entirely in 12% of cases and calls process_refund anyway.

Toby: “I’ll add few-shot examples showing it calling get_customer first. Five or six should do it.”

Rosa: “Will that make it zero?”

It will not, and that question is the whole lesson. Few-shot examples move a failure rate. They do not eliminate one, because a prompt is a request and the model is free to decline it under pressure. Programmatic enforcement guarantees deterministic compliance; prompt instructions are probabilistic and carry a non-zero failure rate.

Yesterday you learned this in Claude Code terms: if it must happen every time without fail, it belongs in a hook. Today the same principle, in a product, where the failure has a customer’s money attached to it.

The governing question all afternoon: is this a thing I want Claude to do, or a thing Claude must not be able to skip? The first is a prompt. The second is code.

2:20 p.m. · The fix

A gate, not a reminder

Twelve percent of refunds go out without identity verification. Your move.

Correct, and this is the exam’s flagship question. A PreToolUse hook inspects each outgoing call, checks whether verification has happened in this session, and denies the call if it hasn’t. Deterministic: the 12% becomes 0%, not 3%.
Reduces, doesn’t eliminate. Few-shot examples are the right tool for ambiguous judgment — which of two similar tools to pick, when to escalate. They are the wrong tool for a rule that must hold 100% of the time, because they still leave the decision with the model.
Still a request. Tool descriptions shape selection, and a better description may help — but nothing about a description prevents a call. The model reads it and decides.
Emphasis is a budget, not a mechanism. Capitalising a rule raises its priority relative to quieter rules nearby. It does not turn guidance into enforcement, and spending emphasis here devalues it everywhere else.

Match the mechanism to the tolerance. A rule with a tolerable failure rate can live in a prompt. A rule with a zero tolerance has to live in code that runs whether the model cooperates or not.

2:45 p.m. · The event list

Where hooks attach

Hooks are callbacks the SDK fires at fixed points in the loop. The Python HookEvent values:

  • PreToolUse — before a tool executes. The enforcement primitive; it can block.
  • PostToolUse — after a tool returns. Where transformation lives.
  • PostToolUseFailure — when a tool execution fails.
  • UserPromptSubmit — when a prompt is submitted.
  • Stop / SubagentStop — when the agent, or a subagent, wants to end its turn. You may refuse.
  • SubagentStart — when a subagent begins.
  • PreCompact — before compaction.
  • Notification, PermissionRequest — notification events and permission decisions.

The TypeScript SDK supports additional events beyond this list.

Registering one

from claude_agent_sdk import ClaudeAgentOptions, HookMatcher

verified = set()

async def require_identity(input, tool_use_id, context):
    name = input["tool_name"]
    if name == "mcp__support__get_customer":
        verified.add(input["session_id"])
        return {}
    if name in ("mcp__support__lookup_order", "mcp__support__process_refund"):
        if input["session_id"] not in verified:
            return {"hookSpecificOutput": {
                "hookEventName": "PreToolUse",
                "permissionDecision": "deny",
                "permissionDecisionReason":
                    "Identity not verified. Call get_customer first.",
            }}
    return {}

options = ClaudeAgentOptions(
    hooks={"PreToolUse": [HookMatcher(matcher=None, hooks=[require_identity])]}
)
import { query } from "@anthropic-ai/claude-agent-sdk";

const verified = new Set<string>();

const requireIdentity = async (input: any) => {
  const name = input.tool_name;
  if (name === "mcp__support__get_customer") {
    verified.add(input.session_id);
    return {};
  }
  if (["mcp__support__lookup_order", "mcp__support__process_refund"].includes(name)) {
    if (!verified.has(input.session_id)) {
      return { hookSpecificOutput: {
        hookEventName: "PreToolUse",
        permissionDecision: "deny",
        permissionDecisionReason:
          "Identity not verified. Call get_customer first."
      }};
    }
  }
  return {};
};

const options = {
  hooks: { PreToolUse: [{ hooks: [requireIdentity] }] }
};

A matcher has three parts: matcher (a tool name or pattern like "Bash" or "Write|Edit" — omit it to match everything), hooks (the callbacks), and timeout in seconds. Timeout defaults: 600 seconds for most events, 30 for UserPromptSubmit.

Every hook input carries session_id, transcript_path, cwd, and optionally permission_mode. A PreToolUse input adds tool_name, tool_input, tool_use_id, and — when it fires inside a subagent — agent_id and agent_type.

3:15 p.m. · Dana’s date problem

Which direction does the hook face?

Northstar’s tools were written by three teams over four years. get_customer returns Unix epoch timestamps. lookup_order returns ISO 8601. The legacy warehouse tool returns MM/DD/YYYY. The agent now reasons about “which happened first” and gets it wrong often enough that Dana has stopped trusting the timeline in every summary.

“I’m not rewriting a fifteen-year-old warehouse service so a chatbot can read a date.”

Where does the normalization go?

Too early. PreToolUse fires before the tool runs, so the data you want to normalize does not exist yet. It can rewrite the call’s arguments — not its results.
Correct. PostToolUse intercepts tool results and transforms them before the model processes them. The model never has to reconcile three formats because it only ever sees one. If a question says “different tools return inconsistent formats,” this is the answer.
Wrong layer. tool_choice controls whether and which tool the model calls. It has nothing to do with the shape of what comes back.
Probabilistic, and wasteful. You’d be spending context and model attention on parsing work that three lines of deterministic code do perfectly, every time. Save the model’s judgment for things that need judgment.
PreToolUse guards what goes out. PostToolUse cleans what comes back.Direction is the whole distinction.

The two write operations

  • PreToolUse → updatedInput, placed directly under hookSpecificOutput, replaces the tool’s arguments before it runs.
  • PostToolUse → additionalContext pushes a string into Claude’s context, wrapped in a system reminder and placed next to the tool result. Capped at 10,000 characters; longer output is written to a file and replaced with a preview and path.

3:50 p.m. · The five-hundred-dollar line

Blocking and redirecting

Finance sets a rule: no automated refund above $500. Over that, a human decides. Dana wants the agent to hand off cleanly rather than just fail.

Which pattern?

Correct. A PreToolUse hook reads tool_input, sees the amount exceeds the threshold, and returns permissionDecision: "deny" with a reason that tells Claude to escalate instead. The reason string matters — it is how the block becomes a redirect rather than a dead end.
Too late by definition. PostToolUse fires after the refund has been issued. “Reversing” it means a second financial transaction, a reconciliation problem, and a customer who saw money move twice.
A rule with money attached needs zero tolerance. Few-shot examples shape judgment in ambiguous cases; a hard threshold is not ambiguous. This is the same mistake as the 12% verification problem, with a larger blast radius.
Guidance, not a gate. And in a shipped product with settingSources: [], the file isn’t even loaded — so the rule would silently not exist.

Decision control, by event

EventsPatternKey fields
PreToolUsehookSpecificOutputpermissionDecision: allow / deny / ask / defer, plus permissionDecisionReason
PostToolUse, PostToolUseFailure, UserPromptSubmit, Stop, SubagentStop, PreCompacttop-level decisiondecision: "block" with a reason
PermissionRequesthookSpecificOutputdecision.behavior: allow / deny
SessionStart, SubagentStartcontext onlyadditionalContext — no blocking
Notification, SessionEnd, PostCompact, InstructionsLoadednoneSide effects only — logging, cleanup

The fourth permissionDecision value is the interesting one: "defer" ends the run with stop_reason: "tool_deferred" and the pending call in deferred_tool_use. That is how you surface “a human needs to approve this refund” in Northstar’s own UI and resume the same session once someone clicks.

For shell-command hooks (the kind defined in settings files rather than SDK callbacks), exit code 2 blocks the action and feeds stderr back to Claude, which reads it and adapts. Stderr from a hook that exits 0 goes to the debug log only — Claude never sees it. If a hook seems to be doing nothing, check its exit code before you check its logic.

4:20 p.m. · The callback that doesn’t fire

canUseTool is not a gate

Toby has already built something that looks like enforcement: a canUseTool callback that inspects every call and approves or denies it. He is confident the refund rule is covered. It is not, and the reason is subtle enough that it is worth slowing down for.

canUseTool is the SDK’s replacement for the interactive permission prompt. It fires only when the permission flow resolves to a prompt. Calls already approved never reach it — and Toby’s config auto-approves the support tools, because otherwise the agent would stall on every ticket.

You need a check that runs on every single tool call, unconditionally.

You’d be trading one failure for another. Removing the auto-approvals does route everything through canUseTool — and also makes every ticket wait on a permission decision, which is the stall you were avoiding. The docs are explicit: to gate every tool call, use a PreToolUse hook.
Correct. A PreToolUse hook fires on every tool call regardless of how permission was resolved. canUseTool is the doorbell — it rings only when someone would have had to answer the door. The hook is the doorframe; everything passes through it.
Changes who decides, not whether you inspect. dontAsk denies anything not pre-approved instead of prompting. Pre-approved calls still sail through uninspected, so your business rule still isn’t evaluated.
Blunt. disallowedTools blocks calls unconditionally — you don’t want no refunds, you want refunds that satisfy a condition. That requires inspecting the arguments, which only a hook does.

The exceptions worth knowing: AskUserQuestion, MCP tools marked requiresUserInteraction, and connector tools an organization set to ask reach canUseTool even when an allow rule matches. In dontAsk mode those are denied outright instead. A canUseTool callback returns either { behavior: "allow", updatedInput?, updatedPermissions? } or { behavior: "deny", message, interrupt? }.

4:45 p.m. · The word “allowed”

Six modes, and one badly-named option

ModeBehavior
defaultStandard prompting behavior
acceptEditsAuto-accept file edits
planRead-only — explore and propose without editing
dontAskNever prompt; deny anything not pre-approved
bypassPermissionsSkip checks (explicit ask rules still prompt). Requires allowDangerouslySkipPermissions: true
autoA model classifier approves or denies what would have been prompts

For an unattended production agent, dontAsk is usually right: there is no human to answer a prompt, and you would rather a surprise call be denied than silently permitted.

Lila writes allowedTools: ["Read", "Grep", "Agent"] and tells Dana the agent can only read files. Is she right?

The single most common misreading of the option. The name promises a whitelist; the behavior is an auto-approve list.
Correct. allowedTools auto-approves the listed tools without prompting. Unlisted tools are not blocked — they fall through to permissionMode and canUseTool. To actually restrict, use disallowedTools.
Close, and worth understanding. plan mode would make it read-only, but that’s the mode doing the work, not allowedTools. Lila’s claim is wrong on its own terms.
Not the distinction. Subagent tool restriction is a separate mechanism — AgentDefinition.tools — but allowedTools fails to restrict for the main agent too.

How you actually block

  • disallowedTools: ["Bash"] — the bare name removes the tool from Claude’s context entirely.
  • disallowedTools: ["Bash(rm *)"] — a scoped rule leaves Bash available and denies matching calls in every permission mode, including bypassPermissions.

Read the three options as a sentence: allowedTools says “don’t ask me about these,” disallowedTools says “never do these,” and permissionMode says “here’s what to do about everything else.”

5:15 p.m. · Kenji’s tools

MCP servers that don’t leave the process

Northstar’s four support tools have to live somewhere. Section 6 taught you to build an MCP server as a separate process talking over stdio. Inside a product, that means another deployable, another lifecycle, another thing that can be down at 3 a.m.

createSdkMcpServer() builds an MCP server that runs in the same process as your application — no subprocess, no transport, no separate deployment.

from claude_agent_sdk import tool, create_sdk_mcp_server

@tool(
    "lookup_order",
    "Look up an order by ID. Accepts a 12-character alphanumeric "
    "order ID (e.g. NS4417XQ2210), not an email or order name. "
    "Returns status, line items, and refund eligibility. "
    "If you only have an email address, call get_customer first.",
    {"order_id": str},
)
async def lookup_order(args):
    return {"content": [{"type": "text", "text": await fetch(args["order_id"])}]}

support = create_sdk_mcp_server(name="support", tools=[lookup_order])
import { tool, createSdkMcpServer } from "@anthropic-ai/claude-agent-sdk";
import { z } from "zod";

const lookupOrder = tool(
  "lookup_order",
  "Look up an order by ID. Accepts a 12-character alphanumeric order ID " +
    "(e.g. NS4417XQ2210), not an email or order name. Returns status, line " +
    "items, and refund eligibility. If you only have an email address, " +
    "call get_customer first.",
  { orderId: z.string() },
  async ({ orderId }) => ({
    content: [{ type: "text", text: await fetch(orderId) }]
  }),
  { annotations: { readOnlyHint: true } }
);

const support = createSdkMcpServer({ name: "support", tools: [lookupOrder] });

tool() has a different shape in each language — worth noticing if you switch the toggle above. In TypeScript it is a function, tool(name, description, inputSchema, handler, extras?), taking a Zod schema and the handler as its fourth argument. In Python it is a decorator, @tool(name, description, input_schema, annotations?), where the decorated async def is the handler and the schema is a simple type map like {"order_id": str} (or full JSON Schema when you need real validation).

The extras argument is TypeScript-only, carrying annotations, a searchHint one-liner shown in the deferred-tool list when tool search is active, and alwaysLoad: true to keep a tool’s full schema in the initial prompt instead of deferring it. Python passes annotations as its fourth positional argument instead. Both return {"content": [{"type": "text", …}]}, and both reference their tools as mcp__<server>__<tool> in allowedTools.

ToolAnnotations are hints, not security controls — the spec says clients should not rely on them for security decisions. Note the two defaults that surprise people: destructiveHint defaults to true and openWorldHint defaults to true, while readOnlyHint and idempotentHint default to false. The safe assumption is baked in.

The description is the interface

Two weeks in, Dana reports the agent keeps calling get_customer for order-status questions and lookup_order for account questions. Roughly a coin flip on which it picks.

First fix?

A whole component to fix a paragraph. You’ve added a service to maintain, a latency hop, and a second thing that can be wrong — without touching the actual cause.
Correct. The description is the primary mechanism the model uses to select a tool, so a thin description is the root cause and expanding it is the low-effort, high-leverage fix. Name the input format, give example queries, state the edge cases, and say explicitly where each tool’s boundary is.
Discards a real distinction. One tool doing two jobs pushes the ambiguity into the arguments, where it’s harder to see and harder to validate.
The exam’s designated distractor. Few-shot examples add tokens to every request and treat the symptom. Fix the descriptions first; reach for examples when genuine ambiguity survives good descriptions.

Two wiring options worth remembering. strictMcpConfig: true uses only the servers you passed in mcpServers, ignoring project .mcp.json, user settings, plugin servers, and claude.ai connectors — the same reproducibility instinct as settingSources: []. And toolAliases maps a built-in tool name to an MCP tool, so { Bash: 'mcp__workspace__bash' } makes Claude call yours instead of the built-in.

5:40 p.m. · What a failure should say

Three fields, one of which is real

The refund tool fails four different ways: the payment provider is briefly down, the order ID is malformed, the order is outside the 30-day window, and the account is locked. Today all four return "Operation failed". The agent retries all four, identically, and gives up on all four.

The fix is a structured error, and the exam has vocabulary for it — but you should know which parts are protocol and which are your own design:

FieldStatusWhat it does
isErrorA real MCP fieldSignals that a tool call failed.
errorCategoryYour conventionClassifies the failure — transient, validation, business, permission — so the agent can pick a recovery instead of guessing from prose.
isRetryableYour conventionWhether the operation can safely be retried at all.

Applied to the four failures: the provider outage is transient and retryable. The malformed ID is validation and not retryable — but fixable, so say what the format should be. The 30-day window is business and not retryable; isRetryable: false on a business error means “don’t retry, explain the rule.” The locked account is permission and belongs with a human.

Learn these as vocabulary, not as API. The exam glossary names errorCategory and isRetryable as if they were fields you look up, and questions will use them by name — but they’re fields you put in your own error payload. Only isError is part of MCP. Don’t go hunting for the other two in the SDK types.

An error message is an instruction to the agent. “Operation failed” tells it nothing, so it does the only thing it can: retry, then quit. Name the category and the retryability and the same model recovers intelligently with no prompt change at all.

6:05 p.m. · Two ways forward

Resume, or branch

Last thing. Northstar wants to test two escalation policies — aggressive versus conservative — against the same hundred-ticket analysis the agent has already done. That analysis was expensive and neither Rosa nor the budget wants it run twice.

OptionEffect
resume: "<id>"Resume a specific session by ID
continue / continue_conversationContinue the most recent conversation
forkSession / fork_sessionWith resume: branch to a new session ID instead of continuing the original
resumeSessionAtResume at a specific message UUID
persistSession: falseDon’t write to disk — the session can’t be resumed later

Two policies, one shared baseline. Which?

They’d contaminate each other. Resuming twice appends both explorations to one timeline, so the second policy is evaluated by an agent that already read everything about the first.
Correct. Forking creates an independent branch from a shared baseline, which is exactly “explore divergent approaches from the same starting context.” Both branches inherit the expensive analysis; neither sees the other. Note it only means something alongside resume — there has to be a session to fork from.
Wrong tool. Compaction reduces context within one session. It doesn’t create the two independent branches this comparison needs.
Correct isolation, wrong price. You’d get clean branches by paying for the hundred-ticket analysis twice — which is the specific cost forking exists to avoid.

Alongside these: listSessions(), getSessionMessages(), renameSession(), and tagSession() for managing what’s accumulated, and sessionStore to mirror transcripts to an external backend so any host can resume them.

6:30 p.m. · What Rosa needs to sign off

Evidence, not assurance

Three last disciplines, each one an answer to a question the exam asks in scenario form.

Make the check a condition, not a request

A Stop hook fires when the agent wants to end its turn, and can return decision: "block" with a reason. That turns “did you confirm the refund posted?” from a question you might forget to ask into a condition the agent cannot end its turn without satisfying.

Escalation is judgment — teach it with examples

Northstar’s agent hits 55% first-contact resolution against an 80% target: it escalates cases it could have handled and pushes on cases it should have handed off. That is not a tool-wiring problem or a model-capacity problem, and no hook fixes it. Add explicit escalation criteria to the system prompt with few-shot examples demonstrating them. This is the one place today where few-shot examples are the right answer — because the failure is genuinely a judgment call, not a rule.

Distrust the average

The evaluation reports 97% accuracy. Dana reports that every ticket forwarded from the legacy warehouse system comes back wrong. Both are true: an aggregate can hide a category that fails nearly always, if the category is small enough. Evaluate per category, not just in total.

Rosa, finally: “Alright. Not because it’s smart. Because I can see what it can’t do.”

And manage the window

Compaction happens automatically; PreCompact fires before it and a compact-boundary message appears in the stream. But delegation is still the primary context lever — an Explore-style subagent keeps a verbose multi-phase discovery from exhausting the main window, because the findings come back as a summary and the fifty files don’t come back at all.

Past a few delegated tasks per turn, the Workflow tool moves orchestration into a script the runtime executes outside the conversation context — the right shape when a run coordinates dozens to hundreds of agents rather than three.

The architect’s pocket card

On Monday Dana asks how you decided so fast. You answer:

Ask what the tolerance is. A rule that can fail sometimes lives in a prompt. A rule that must never fail lives in a hook. Twelve percent is not a prompt-engineering problem.

Face the hook the right direction. PreToolUse guards what goes out — deny, rewrite with updatedInput, or defer to a human. PostToolUse cleans what comes back — normalize formats, add context. Stop refuses to let the turn end. And canUseTool is not a gate: it only fires when something would have prompted.

Say what you mean about tools. allowedTools auto-approves, it doesn’t restrict. disallowedTools blocks — bare names remove the tool, scoped rules survive even bypassPermissions. In-process MCP servers keep custom tools inside your application, and the description is the interface: when the model picks wrong, the description was thin.

Make failures informative. isError is real; errorCategory and isRetryable are conventions you owe the agent. A structured error is the difference between a retry loop and a recovery.

Then branch instead of repeating yourself, gate the outcome instead of asking about it, and never trust an average. That is the Agent SDK: not “what can it do?” but “what has been made impossible, and what evidence proves the rest?”
