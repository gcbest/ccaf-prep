The API access flow, in five steps

  1. Client → your server. The client sends the user's text to the developer's server. Never access the Anthropic API directly from a client app — that is how the API key stays secret.
  2. Your server → Anthropic. The server makes the request using an SDK (Python, TypeScript, JavaScript, Go, Ruby) or plain HTTP. Required parameters: API key + model name + messages list + max_tokens limit.
  3. Text generation runs inside the model (four stages — next scene).
  4. The model stops when max_tokens is reached or a special end-of-sequence token is generated.
  5. Anthropic → your server → the client. The response carries the generated text plus usage counts plus a stop_reason; the server passes what the user needs on to the client.

Security memory hook: the client whispers the request to your server; only your server is allowed to flash the API key at the door. Store the key in an environment file that is excluded from version control — hardcoding it in source is the classic way keys leak on GitHub.

9:20 a.m. · Step three, opened up

What happens between “send” and “text”

Theo asks the honest beginner question: what is the model actually doing in those two seconds? Rafael takes it in four stages.

  • Tokenization — the input is broken into tokens: words, parts of words, symbols, spaces.
  • Embedding — each token is converted into a list of numbers representing all the possible meanings that word could carry.
  • Contextualization — those embeddings are adjusted based on neighbouring tokens, pinning down the precise meaning in this sentence.
  • Generation — the output layer produces probabilities for the next word; the model selects one using probability plus randomness, appends it, and repeats the whole process.

Four terms worth keeping crisp: a token is a chunk of text; an embedding is a numerical representation of word meanings; contextualization is meaning refinement using neighbouring words; max_tokens is the generation length limit; stop_reason is why the model stopped generating.

One more field matters to Rafael by lunchtime: response.usage reports input and output token counts. That is what the bill is calculated on.

Chopper, labeller, seasoner, plater. Tokenize, embed, contextualize, generate — and notice that “probability plus randomness” in the last stage is exactly the dial temperature turns.

9:55 a.m. · The first green light

Four setup steps and three required arguments

Rafael sets Rooftop's spike up in a notebook. Install the packages (anthropic and python-dotenv). Create the environment file with ANTHROPIC_API_KEY and add it to version-control ignores. Load it with python-dotenv. Create the client and define a model variable.

message = client.messages.create(

    max_tokens=1000,

        {"role": "user", "content": "Summarize this roof inspection."}

messages is a list of conversation exchanges. A user message is {"role": "user", "content": "..."} — human-authored content. An assistant message holds model-generated content. The full response object carries metadata and a nested structure; message.content[0].text pulls out just the generated text.

The most commonly misread parameter: max_tokens is a safety limit on generation length, not a target length. Setting it to 1000 does not ask Claude for a thousand tokens; it forbids more than a thousand. If you want a specific length, say so in the prompt.

Every request needs a brain, a ceiling, and a conversation envelope — model, max_tokens, messages — plus the API key the client carries for you.

11:40 a.m. · The dial

Two features, two very different needs

Rooftop has a field extractor that pulls measurements and defect codes out of surveyor notes into a fixed record. It also has a marketing endpoint that generates campaign taglines for Northstar's renewal mailers. Nadia asks what temperature each should run at.

Temperature is a parameter from 0 to 1 that controls randomness in generation by influencing token-selection probabilities. At 0, output is deterministic—the highest-probability token is always selected. Higher values increase the chance of selecting lower-probability tokens, producing more creative and unexpected output.

Your call on the field extractor

Right. Low temperature suits data extraction and factual tasks that require consistency. The same note should yield the same record every time.
Hedging. Middle values suit explanation and constrained creativity. An extractor filling a fixed schema wants consistency, so run it near 0 and save the middle of the dial for prose that must vary a little.
Backwards. High temperature is for brainstorming, writing, jokes, and marketing — that is the tagline endpoint. Applied to extraction it just makes your records inconsistent.

The honest caveat: a higher temperature does not guarantee a different output, and a lower one does not guarantee a correct one. Temperature reshapes the probability distribution over next tokens. It is a variability knob, not a quality knob.

Temperature is a spice dial. Zero for the dish you need identical every service; crank it up when surprise is the product.

1:05 p.m. · The spinner

Thirty seconds of nothing

The multi-peril claim summary takes a while. Theo's app shows a spinner for the entire generation, and the field testers assume it has hung.

Response streaming displays the response chunk by chunk as it is generated instead of waiting for the complete message. Claude sends an immediate acknowledgement, then a stream of events each carrying a piece of text, which your server forwards to the frontend in real time.

EventMeaning
message_startInitial acknowledgement — no text yet
content_block_startText generation begins
content_block_deltaContains the actual text chunks — the one that matters most
content_block_stop / message_stopGeneration complete

Three levels of convenience in the Python SDK: client.messages.create(stream=True) returns a raw event iterator; client.messages.stream() with its text_stream property hands you just the text; and stream.get_final_message() reassembles every chunk into the complete message so you can store it.

with client.messages.stream(
    model=MODEL, max_tokens=1000, messages=messages
) as stream:
    for text in stream.text_stream:
        print(text, end="")
    final = stream.get_final_message()

Streaming buys time-to-first-token, not quality. It improves the experience and lets you capture the assembled message for storage. It does not change what Claude produces, and it does not remove the need to handle errors and incomplete output.

Two ways to steer output without touching the prompt

Pre-filling assistant messages. Manually add an assistant message at the end of the conversation. Claude treats it as content it already authored and continues from the exact end of the pre-filled text—not from a fresh sentence. Pre-fill “Coffee is better because” and you get a justification for coffee. You must stitch the pre-fill and the generated continuation together yourself.

Stop sequences. Supply an exact string; the moment Claude generates it, the response halts immediately, and the stop-sequence text is not included in the output. Prompt “count 1 to 10” with a stop sequence of five and you get “one, two, three, four, ” — refine the stop sequence to , five and you get the clean “one, two, three, four”.

Precise control without prompt surgery. Pre-fill steers direction; stop sequences control where it ends; stop_reason tells you which one actually fired.

3:30 p.m. · The photographs and the policy

Rooftop finally sees what the surveyor saw

Every claim arrives as a bundle: a set of roof photographs and the homeowner's policy PDF. Both go into the same messages array.

Images

Claude accepts image content blocks in user messages, holding either base64-encoded data or a URL to an online image. Multiple image blocks are allowed per message, up to 100 images per request, and images consume tokens calculated from pixel height and width—so downscale when full resolution is not needed. Supported formats are JPEG, PNG, GIF, and WebP.

Two ordering habits: when an image and its description share a message, put the image block before the text, and give multiple images clear labels or captions so Claude can refer to “the second image” unambiguously. Claude can also reference images from earlier turns still in context.

The counter-intuitive part: image accuracy depends on prompt sophistication, not image quality. Simple prompts often fail. The course's worked example — automated fire-risk assessment from satellite imagery, scoring tree density, property access, and roof overhang — only works with step-by-step analysis instructions, one-shot or multi-shot examples alternating image and text, explicit guidelines, and verification steps.

PDFs

A PDF goes in as a document block with media type application/pdf—nearly the same code as an image, with the type and media type swapped. Claude reads the extracted text and the visual layout: tables, charts, embedded images, mixed content. That is why it is preferable to pre-extracting text yourself whenever the document's visual structure carries meaning. Page-count and file-size limits apply, and each page bills roughly like an image plus its text.

Citations

Ines's requirement: every claim in a homeowner note must be traceable to the policy. That is citations, opted into per document block.

{
  "type": "document",
  "source": {"type": "base64",
             "media_type": "application/pdf",
             "data": pdf_b64},
  "title": "Northstar HO-3 Policy (2024)",
  "citations": {"enabled": True}
}

The response content then becomes a list of text blocks, some carrying citation arrays with location data. Two location types: citation_page_location for PDFs (document index, title, start page, end page, cited text) and citation_char_location for plain text (character position in the text block). A UI can turn those into hover popups that show the source document, page number, and exact quoted passage.

Citations turn assertion into evidence. They let a user investigate how Claude built a response from source material, instead of it appearing to speak from memory alone.

Everything so far was plumbing. The prompt is the product.Parameters decide what is possible. The prompt decides what is good.

4:10 p.m. · The 2.32

Nadia scores the first prompt and nobody enjoys it

Nadia Kwan runs Rooftop's draft prompt through a scoring pipeline. It comes back 2.32 out of 10. Rafael's face falls; Nadia is delighted, because now there is a number to move.

The improvement cycle is five steps: set a goal → write an initial prompt → evaluate it → apply a technique → re-evaluate, repeating the last two. Each technique should be measurable — track the score before and after.

Technique 1 — being clear and direct

The first line is the most important part of the prompt. Clear means simple language stating exactly what you want, with no ambiguity. Direct means an instruction rather than a question, starting with an action verb: Write, Create, Generate, Identify.

Before: “I was reading about renewable energy… what countries use it?”
After: “Identify three countries that use geothermal energy. Include generation stats for each.”

Technique 2 — being specific

Two kinds of specificity, often combined:

  • Output quality guidelines — list the qualities the output must have: length, structure, tone, elements to include. These control the characteristics of the finished thing.
  • Process steps — explicit steps for Claude to follow. These control how Claude arrives at the answer.

Rooftop's homeowner note has a fixed shape but no tricky reasoning. What do you add?

Correct. Output quality guidelines are recommended for almost every prompt — they are your safety net. A note with a known shape needs its qualities named, not its reasoning route prescribed.
Over-engineering. Process steps earn their place on complex, critical-thinking work — troubleshooting, decision-making, multi-angle analysis — where you want Claude to consider perspectives it might not reach naturally. A straightforward drafting task does not need them.
Half right. Professional prompts do often combine them, but the rule is asymmetric: guidelines in almost every prompt, steps only when the route matters as much as the answer. The multi-peril claims path is where steps belong.

Technique 3 — structure with XML tags

Wrap each content section in a descriptive, custom XML tag. Not data — sales_records. Not stuff — my_code and docs. Descriptive names give Claude context about the nature of the content, not just its boundary.

Draft a homeowner note.

XML tags are most valuable when you are including large amounts of context or data, mixing content types (code plus documentation), or interpolating multiple variables. They stop Claude confusing your instructions with your data, or one data source with another—and they help even for short blocks, because a tag like <athlete_information> signals “this is external input to consider”.

Technique 4 — providing examples

Give Claude sample input/output pairs wrapped in XML tags such as <sample_input> and <ideal_output>. One-shot is a single example establishing a pattern; multi-shot is several, typically covering different scenarios and edge cases.

Examples are strongest for corner cases (sarcasm in sentiment analysis), complex output formats (a specific JSON structure), and exact style or tone. Place them after the main instructions and guidelines. Two refinements do most of the work:

  • Add context explaining why the example output is ideal, not just the pair — this helps Claude generalize the reasoning rather than copying the shape.
  • Mine your highest-scoring eval outputs for examples. Real 10/10 input/output pairs beat invented ones.

A professional prompt is a stack, not a sentence: a clear, direct opening line, then specific guidelines (and steps where warranted), then XML-tagged structure, then one or more high-quality examples with a note on why they are good.

4:55 p.m. · The ship-it meeting

“It works on the three cases I tried”

Rafael has tested the prompt on three real claims and they all read well. He wants to ship. Nadia draws the distinction that runs the rest of the afternoon.

Prompt engineering is the set of techniques for writing and editing prompts so Claude understands the request. Prompt evaluation is automated testing that measures how well a prompt actually performs, using objective metrics — testing against expected answers, comparing versions, reviewing for errors.

Three paths lead out of a first-draft prompt. Which one is Northstar taking?

Path 1 — a trap. It feels like validation and gives no objective measure of performance across the input space. High risk of breaking on unexpected real-world input.
Path 2 — also a trap. Better than path 1, and still the place most engineers stop. Users will keep surprising you, because a handful of hand-picked inputs is not the input space.
Path 3 — the recommended one. More upfront work and cost, much higher confidence. Objective scoring is what lets you A/B two prompt versions and know which is actually better.

The five-step eval workflow

  1. Draft a prompt — your baseline to optimize.
  2. Create an eval dataset — sample inputs representative of production traffic. Hand-written or Claude-generated; three examples or thousands.
  3. Feed through Claude — interpolate each dataset input into the prompt template, send it, collect the outputs.
  4. Feed through a grader — score each output, typically on a 1–10 scale, and average for overall prompt performance.
  5. Change the prompt and repeat — re-run and compare average scores across versions.

Generating the dataset

Use a faster, cheaper model such as Haiku to generate the dataset — dataset generation is not the task being tested. Get clean JSON out with the technique from earlier today: prefill the assistant turn with ```json, set stop_sequences to ["```"], then parse the result and save it to a dataset file.

Keep the dataset small — two or three cases — while you are actively iterating, so each loop is fast; scale up to tens or hundreds for final validation. Include a format field on each test case ("python", "json", "regex") so a code grader knows which validator to apply.

Engineering designs the bridge; evaluation drives test trucks over it. Both are required, and only one of them produces a number.

5:30 p.m. · The grader question

Who decides whether an output is any good?

The eval loop has four moving parts: a dataset, a prompt, an LLM, and a grader. Three small functions hold it together — run_prompt merges a test case into the prompt and sends it; run_test_case calls run_prompt, grades the result, and returns a summary; run_eval loops the dataset and assembles everything. Run against Haiku, a full dataset pass through all three functions takes about 31 seconds — cheap enough to run after every prompt edit. The grader is the part everyone underestimates.

GraderHow it worksGood for
CodeProgrammatic checksLength, keyword presence or absence, syntax validity (JSON / Python / regex), readability scores
ModelAnother Claude call evaluates the outputResponse quality, instruction-following, completeness, helpfulness, safety
HumanManual reviewNuanced quality, comprehensiveness, depth, relevance — most flexible, slowest and most tedious

Rooftop's extractor must emit valid JSON and a note that follows Ines's tone rules. How do you grade it?

Catches half the failures. A code grader will confirm the JSON parses, and cheerfully pass a perfectly-formed record with a cold, wrong-toned note attached. Syntax validity is not instruction-following.
The other half. A model grader judges tone and completeness well, but it is an inconsistent syntax checker. You want a parser deciding whether JSON parses.
Right. Combine them — the course's formula is (model_score + syntax_score) / 2, pairing semantic evaluation with syntax validation so you measure correctness and technical validity at once.
Most flexible, least scalable. Human graders are best for nuanced depth and relevance, but they are slow and tedious, and they cannot run on every commit. Use them to spot-check, not to gate.

Code-based grading

Three validators, each wrapped in try/except, each returning 10 on success and 0 on failure: json.loads for JSON, ast.parse for Python, re.compile for regular expressions. Improve format compliance first by instructing the model to reply with raw code only — no comments, no commentary — and pre-filling the assistant message with a code-block opener plus a stop sequence.

def validate_json(text):
    try:
        json.loads(text)
        return 10
    except Exception:
        return 0

The limitation is built in: a code grader needs to know the expected format, which is exactly why each test case carries a format field.

Model-based grading

Write the grading prompt to request strengths, weaknesses, reasoning, and a score — never a bare number. Without that context, models default to middling scores around 6 regardless of actual quality. Ask for the result as JSON (prefill plus stop sequence again), store score and reasoning per test case, and average across the dataset.

A grader must return an objective signal, and the evaluation criteria are defined upfront, not negotiated after you see the results.

2.32 was never the point

Nadia wires the loose functions into a reusable PromptEvaluator. Four things about it are worth carrying into the exam:

  • max_concurrent_tasks controls parallelism. Start low — around 3 — to avoid rate limits, and raise it once you know the ceiling.
  • generate_dataset(task_description, prompt_inputs_spec, output_file, num_cases) auto-generates a small test set from a description of the task and a spec of the prompt's required inputs.
  • run_evaluation(run_prompt_function, dataset_file, extra_criteria) runs the loop and lets you inject additional grading criteria for this particular prompt.
  • The output is both a numeric score and a formatted HTML report showing per-test-case results — use it to see exactly where and why a prompt is failing, not just that it is.

Rooftop's homeowner-note prompt started at 2.32. Clear and direct instructions moved it. Output guidelines moved it further. XML tags stopped the data bleeding into the instructions. Two examples mined from the highest-scoring runs pinned the tone Ines wanted.

“A low first score is evidence, not failure. The number you report is the improvement, not the baseline.”

Rafael commits the eval dataset alongside the prompt. It is now a regression suite: the next person who edits that prompt will find out immediately whether they made it worse.

Keep the dataset. A prompt without an eval is an opinion. A prompt with a retained dataset is a component you can change safely.

The architect's pocket card

Ines asks how you knew which knob to turn each time. You answer:

Build with primitives, scale on infrastructure, run with control. Pick the model per task — Haiku for speed, Opus for intelligence, Sonnet for balance — and audition the cheapest first against 20–30 examples. Keep the API key on your server, never in a client. Every request needs model, max_tokens, and messages; the API is stateless, so you resend the history yourself. The system prompt governs how, not what. Temperature near 0 for extraction, near 1 for creative work. Stream long responses for time-to-first-token. Read stop_reason before you change anything; steer with prefills and stop sequences; force a tool schema when the output shape must hold. Put the image before the text, the PDF in a document block, and turn citations on when claims must be traceable. Then write the prompt properly: a clear, direct first line, output guidelines in almost every prompt, process steps only for hard reasoning, XML tags around interpolated content, and examples mined from your best real outputs.

And do not ship on three good cases. Build the dataset, run the graders, keep the score, and change the prompt on evidence.
