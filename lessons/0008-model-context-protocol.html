The Northstar adapter

You are the architect. Northstar has been hand-building a connector for every service it touches. Today you stop, and build one thing that every surface can plug into.

8:05 a.m. · The wall of adapters

“I maintain seventeen integrations and I am one person.”

Tomás Reyes, Northstar’s integrations engineer, has pinned a printout to the wall behind his desk. It is a list of every tool schema he has hand-authored this year: GitHub repositories, pull requests, issues, projects. Then Slack. Then the document store. Each one is a JSON schema he wrote, a function he implemented, and a contract he has to keep working when the upstream API changes.

“GitHub alone has repos, PRs, issues, and projects. If I want Claude to answer questions about our GitHub data, I have to write, test, and maintain a tool for every one of those. That’s not a feature. That’s a second job.”

This is the exact problem the Model Context Protocol was designed to solve. MCP is a communication layer that provides Claude with context and tools without requiring developers to write tedious integration code. It does that by shifting tool definition and execution away from your server and onto dedicated MCP servers.

An MCP server is an interface to an outside service. It wraps that service’s functionality into ready-to-use tools and exposes them in a standardized way. Your application connects to the server instead of implementing everything from scratch.

Who writes these servers? Anyone can. In practice the service provider often ships an official implementation — AWS publishing an official MCP server for its own services is the course’s example. The core value is that someone else did the integration work, and it is their job to keep it current.

First principle: MCP does not change what tools are. It changes who does the work of creating them, and moves the maintenance burden from application developers to MCP server maintainers.

9:05 a.m. · Drawing the boxes

Client, server, and the thing in between

You draw the architecture for Tomás. It is two boxes and one arrow, and almost every MCP question reduces to knowing which box does what.

  • An MCP server publishes capabilities. Internally it contains three kinds of component: tools, resources, and prompts.
  • An MCP client is the communication interface between your server and the MCP server. It is your access point to the MCP server’s capabilities, and it handles the message exchange and protocol details.

The critical thing about the client: it never executes anything itself. It is a messenger. Two message-type pairs carry almost all the traffic:

  • ListToolsRequest / ListToolsResult — “what tools do you have?”
  • CallToolRequest / CallToolResult — “run this tool with these arguments, give me the result.”

The full request flow

A user asks, “What repositories do I have?” Here is every hop:

  1. User query arrives at your server.
  2. Your server asks its MCP client for the available tools.
  3. The client sends a ListToolsRequest; the MCP server replies with a ListToolsResult.
  4. Your server sends the query plus the tool list to Claude.
  5. Claude decides to call a tool.
  6. Your server asks the client to run it; the client sends a CallToolRequest.
  7. The MCP server executes the tool — it makes the real GitHub API call.
  8. The result flows back as a CallToolResult, through the client, to your server, to Claude.
  9. Claude formulates the final answer; the user gets it.

Many steps, but each component has exactly one responsibility, and the client abstracts away all the server-communication complexity.

Memory hook: the MCP client is a hotel concierge. It phones the kitchen for you and carries the tray back. It never once cooks the meal.

9:30 a.m. · The wire

“How do the two actually talk?”

Ade Balogun, who is building the Northstar CLI, wants to know what protocol sits between client and server. The honest answer is: whichever one you need. MCP is transport agnostic — client and server can communicate over standard input/output (stdio), HTTP, WebSockets, or other network protocols.

Ade’s first build is a CLI chatbot. The client and the server both run on his laptop, launched by the same command.

Which transport fits Ade’s deployment?

Correct, and it is the common case. The most common MCP setup is client and server running on the same machine, communicating over standard input/output. Nothing needs to cross a network, so nothing should.
Legal, but unnecessary here. HTTP is a supported transport and is the right shape for a remote server you connect to over a network. For two processes on one laptop, stdio is the common and simpler setup.
Also supported, also overkill. WebSockets are one of the protocols MCP can run over, but Ade’s client and server share a machine. The standard local arrangement is stdio.
That is the misconception to unlearn. “Transport agnostic” means precisely that the pairing is not fixed: stdio, HTTP, WebSockets, and others all work. For Ade’s same-machine CLI, choose stdio.

Transport is a deployment decision, not a protocol decision. The same ListTools/CallTool conversation travels over any of them.

MCP standardizes discovery and invocation.The model still decides how to use a tool once the client hands over its schema.

10:20 a.m. · The first two tools

No JSON schemas were harmed

Tomás defines two tools on the document server: one that reads a document’s contents, one that edits it. What surprises him is how little he writes.

@mcp.tool(
    name="read_doc_contents",
    description="Read the contents of a document and return it as a string.",
)
def read_document(doc_id: str = Field(description="Id of the document to read")):
    if doc_id not in docs:
        raise ValueError(f"Doc with id {doc_id} not found")
    return docs[doc_id]

The second tool, edit_document, takes doc_id, old_string, and new_string, validates the document exists the same way, and performs a find-and-replace on its content. Both raise a ValueError when the id is not in the dictionary.

What the SDK gave him for free

  • No manual JSON schema writing — the decorator plus Python type hints plus Pydantic Field() descriptions auto-generate the schema Claude sees.
  • Automatic validation derived from the type hints.
  • Clear parameter descriptions carried straight into the model-facing interface.
  • Natural error handling — Python exceptions integrate directly.
  • Automatic registration — the decorator registers the tool; there is no separate manifest.

The pattern is always the same: decorator → function definition → parameter typing → validation → core logic. And remember the description is not documentation for humans; it is part of the interface Claude reads. It should say when the tool is appropriate and what its errors mean.

11:10 a.m. · The other side of the wire

Ade builds the client

A client implementation has two components. The SDK provides a Client Session — the actual connection to the MCP server, which requires careful resource cleanup when it closes. Ade wraps it in a custom MCP Client class that owns connect, cleanup, and the async enter/exit lifecycle, and exposes the server’s functionality to the rest of the codebase.

async def list_tools(self) -> list[types.Tool]:
    result = await self.session().list_tools()
    return result.tools

async def call_tool(self, tool_name: str, tool_input: dict) -> types.CallToolResult | None:
    return await self.session().call_tool(tool_name, tool_input)

That is the entire discovery-plus-execution surface the rest of the application needs. The flow through it: the app requests a tool list for Claude → list_tools() returns the server’s tools → Claude selects one and supplies parameters → call_tool() executes it on the server → the result goes back to Claude.

Ade tests it by running the client file directly with a small harness to confirm the connection opens and the tools list. Then he runs the CLI and asks, “what is the contents of the report.pdf document.” Claude calls the tool. It works.

Why wrap the session: the Session is the live electrical wire. The wrapper is the electrician who insulates it and remembers to turn it off. Wrapping the session in a larger class is the common practice, not a stylistic flourish.

11:40 a.m. · The most important table in the room

Three primitives, three owners

An MCP server exposes exactly three kinds of primitive. The thing that distinguishes them is not what they can do — it is who decides when they run.

PrimitiveWhat it isControlled byUse it when
Tools An action Claude can invoke, with a schema and arguments The model — Claude decides when to call it You need to give Claude a new capability it uses autonomously (e.g. “calculate the square root of 3” → Claude reaches for a code-execution tool). Tools serve the model.
Resources Read-only data behind a URI, returned with a MIME type Your app — application code decides when to fetch You need data inside your application, to populate UI (autocomplete lists, document listings) or to inject context into a prompt — the model of Claude’s own “Add from Google Drive.” Resources serve the app.
Prompts A tested instruction template that resolves to messages The user — triggered by an explicit action You want a predefined, optimized workflow a user starts on demand — a slash command, a menu item, a chat-starter button. Prompts serve your users.

Now the first drill. Ade wants an @-mention menu in the CLI: type @, see the list of available documents, pick one, and have its content go into the prompt.

Which primitive?

Exactly right. The application decides when to fetch the list and when to fetch the chosen document — the model is not involved in that decision. That is the defining trait of a resource. And because the app injects the content directly, Claude never has to make a tool call and wait for the round trip.
It would work, and it would be slower and clumsier. Making this a tool hands the decision to Claude and costs an extra round trip: Claude must decide to fetch, call, and wait. The app already knows which document the user picked. Use a resource and put the document on Claude’s desk before the meeting.
Wrong primitive for the job. Prompts are user-triggered instruction templates — they produce messages, not data for your UI. Populating an autocomplete list and injecting the selected content is app-controlled data retrieval, which is a resource.

Say it as a chant: the model pulls the lever, the app sets the table, the user presses the button — tool, resource, prompt.

12:15 p.m. · Two mailboxes

Defining resources

Resources expose read-only data; tools perform actions. A resource follows a plain request/response pattern: the client sends a ReadResourceRequest with a URI, and the server returns a ReadResourceResult. There are two shapes.

# Direct — static URI, no parameters
@mcp.resource("docs://documents", mime_type="application/json")
def list_docs() -> list[str]:
    return list(docs.keys())

# Templated — parameterized URI, params become kwargs
@mcp.resource("docs://documents/{doc_id}", mime_type="text/plain")
def fetch_doc(doc_id: str) -> str:
    if doc_id not in docs:
        raise ValueError(f"Doc with id {doc_id} not found")
    return docs[doc_id]

The mime_type is a hint telling the client how to parse or display the response — application/json, text/plain, application/pdf, and so on. The SDK auto-serializes the return value, so nothing needs manual JSON-stringifying. Both shapes are testable in the Inspector, which lists Resources and Resource Templates separately.

Tomás asks whether he could collapse both into one URI that returns the list when called bare and a document when given an id.

Should he?

Yes. The recommended pattern is one resource per distinct read operation — “list all documents” at docs://documents, “fetch one document” at docs://documents/{doc_id}. Each URI keeps a single-purpose, predictable contract.
Clever, and wrong. Overloading one URI with two behaviors makes its contract ambiguous for every client that consumes it. One key per lock: the lobby key that lists the mailboxes should not also open apartment 4B.
That gives away the advantage. A tool hands the fetch decision to the model and adds a round trip. The whole point of using resources here is that the application already knows what it wants and can inject it directly. Keep two resources.

Design note: keep resources least-privilege. They are a read surface, so expose the narrowest read that satisfies the use case.

1:00 p.m. · Reading from the other side

The client fetches a resource

Ade adds the mirror-image method to his client wrapper.

async def read_resource(self, uri: str) -> Any:
    result = await self.session().read_resource(AnyUrl(uri))
    resource = result.contents[0]
    if isinstance(resource, types.TextResourceContents):
        if resource.mimeType == "application/json":
            return json.loads(resource.text)
    return resource.text

Two details carry all the weight. The result’s contents is a list, and you typically use only the first element. And the mimeType on that element is what tells you how to parse it: application/json goes through json.loads(); anything else is returned as raw text. The MIME label is the package’s handling sticker.

In the CLI, typing @ now triggers an autocomplete list of resources. Ade’s document picker uses arrow keys to navigate and the space bar to select. The moment a document is chosen, its contents are pulled in and included in the prompt sent to Claude — no tool call, no extra round trip. Claude never has to leave the room to fetch the file.

This is the real-world parallel worth remembering: Claude’s own “Add from Google Drive” works this way. Application code — not the model — decides which documents to show and injects the content. App-controlled context is a resource.

1:35 p.m. · The tested instruction

“Users can already just ask. Why write a prompt?”

Renata pushes back. A user can type “reformat report.pdf in markdown” today. Why would the server author bother shipping a prompt for it?

Because a thoroughly tested, specialized prompt written by the people who built the server gets more consistent, higher-quality results than every user inventing their own instruction. The prompt is where domain expertise gets encoded once.

@mcp.prompt(
    name="format",
    description="Rewrites the contents of the document in Markdown format.",
)
def format_document(
    doc_id: str = Field(description="Id of the document to format"),
) -> list[base.Message]:
    prompt = f"""Your goal is to reformat a document to be written with
markdown syntax. The id of the document you need to reformat is:
<document_id>{doc_id}</document_id>
Add in headers, bullet points, tables, etc as necessary."""
    return [base.UserMessage(prompt)]

The function returns a list of messages sent directly to Claude — it can contain multiple user and assistant messages for more complex flows. It is not a suggestion; it is a pre-written boarding pass that Claude reads and acts on.

Users trigger prompts through explicit UI actions: / slash commands, menu selections, button clicks. Never automatically.

Renata now wants a one-click control under the chat input labelled “Reformat this document,” which runs Northstar’s tested markdown workflow.

Which primitive?

Correct. A predefined workflow that a user starts by an explicit action is the definition of an MCP prompt. Claude’s own chat-starter buttons are the canonical example. The button is a vending-machine button: the user pushes it and gets the prepacked workflow.
Wrong controller. Tools are model-controlled — Claude decides when to call them. Renata is describing something the user deliberately fires. That is a prompt. (Note the prompt will likely cause Claude to use the read and edit tools; the two cooperate.)
Wrong layer. Resources return read-only data for your app; they do not carry instructions. A tested set of instructions, fired by a user action, is a prompt.

Four benefits of server-authored prompts: consistency (same reliable results every time), encoded expertise (domain knowledge baked in once), reusability (every client of the server inherits them), and single-point maintenance (improve once, all clients improve).

2:10 p.m. · Wiring the slash command

Prompts in the client

The client side is the same discovery-then-invoke gesture as tools, just aimed at a different drawer.

async def list_prompts(self) -> list[types.Prompt]:
    result = await self.session().list_prompts()
    return result.prompts

async def get_prompt(self, prompt_name, args: dict[str, str]):
    result = await self.session().get_prompt(prompt_name, args)
    return result.messages

The arguments the client supplies — say {"doc_id": "plan.md"} — become keyword arguments on the server’s prompt function and get interpolated into the template text. What comes back is a messages array that forms the conversation input for the model.

End to end in Ade’s CLI: the user types /format → picks a document → the client calls get_prompt("format", {"doc_id": ...}) → the server returns the resolved messages → the client sends them to Claude → Claude uses the read_doc_contents and edit_document tools to fetch, reformat, and save the document.

“Same doorbell, different room. Press it for the tools closet or the prompts drawer — it is the identical ‘what have you got’ gesture either way.”

2:45 p.m. · The drill, one more time

Three capabilities, three answers

Hannah Whitlock, Northstar’s security reviewer, joins the room and does what security reviewers do: she asks you to classify things before she signs anything off. Northstar’s analytics team wants Claude to be able to run arbitrary arithmetic — square roots, regressions — by executing code in a sandbox, entirely on its own initiative, whenever a question needs it.

Which primitive?

Yes — and note why. Not because it executes code, but because the decision to invoke belongs to the model. Claude spontaneously reaching for the calculator is the defining trait of a tool. This is the course’s own example: code execution for calculations is model-controlled.
No — resources are read-only data. They do not perform actions, and the fetch decision belongs to your app, not to Claude. Autonomous execution by the model is a tool.
No — prompts are user-triggered. Nobody is pressing a button here; Claude decides on its own, mid-answer, that it needs to compute something. Model-decided invocation means tool.

The decision guide, compressed: need to give Claude a new capability → tool. Need data into your app for UI or prompt context → resource. Want a predefined, user-triggered workflow → prompt. Each primitive serves a different layer of your stack.

3:20 p.m. · Forty tools and one worried reviewer

Connecting a server from the Claude API

Northstar also wants Claude to reach the company Slack. There is an existing MCP server for it, and connecting from the Claude API takes two pieces in the request:

  • mcp_servers — declares the connection: type, URL, name, and an optional authorization_token.
  • A tool entry with "type": "mcp_toolset" and "mcp_server_name": "..." — this grants access. The default is all tools on that server.

Claude introspects the server itself and discovers the available tools and schemas, so you never write a tool schema by hand for an MCP-provided tool. (As of the course, the MCP connector required a beta header.)

Hannah has counted. The Slack server exposes about forty tools, and some of them post messages and delete things.

“I am not signing off on a configuration where the blast radius is ‘whatever the vendor decided to ship this quarter.’”

How do you limit the blast radius?

Right shape. Set "default_config": {"enabled": False}, then turn on only what you need in configs — e.g. search_messages and list_channels. That keeps the server effectively read-only: search and list allowed, post and delete blocked. Deny-by-default means next quarter’s new tool arrives disabled.
Fails on the next release. An allow-everything-minus-a-blocklist config silently admits every tool the vendor adds later. Disable everything by default and enable specific tools instead.
Instructions are not a permission boundary. If a destructive tool is exposed, it is callable. Scope it out in the configuration — default_config disabled, named tools enabled — rather than asking politely in the system prompt.
You just re-created the problem MCP solved. Forking means you now maintain the integration you connected to a server to avoid. The connector supports per-tool enablement; use it and let the provider keep maintaining the server.

Same idea, one layer up: Claude Code has an embedded MCP client, and servers are added with claude mcp add [server-name] [startup-command]. Restart, and the new capabilities are live — Sentry, Jira, Slack, or your own. Every server you add widens the surface, so add deliberately.

4:30 p.m. · Sign-off

Hannah’s conditions

Hannah will approve the document server, on conditions. They read like a design checklist, because that is what good MCP server design is.

  • Keep tools narrow. One clear job each, with a predictable return value.
  • Make descriptions specific. The description is a model-facing interface: say when the tool applies, what it returns, and what its errors mean.
  • Validate inputs. Type hints and Field() give you validation for free; existence checks and ValueError give the model a meaningful failure instead of a crash.
  • Keep resources least-privilege. Expose the narrowest read that satisfies the use case.
  • Make prompts explicit about the expected output. A tested prompt that does not state its output shape is only half-tested.
  • Version or deprecate; never silently redefine. If a capability’s meaning changes, ship a new one and retire the old one deliberately, so clients can adapt.

Then the permission point, which is the one people get wrong. Connecting a server does not dissolve the underlying system’s access control, and exposing a server’s tools to Claude is a decision you make per tool. A connector is an office badge, not a skeleton key — and the badge you issue should open the fewest doors that let the job get done.

And the boundary on your own confidence: a green run in the Inspector proves the protocol works. It does not prove the application’s permissions and business rules are correct. Those are verified where they live — in the application.

Hannah signs. Tomás takes the printout of seventeen hand-written integrations off the wall.

The architect’s pocket card

MCP moves integration work off your plate. A server wraps an outside service and exposes ready-made tools, resources, and prompts; a client is the messenger that lists and invokes them and never executes anything itself. The traffic is ListToolsRequest/ListToolsResult then CallToolRequest/CallToolResult, over any transport — stdio for the common same-machine case, HTTP or WebSockets otherwise.

Three primitives, three owners. Tools are model-controlled and serve the model. Resources are app-controlled, read-only, URI-addressed, MIME-typed, and serve your app. Prompts are user-controlled instruction templates that resolve to messages and serve your users. New capability → tool. Data for UI or prompt context → resource. User-triggered workflow → prompt.

Build it with FastMCP. Decorators plus type hints plus Field() descriptions replace hand-written JSON schemas. Test with mcp dev in the Inspector, where state persists between calls — but treat that as a protocol check, not proof of your permissions. Implement the side you own; the course builds both only to show the whole loop.

Connect it carefully. From the API, mcp_servers plus an mcp_toolset entry grants access to all tools by default; disable everything and enable named tools to keep a server read-only. Tools are for your stuff, Skills are for your processes, MCP is for everyone else’s.
