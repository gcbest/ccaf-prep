8:05 a.m. · The demo that went nowhere

“It writes lovely paragraphs about a database it cannot see”

Northstar Assist shipped last month on the Claude API. Overnight, three tickets arrive with the same shape. A customer asks about their order. A rep asks what time it is in the Lisbon office. The ops team asks Assist to actually set a reminder, and Assist replies, warmly, that it would be happy to — and then does nothing at all.

Dara Osei, the backend engineer who built the endpoint, puts it plainly at standup.

“By default, Claude only knows what was in its training data. No live data, no current time, no side effects. Everything we shipped is a very articulate closed room.”

Tool use is the door. The flow has five beats, and once you see them you will see them everywhere for the rest of this lesson:

  1. Send a message to Claude with tools available.
  2. Claude responds with either a final answer or a tool-use request.
  3. Your code executes that tool.
  4. You send the result back to Claude as a tool_result block.
  5. Repeat until stop_reason is end_turn.

Run that loop autonomously — Claude receiving a goal, picking tools, and continuing until it decides the task is finished — and you no longer have a chatbot. You have an agent: an autonomous version of Claude running both sides of the messaging loop without a human in the middle.

Division of labour, stated once and never renegotiated: you own the loop and the tools; Claude owns the reasoning. Claude never touches your database. It writes a request; your code decides whether and how to honour it.

First principle: a tool does not give Claude new abilities so much as it gives Claude a way to ask for something. Every capability you add is a request you have agreed in advance to fulfil.

8:40 a.m. · Three ordinary functions

The tool nobody called

Dara starts with the reminder feature, and finds it needs three tools, not one. Claude knows roughly what today's date is but not the exact time; it sometimes miscalculates date arithmetic across long spans; and it has no mechanism at all for storing a reminder. So: get_current_datetime, add_duration_to_datetime, set_reminder.

The functions themselves are plain Python. What makes them tools is three habits: descriptive function and argument names, immediate input validation, and error messages that mean something — because the error text goes back to Claude, which can read it and retry with corrected parameters.

Then each function needs a tool schema: a JSON Schema description with exactly three parts.

{
  "name": "get_current_datetime",
  "description": "Returns the current date and time. Use this
    whenever a request depends on 'now' — scheduling, elapsed
    time, or relative dates. Returns a formatted string in the
    requested strftime format.",
  "input_schema": {
    "type": "object",
    "properties": {
      "date_format": {"type": "string",
        "description": "strftime format, e.g. %Y-%m-%d %H:%M:%S"}
    }
  }
}

input_schema is ordinary JSON Schema — a general data-validation spec, not an AI invention, borrowed by the ML community for tool calling. The convention is to name each schema <function_name>_schema so it pairs obviously with its function, and you can hand your function to Claude and ask it to draft the schema for you. One Python-SDK detail worth keeping: import ToolParam from anthropic.types and wrap each schema dict in ToolParam(...) before adding it to the tools list — skip that and you'll chase type errors that have nothing to do with the schema's actual content.

10:00 a.m. · The loop, written down

“What day is 103 days from today?”

One question, two tools, in order: Claude calls get_current_datetime, reads the result, then calls add_duration_to_datetime, then answers. Nobody told it that sequence. It worked it out.

You cannot predict how many tools a query will need, so the loop has to handle chains of arbitrary length. Dara's three functions do exactly that:

  • run_conversation — calls Claude with the messages plus the tools, appends the assistant response to history, checks stop_reason; if it isn't tool_use, break; otherwise run the tools, append the results as a user message, and loop.
  • run_tools — filters the content array for blocks of type tool_use, executes each one, and builds a tool_result block per request, wrapping execution in try/except so a failure comes back as is_error: true with the error message as content rather than crashing the loop.
  • run_tool — a plain dispatcher matching tool name to function.

Adding the third tool takes three edits and nothing else: put the schema in the tools list, add a case to the dispatcher, write the function. That is the whole extension story.

The helpers need one refactor first. add_user_message and add_assistant_message must accept multiple blocks instead of plain strings, chat must accept a tools argument and return the entire message rather than the first text block, and a small text_from_message helper pulls out every text block for display.

The loop is boring on purpose. Call → check stop_reason → dispatch → return results → repeat. Everything clever in an agent lives in the tools and their descriptions, not in the while loop.

3:35 p.m. · Nine hundred pages of policy

“Just put the manual in the prompt”

Lila Novak, who owns Northstar's knowledge base, has 900 pages of support policy and a simple proposal: paste it into the system prompt. Dara lists what goes wrong — hard length limits, degraded effectiveness on very long prompts, higher cost, slower processing.

RAG — Retrieval Augmented Generation — is the alternative: break documents into chunks up front, and at query time include only the chunks most relevant to the question. The benefits are focus on relevant content, scale across very large or numerous documents, and lower cost and latency. The costs are real too: a preprocessing step, a search mechanism that must define “relevant,” chunks that may lack the context they need, and a menu of chunking approaches to choose between.

Chunking strategyHowTrade-off
Size-basedFixed-length character or token chunks, with overlapSimplest and most reliable fallback, works with any content including code; can still fragment meaning
Structure-basedSplit on document structure — headers such as \n## Cleanest chunks when formatting is guaranteed; fails on unstructured text
Sentence-basedSplit into sentences, group N per chunk with overlapPractical middle ground for general prose
Semantic-basedNLP measures how related consecutive sentences are, groups by relatednessMost relevant chunks; computationally expensive and complex

Lila's corpus is mixed: some clean Markdown, plenty of pasted email, a few code appendices. No formatting guarantee.

Your call

The production default. Size-based chunking with overlap is simple, reliable, and works with any document type — the overlap carries characters from neighbouring chunks so meaning doesn't fall into the crack between two cuts. It duplicates a little text; that's the price.
Only if the formatting is guaranteed. Structure-based splitting gives the cleanest chunks on reliable Markdown or HTML, but Lila's corpus includes pasted email with no headers. Fall back to size-based with overlap.
Strongest chunks, heaviest bill. Semantic chunking groups sentences by relatedness and is the most advanced option, but it's computationally expensive and complex. Start with size-based plus overlap; there is no universal best method.

Chunking quality sets the ceiling on retrieval quality. Bad chunks retrieve the wrong “bug” — the insect one, for a software question — and no amount of clever search downstream recovers from that.

4:00 p.m. · Coordinates for meaning

Embeddings, and the flow end to end

A text embedding is a numerical vector representing a text's meaning; each dimension is a value between roughly -1 and +1, and no individual dimension is human-interpretable. Semantic search uses those vectors to find chunks related in meaning rather than by exact words.

One planning fact: Anthropic does not provide embeddings. The recommended provider is VoyageAI — a separate account and API key (VOYAGE_API_KEY), with models such as voyage-3-large. It's free to start and integrates through a plain SDK call, so there's little setup cost to trying it before committing.

Lila's pipeline, in seven steps — the first four run once, ahead of time; the last three run per query:

  1. Chunk the source documents.
  2. Generate an embedding for each chunk.
  3. Normalise the vectors to magnitude 1.0 (embedding APIs generally handle this).
  4. Store the embeddings in a vector database.
  5. Embed the user's question with the same model.
  6. Find the nearest stored embeddings by cosine similarity.
  7. Assemble the prompt: the question plus the retrieved chunks, sent to Claude.

Cosine similarity is the cosine of the angle between two vectors, from -1 to 1, where closer to 1 means more similar. Cosine distance is 1 minus that, so closer to 0 means more similar — which is what a vector search typically hands back.

Store the text with the vector. Lila's index keeps each embedding alongside metadata holding the original chunk. A bare vector is unreadable; retrieval is only useful if you can hand the actual passage to Claude.

Running that pipeline on a real question — "what did the engineering department do last year?" — against a two-result search returns, say, the section-two chunk at cosine distance 0.71 and the methodology-section chunk at 0.72. Both close to 0, both worth handing to Claude; the ranking between them is a rounding error, not a meaningful gap.

Preprocessing is where RAG is won. Steps 1–4 happen long before a user asks anything, and they determine what step 6 can possibly find.

4:25 p.m. · INC-2023-Q4-011

The search that understood everything except the answer

A rep asks Assist about incident INC-2023-Q4-011. Semantic search returns three thoughtful chunks about incident handling in general and misses the one chunk that literally contains the ID — because embeddings optimise for conceptual similarity, not literal string matches.

BM25 (Best Match 25) is the lexical counterweight, in four steps: tokenise the query; count term frequency across the chunks; weight rarer terms more heavily than common ones like “a”; return the chunks containing the most instances of the highest-weighted terms. A rare identifier is exactly the kind of term BM25 spotlights.

Embeddings / semanticBM25 / lexical
Matches onMeaningLiteral terms
Strong atParaphrase, related conceptsIDs, codes, rare or specific words
Blind spotExact term matchesWording it has never seen

Your call

Hybrid search — the standard production pattern. Run semantic and BM25 in parallel and merge the results, so you get conceptual relevance and exact-term precision. A retriever class forwards the query to both indexes; reciprocal rank fusion merges them, summing 1/(rank + 1) across methods so documents ranked highly by both rise to the top. Concretely: if vector search ranks results [doc2, doc7, doc6] and BM25 ranks them [doc6, doc2, doc7], doc2 collects a strong score from both lists and the fused order comes out [doc2, doc6, doc7] — the document nobody ranked dead last beats the one that was merely somebody's favorite.
Trading one blind spot for another. BM25 alone loses the paraphrase and related-concept matching that made semantic search worth having. Run both in parallel and merge — that's hybrid search.
Doesn't address the cause. Smaller chunks don't teach an embedding model to care about a literal ID string. Add a lexical index alongside the vector index and merge the results.

Both indexes expose the same tiny API — add_document and search — which is exactly why they compose. Keep each index isolated and put the merging in a retriever wrapper you can extend later.

5:40 p.m. · One word, one invalidated cache

The rules Dara pins above the desk

Northstar Assist resends the same 4,000-token system prompt and the same tool schemas on every request. Caching is the obvious win — and it is full of small, exam-shaped rules.

RuleDetail
LifetimeOne hour — only useful if you resend the same content within that window
Not automaticYou add a cache breakpoint manually, using the longhand block form with cache_control: {"type": "ephemeral"}
ScopeEverything before and including the breakpoint is cached; content after is processed normally
InvalidationA hit requires the content up to the breakpoint to be identical — even adding “please” invalidates it
Where breakpoints goTool definitions, system prompts, and message blocks: text, images, tool use, tool results
Order & limitProcessing order is tools → system prompt → messages; up to 4 breakpoints per request
Minimum size1024 tokens summed across everything up to the breakpoint
system = [
  {"type": "text",
   "text": NORTHSTAR_SUPPORT_PROMPT,
   "cache_control": {"type": "ephemeral"}}
]

Check the result in usage: cache_creation_input_tokens counts what was written on the first request, cache_read_input_tokens what was reused on later matching ones. Partial hits are possible when only later content changed.

Which of these earns a breakpoint?

The two best candidates there are. System prompts and tool definitions rarely change between requests, and both sit early in the tools → system → messages processing order, so one breakpoint after each covers the stable prefix. Best practice with tools: copy the tools list, clone the last schema, add cache_control to the copy, so you never mutate the originals.
The one thing that always changes. Caching only pays when content is identical across requests. Put breakpoints on the stable prefix — system prompt and tool definitions.
Below the floor. Minimum cacheable size is 1024 tokens summed up to the breakpoint, so a 40-token preamble never qualifies. Cache the system prompt and tool definitions instead.
Self-defeating. A changing timestamp inside the cached prefix invalidates the cache on every single request. Keep volatile values out of the cached region — then the system prompt and tool definitions cache cleanly.

Caching rewards stability, not size. Anything that varies belongs after the last breakpoint, or the cache never hits and you've paid the write cost for nothing.

6:05 p.m. · The airlocked lab

A CSV, a sandbox, and no network

Last request of the day. Lila wants Assist to analyse a 40MB CSV of ticket volumes and hand back a chart.

Code execution is a server tool: Claude writes and runs Python in an isolated Docker sandbox, multiple times per conversation if needed, and interprets its own results. You include the predefined tool schema and implement nothing. The sandbox has one hard constraint — no network access.

The Files API is the airlock. Upload a file once, get back a file ID, and reference that ID in later requests instead of re-encoding the data every time.

How does the CSV get in — and the chart get out?

Exactly the pairing. Upload via the Files API, reference the file ID in a container_upload block, and Claude's code reads it inside the sandbox. Files the container generates come back out as file IDs in code_execution_output blocks, which you then download.
Impossible here. The code execution container has no network access — that's precisely why the Files API exists as the way in and out.
Works once, then hurts. Re-encoding the same 40MB on every request wastes context and money. Upload it once through the Files API and reference the ID from then on.

Constraint first, then pattern. “No network” is not a limitation to route around; it is the reason the Files API is the loading hatch for both samples and finished specimens.

The architect's pocket card

At the retro, Kwame asks how Assist went from a text generator to a system in one day. You answer:

Everything is the same five-step loop. Send tools, get a final answer or a tool_use, execute, return a tool_result, repeat until end_turn. A tool is name, description, and input_schema — and the description is what Claude actually reads. Preserve the whole content array, match every tool_use_id, keep the schemas on every request, and put results in a user message. Batch independent calls. Force a tool with tool_choice when the output shape is non-negotiable. Ask whose machine runs each tool. Keep tools abstract and combinable. Computer Use is the loop with screenshots as results, sandboxed. Your stuff is a tool, your process is a Skill, everyone else's stuff is MCP — connected with mcp_servers plus an mcp_toolset, and scoped by disabling everything then enabling what you need. Chunk with overlap, index semantically and lexically, merge, rerank the shortlist, and contextualise chunks before they're indexed. Then manage what Claude holds: just-in-time, compaction, caching, memory — and remember the cache lasts an hour, needs 1024 tokens, allows four breakpoints, and dies if one word changes.

That is the difference between a model that talks and a system that works: not more intelligence, but better-designed hands and a well-packed suitcase.
